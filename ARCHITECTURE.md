# Architecture

How Switchboard is built: what the binary is, its parts, where each part keeps its state, how it is tested, and where it came from. [README.md](README.md) says what it is for someone using it, [docs/guide.md](docs/guide.md) what each feature does, and [CLAUDE.md](CLAUDE.md) the rules for working on it.

## What it is

- **One binary, `switchboard`.** `switchboard` alone starts the workspace or attaches to it; `switchboard <command>` runs everything else (`switchboard help` lists them). A link to the binary named after a command runs that command too. Claude Code and git are the only programs it expects; anything else (an editor, lazygit, a shell of your choice) runs in a pane like any program.
- **A workspace of crates, the binary at its root.** `switchboard` is the package at the root of a Cargo workspace; `crates/` holds what an app is built from without it: `switchboard-ui` (what everything draws with), `switchboard-plugin-api` (what a plugin and the workspace say to each other), `switchboard-diff` (the diff, an app that also runs alone and the first plugin) and `switchboard-notes` (the notes app, the second). "The crates" below says what each holds.
- **Its own terminal multiplexer, with a server.** A background server owns every pane's terminal, so closing the terminal never stops a running agent; clients attach and detach as with tmux. The layout is saved as it changes and restored after a reboot, each Claude pane resumed with `claude --resume`.
- **Everything built in**: the sidebar and mission control, the palette, menus, messages and tips, each tab's header, the Markdown views (PR description, ticket, link view), the diff viewer with its story and questions, the notes app, the Slack relay.
- **No dotfiles.** `switchboard setup` puts in place what Claude Code needs and nothing else: Switchboard's hooks, instructions, skills and statusline as a Claude Code plugin that only the Claude in its panes loads, the statusline from a module of the plugin's that layers it over your settings in memory (which an administrator's plugin answering Claude Code's settings first can skip: the server watches each session's statusline from SessionStart, and one still silent 15 seconds after a turn ends is said once and reported by setup, `Agents::statusline_overdue`), and its permissions from its skills' `allowed-tools` and a hook of the same module on Claude Code's permission decision (or, with Settings' "Load Switchboard as a plugin" off, all of it in `~/.claude` for every Claude, the statusline and permissions merged into your Claude settings). The only configs of other programs it offers are what the workspace itself needs: Option as Alt and Notes' Cmd keys in a terminal's config, never an editor's. An app Switchboard runs gets Switchboard's settings at launch, by flags or environment, never by changing its config: lazygit in a pane's place is given `LG_CONFIG_FILE` naming Switchboard's copy and then your config, so Esc quits it there unless your config says otherwise.
- **Runs on** x86_64 Linux, x86_64 macOS and aarch64 macOS, built with the latest stable Rust, pinned in `rust-toolchain.toml`.
- **Crates are fine; system packages are not.** Pure-Rust crates (rustls, not OpenSSL; zbus, not libdbus), so a build needs rustup and a C compiler, and a user needs nothing. The `net` feature (on by default) holds the only C the build compiles, TLS's, so `cargo check --no-default-features --target aarch64-apple-darwin` type-checks every macOS path from Linux.

## The parts

```
switchboard (client) ──Unix socket── switchboard server ──PTYs── shells, claude, ...
switchboard hook <event>  ──┘            │
switchboard <command>     ──┘            ├─ background tasks: GitHub, Linear, calendar,
                                         │  Slack, transcripts, git, claude -p
                                         └─ ~/.local/state/switchboard (layout, state)
```

- **Server** (`src/mux/server.rs`): one task owns all state (`Server`): sessions, tabs, panes, clients, overlays. Everything else (client sockets, PTY readers, timers, background lookups, file watches) sends it `Event`s over a channel; it handles them in order and draws the clients that changed. So nothing locks, and a slow lookup never holds up drawing. It runs on a tokio runtime; blocking work goes to `spawn_blocking` or a thread of its own. A pane's directory is `Server::pane_dir`, which everything that names a tab, lists the panes or opens beside one reads: the `cwd` its Claude's last hook reported, while the same process group is in front, else the directory of its program (`Pane::cwd`), and never one that has been removed (`util::nearest_existing`); a tab's `@tab_dir` option, while that directory is there, takes the place of every one of its panes' (the review tab's PR worktree, whose Claude works from the main clone), though a split, a new tab, a respawn, a tool in a pane's place and the keys that open a tab in a directory still start in the pane's own (`Server::pane_own_dir`), and a respawn takes the option away. The saved layout keeps the program's own directory, where `claude --resume` finds the session. One server runs per state directory, held by a lock (`src/mux/socket.rs`); a client that finds none starts it detached (`setsid`), its output in `server.log`.
- **Upgrading in place** (`src/mux/upgrade.rs`): `switchboard upgrade` (and `M-p`'s action, which `switchboard upgrade --latest` asks for from a command that waits on it, answered by the new build once it has taken over or with why it didn't build, and `switchboard update` once a release is in place) restarts the server on the binary at the path it started from, without ending anything. `M-p`'s action first builds the main clone of the checkout a build from a clone was built in (`src/mux/latest.rs`, from build.rs's `SWITCHBOARD_MAIN_CLONE`, read from the checkout's `.git` by `src/mux/main_clone.rs`, empty in a release build), since a worktree is removed once it lands: only when the clone is on its default branch with nothing uncommitted, after fetching origin and fast-forwarding to it (a try's server names its worktree in `SWITCHBOARD_CHECKOUT` instead, built as it is), puts the result in place of the server's binary when that is a copy, and restarts only when the file at that path is no longer the one the server started from (its device, inode, size and modified time). A build put there by hand since the server started is restarted on as it is only when the commit its `--version` says has the clone's HEAD, once brought up to date, in its history (`latest::built_from_head`), and is built over otherwise. Cargo's JSON messages are read as they come and the build tells the server what it is doing (`latest::Report`: the fetch's commits and time, the build begun, the crates built at most twice a second, the install, cargo's error lines), which `src/mux/build_row.rs` shows in the sidebar's build row and a steps box that lets keys through to the tab (`ui::Step::Through`); the crates each checkout's build counted are kept in the state directory's `restart-build.json` for the next build's meter. The new build shows "Restarted on <commit>" from its own `SWITCHBOARD_COMMIT`, so the handover carries nothing for it. A server whose binary is in a cargo target directory (an ancestor holding cargo's `CACHEDIR.TAG`), which any worktree's build or test writes over, never restarts on that path: the build goes to `~/.local/bin/switchboard` when there is one, else to a copy in `~/.cache/switchboard/build`, and the restart execs that (`upgrade::Pending`'s `on`). The new binary is first asked `server --handover-version`, and only one answering the handover's version is exec'd. The server stops taking connections (they wait in the socket's queue), has every connection stop reading, pauses every pane between two reads (`src/mux/pty.rs`), answers the commands under way, has each connection write what is queued for it and give its socket back, then writes `handover.json` in the state directory (the saved layout's shape, plus each pane's master descriptor, pid, size, unwritten input and screen as the bytes that draw it again, `src/mux/replay.rs`, a frame the program was drawing included and what the emulator held of a sequence not yet whole; each terminal's connection by descriptor with its session, size, the frame bytes in flight and the keys its parser held (a paste not yet ended); the listening socket and the lock; each pane's Claude's state; the pictures each pane's program gave the terminal, for drawing as sixel, and the cell the terminal said it draws them in; the connection of the `switchboard upgrade` that asked) and `execv`s `switchboard server --handover <file>` with those descriptors left open. The process and its pid stay the same, so the panes' programs stay its children and never see their terminal close. The new build takes each pane up (`Pane::adopt`) instead of starting one, rebuilds the sessions and tabs, tells each program its size again (SIGWINCH), serves each connection again from the frame it was at and redraws its screen whole, and answers the asker. Anything failing before the exec, or the exec itself, resumes everything as it was. What isn't carried: the overlays open (menus, mission control, copy mode, a prefix key pressed), a pane's scroll region, tab stops and character sets (a full-screen program redraws on the SIGWINCH), what background lookups were under way (asked again), and the processes they had started, left unreaped until the server ends.
- **Main ahead of the build** (`src/mux/behind.rs`): the server counts, off its task, the commits on its main clone's `origin/<default>` (else the local default branch) that the commit it was built from (build.rs's `SWITCHBOARD_COMMIT`) lacks, as it starts, every hour, and when a tab sets `@tab_landed`, with no fetch of its own, and shows one notification under the `behind` source while there are any, its count updated in place and its menu leading with `M-p`'s restart (`choices::Do::Restart`); dismissed, it stays away until main moves. A release build, or a try naming its checkout, has no main clone and counts nothing.
- **Panes** (`src/mux/pane.rs`): a PTY and a terminal emulator (alacritty_terminal) each. portable-pty opens the PTY and starts the program; from then on the pane holds the master's descriptor and the program's pid (`src/mux/pty.rs`), with a thread reading it and one writing what is typed, both waiting with `select` beside a pipe that pauses them between two reads or writes, so a pane can also be taken up from a descriptor and a pid. The emulator's replies to programs' queries go back to the PTY, with what the attached terminal says of itself (`src/mux/terminal.rs`): its cell's size in pixels, which the client sends with its size and each PTY is given, and its colors, asked as it attaches (OSC 10, 11 and 4) and told to a program that asks the same; OSC 52 from the pane in front of the client acting now goes to the clients' clipboard (Settings' `pane_clipboard`), and from any other pane nowhere. Every pane's environment carries `SWITCHBOARD` (the socket) and `SWITCHBOARD_PANE` (its id), which the hooks and commands use as tmux's `TMUX` and `TMUX_PANE` were used, `GH_BROWSER` (`switchboard open-url`), so gh's `--web` opens in the Chrome profile `browser.json` gives the site, and, while `claude_plugin` is on, `CLAUDE_CODE_PLUGIN_DIRS` naming Switchboard's plugin (`src/setup/plugin.rs`), so Claude run there loads its hooks, skills and instructions; a headless `claude -p` Switchboard starts for itself leaves it out (`plugin::headless`). `src/mux/passthrough.rs` lets the notes pane alone send kitty's graphics commands on to the terminal and take easy mode's Cmd keys; for a terminal that gets sixel (src/mux/graphics.rs: by its answer to DA1 by default, or any with Settings' "Image protocol" on sixel), `src/mux/sixel/` keeps those commands instead (`kitty`: each image's PNG and placement, per pane, handed over by an upgrade) and the server draws each picture itself as sixel, for a terminal without kitty's (Windows Terminal).
- **Layout** (`src/mux/layout.rs`): each tab is a tree of splits. A lone pane (one, or zoomed) fills the width unless Settings' `lone_pane_width` (off by default) caps it, against the sidebar (`layout::capped`, through `Session::area_for`, which every placement, resize and hit test asks), the columns beside it drawn by `compose::draw_spare`; mission control always fills the width beside the sidebar. A drag of the rule at a lone pane's edge (`Drag::Edge`) and the resize keys on a lone pane set that tab's own width, its `@lone_width` option (`Server::set_own_width`, `layout::lone_moved`), which `Session::area_for` takes before the setting and the layout saves with the tab's other options. Overlays sit above it: the boxes of `src/ui/` and mission control (what tmux's popups were).
- **The sidebar's width** (`Session::sidebar_width`, `src/sidebar/config.rs`'s `columns_at`): none takes `sidebar.json`'s; a drag of its edge (the server's `sidebar_edge_mouse`, before mission control takes the mouse, whose list of views in the sidebar's place shares the edge) or the pane resize keys while it has the keys give it one, between `config::LEAST` and half the window, which `fit_sidebars` lays every tab out beside and `src/mux/persist.rs` saves with the session, so a restart and an upgrade keep it; Settings' `sidebar_resize` off passes it over without forgetting it.
- **Drawing** (`src/mux/compose.rs`): per client, a ratatui `Buffer` is filled with the tab (sidebar, panes, borders, and the tab's header from `src/mux/header.rs`) and any overlay, and only the cells that changed are sent, each a pane's program made part of a hyperlink (OSC 8) inside it, kept beside the buffer since a cell can't carry one. The built-in screens draw into that buffer. An image atom (`src/ui/images.rs`) describes a picture: it writes kitty's Unicode placeholder cells into the buffer and adds itself to the frame's `images`, with a key made of what it is drawn from and how to raster it, and never chooses how it reaches the terminal. That is `src/mux/graphics.rs`'s alone, for every picture, the server's and the panes': It decides by `image_protocol` (`for_terminal`): `kitty` or `sixel` gives every terminal that way, as chosen, whatever it is; only `auto`, the default, goes by each terminal, by what it attached as (`TERM`, `TERM_PROGRAM`, `COLORTERM` and `WindowsTerminal` where `WT_SESSION` is set, `client::attaching_as`, kept on the client and in the handover): kitty's protocol where it speaks it, sixel for one whose answer to "what are you" (DA1, `CSI c`, asked as it attaches) lists sixel (`Server::terminal_answered`, which marks the client `answers-sixel`), neither otherwise, a Windows Terminal that gets neither having its picture cells blanked rather than shown as boxes (`pictures_blank`). The apps in panes can't see that answer, so they ask the server what the terminals showing their session get (`switchboard show @graphics`, `Server::graphics_for_pane`: `kitty`, `sixel`, `round` or `none`), and draw their pictures and round ends by it; with nothing attached the answer is empty and they go by the terminal they run in; a terminal that gets neither way has picture cells blanked and their half circles made spaces of their color (`fix_ends`), whatever the apps last asked, and a half circle a program of yours draws in its pane is left to the terminal. Everything else drawn one way for one terminal and another for the rest is decided there too, so nothing else reads a terminal's name (`tests/it/graphics.rs` checks): truecolor (`truecolor`, which `status::theme` draws the canvas's colors by), the mouse pointer's shapes (`pointer_shapes`, whose rule is `crates/ui/src/pointer.rs`'s `takes_shapes`, so an app alone in a terminal, with no server to ask, follows the same one), and the half circles at the ends of kit's objects (`ends`): sixel pictures of them where it gets sixel, every half-circle cell in the frame turned into one once it is drawn (`sixel::draw_ends`), the glyphs where the terminal draws them itself (Ghostty) otherwise, and spaces of the fill elsewhere, kit given `caps` by `round_ends`. `Server::graphics_of` gives a frame its `Graphics` from that (none, each atom's text form, with `server_images` off too) and the cell the images are rastered at, `for_panes` says whether a client is passed the panes' graphics commands or has the server draw them, and `apps_draw` whether an app in a pane draws pictures at all. With kitty's, each client's `Screen` keeps an `ImageCache` of what its terminal holds, so a frame sends (inline, `t=d`) only an image new or changed, deletes one no longer placed, and sends them all again when it draws the screen whole; the shadow under a box is a placement under the text, which only kitty's can be, so with sixel it is its text form (`Graphics::under_text`). Only `src/mux/graphics.rs` writes kitty's graphics commands (the server's, and those Notes and the image view give by a PNG's path) and only `src/mux/sixel/encode.rs` a sixel; `tests/it/graphics.rs` fails on any other file in `src/` whose source writes either out (an escape in a string, the byte in an array), or any DCS, and a frame's sixel (`compose::Placed`) can be made only inside `src/mux`. An avatar's photo comes from `Server::photo` (`src/photos/`), which loads it off the task the first time it is asked for: from `~/.cache/switchboard/photos/` while under 30 days old, else from Slack (`users.info` with the relay's bot token), Linear (`avatarUrl`) or GitHub (`avatars.githubusercontent.com`), or for someone known only by an address (a calendar's attendee, kept under the address's SHA-256) from Linear's user by that email and else Slack's `users.lookupByEmail`, and draws every client again once it arrives, mission control's snapshot taken again with it. An overlay that places images draws into the whole frame (`Overlay::draw_frame`): mission control's boards place theirs there (`render::Image`, a meter, a series, a switch or a keyboard, or an avatar, by its `Shape`: the Calendar's going attendees' photos and the Inbox board's actors' and comment writers' (`src/mission/inbox_board.rs`), from the snapshot's `photos`, which `mission_prepare` asks `Server::photo` for, the Autopilot board's meters, the Resources board's sparklines, the Keys board's keyboard as a heatmap of the week's Alt keys (`src/mission/keys_board.rs`, `images::keyboard`, its letters rastered from a 5 by 7 font the module carries, since the binary has none), the Settings board's switches (`src/mission/settings_board.rs`, drawn from the Settings view's own rows, each option carrying its default and whether it changed), and the Usage board's chart stacked by tab, limit meters and request sparklines, `src/mission/usage_board.rs`, drawn from the model `src/usage/charts.rs` works out off the task from the statusline's `usage/spent-<day>.tsv`, the survey's `usage/sessions-tabs.tsv` and the request audit's hours and sources), a tab's history (`src/history/view.rs`) its state lane and context chart (`images::lane`, `images::chart`) under the pane's screen as it was, and `src/ui/picture.rs` shows a picture full size over the pane that asked (`switchboard picture`), decoded off the server's task and kept on the pane's place before each draw, as `src/ui/pictures.rs` shows the pictures `switchboard look` is given in the side panel (the empty columns beside a narrow lone pane), stacked, the pane keeping its keys, and hands them to the desktop's viewer where there are none. With sixel chosen, for a terminal that gets it, the panes' graphics commands are kept rather than passed on (`src/mux/sixel/kitty.rs`: a PNG by its path, from Notes and the image view, or its data inline in parts, from the Markdown views, held to a size and carried across `switchboard upgrade`), and once the overlays are drawn every kitty placeholder cell in the frame is blanked, and those still as a pane allowed to send pictures drew them before anything was drawn over it (not a copy of a pane's text, as mission control's cards and a peek make), and those naming one of the frame's own `images` wherever they are, are gathered into pieces of a picture (`src/mux/sixel/place.rs`), each drawn as sixel beside the buffer the same way, written after the text and again whenever a cell under it is sent, its cells erased once it is gone, never on the last row, which a pane reaches with no status line under it; reading, fitting, quantising (NeuQuant past 256 colours) and encoding a pane's picture run off the task (`src/mux/sixel/encode.rs`), as does rastering and encoding one of the server's own drawn from a photo (`Placed::photo`: an avatar, a Slack picture) or larger than `AT_ONCE_PIXELS` (a picture shown full size), while a smaller drawing of a few colours (a switch, a meter, a chart) is rastered and encoded on the task as the frame is, as kitty's are sent, so it never shows a blank frame as it changes; the results are kept in caches held to a size, and a picture's cells stay blank until it is drawn. The cell size it is drawn at is what the terminal answers to `CSI 16 t`, asked as it attaches: Windows Terminal's sixel cell, 10 by 20 pixels whatever its font.
- **Input** (`crates/ui/src/input.rs`, `src/mux/keys.rs`): the client sends raw bytes; the server parses them into keys, mouse and paste, each with its raw bytes, matches bindings (the defaults are what tmux.conf bound, under the same keys; `~/.config/switchboard/keys.json` changes them, each key it binds kept in `Bindings::yours` or `yours_prefix` for the Keys view's "yours"), and passes anything unbound to the focused pane, encoded again for it: mouse events for its position and mode, and keys in the form its program asked for. The mouse pointer's shape follows what a click would do (`crates/ui/src/pointer.rs`): after each mouse event, and after each frame it draws for where the mouse last was (a key may have put another tab, a box or copy mode under it), the server asks the overlays from the top down (a box from its `Drawn`, mission control from its hits), then the sidebar, the header, the panes and the lines between them, and sends `OSC 22` with the CSS cursor name to a Ghostty or kitty client only when the shape changes, with every movement reported (1003) for such a client while hover_highlight is on. Over a pane the shape is the text beam, unless the pane's app names another for it: an app says what is under the mouse from where it last drew, through the plugin API's `Action::Pointer`, which `src/diff/host.rs` keeps as the pane's `@pointer` option (a CSS cursor name, gone when the pane's program is replaced), and the server shows it over that pane (but in copy mode, where the clicks are its own) and sets each client's pointer again where its mouse last was (`Server::sync_pointers`), since the app names the shape after the server has passed it the movement. The diff does (`App::point` in `crates/diff/src/app.rs`, its `shape_at` following what a click does), and alone in a terminal writes `OSC 22` itself where the terminal takes it (`pointer::here`), the beam put back as it quits. As tmux's `extended-keys on` did, the client asks the terminal for keys told apart (the kitty keyboard protocol's flag 1 and modifyOtherKeys level 2, `extended_keys` setting), which the parser reads in either form, and a key reaches a pane as CSI u only when its program turned on the kitty protocol (which alacritty_terminal keeps) or modifyOtherKeys (watched for in its output, `src/mux/extkeys.rs`), its old bytes otherwise: Ctrl-Shift-P reaches Notes as itself and a shell as Ctrl-P.
- **Client** (`src/mux/client.rs`): raw mode, the alternate screen, mouse and paste reporting on, keys told apart where the terminal can; stdin to the socket, the socket to stdout; resizes sent on SIGWINCH, with the window's size in pixels; the terminal put back however it ends, the pointer's text beam included where it takes `OSC 22`. It refuses to attach inside a pane of its own server. On the server's side each attached connection is one task reading into a buffer of its own and writing from another (`serve_client`), so it can stop between two frames and be handed to a new build; the client never knows.
- **Apps in panes**: what ran in a pane under tmux (glow and less for a PR or ticket, diffview in Neovim, the notes app in Neovim) is a program of Switchboard's own run in a pane the same way: `switchboard pr-view`, `ticket-view`, `link-view`, `view`, `diff`, `notes`, full-screen programs drawn with ratatui and crossterm. The server stays a multiplexer, opening them in a split or in a pane's place (the pane parked until the program ends), or in the side panel beside a narrow lone pane, its spare columns, where M-v's PR view first closes whatever is there (`in_place::clear_beside`), and each app is built and tested on its own.
- **Commands** (`src/mux/commands.rs`): what scripts and skills used tmux for (list the tabs, open a tab, send keys to a pane, read its screen, rename a tab, set an option, say something) is `switchboard <command>` sent over the socket and run on the server's own state. A command run by hand (`ClientMsg::Command`'s `by_hand`, which only the binary's own `switchboard <command>` sets) from a pane is held to its own tab and kept off Switchboard's own marks (`Server::refuse_by_hand`, `commands::own_mark`), since Claude may run `switchboard set` and `switchboard respawn` without asking; `switchboard respawn` asks `respawn-program`, which builds the command on the server and starts only `respawn::allowed`'s programs from a pane. Switchboard's own programs ask without `by_hand`.
- **Agent state** (`src/agent/`): Claude Code's hooks, from Switchboard's plugin (or `~/.claude/settings.json` the old way), run `switchboard hook <event>`, which sends the hook's JSON and `SWITCHBOARD_PANE` to the server, which marks the pane working, waiting or done and rolls that up into its tab. A wait belongs to whoever asked (the conversation or a subagent, the hook's `agent_id`) and to its call (the hook's `tool_use_id`, `PaneAgent::wait_call`): a new prompt, a finished turn, a new question or request, a session starting or ending, or the one waiting starting another tool ends it, and a call ending ends it only when it is the call waited on, or when either hook names no call, so the conversation's other calls ending while it asks (a backgrounded agent returning, a monitor firing) leave the tab waiting. A question the transcript shows unanswered whose hook never came is a wait on its call too, unless the conversation has since run a hook that could have followed its answer (`went_on`: any that marks a state but another call ending). Settings' `hook_log`, off by default, writes each hook's event, tool, pane, call and subagent to `server.log`, never its words. In a tab of autopilot's hands-free mode (`@autopilot_handsfree`) it answers a question box with a deny naming the options it chose (the recommended one, else the first) and a turn ending on a question with a block (`src/agent/hands_free.rs`), the only hook output `switchboard hook` prints, and writes each choice's `Decided hands-free` line into the item's plan note, or under the item in its note, off its task under the note ID's lock (`id::rewrite`). The step a loop says it is at (`@agent_phase`, `land-lock phase`) is kept with when each began (`PaneAgent::phases`, the last 32, handed over in an upgrade), which autopilot's board times its stages from. A pane keeps a state only while it runs Claude (`src/agent/sessions.rs`): its program in front is named as Claude Code's executable is, or a process in front has a session file in `~/.claude/sessions` written after that process started, since nothing removes the file of a Claude that ended without saying so and the kernel hands its pid out again, so a shell that gets the pid back is not taken for Claude. A `PostToolUse` of Bash running `gh pr create` or `gh pr view` also gives the PRs whose addresses it printed (`src/agent/prs.rs`), which the tab then follows beside its branch's, kept in its `@tab_prs` option (`src/tabs/prs.rs`): one is current (`@tab_pr_current` when picked, else the branch's, else the newest the lookups know is open), which `Server::tab_pr` and `tab_pr_repo` answer, so everything that reads a tab's one PR (its label, M-v, M-d, the sidebar's facts, the cards) reads the current one, and `Server::tab_prs` gives them all; each is asked about with the tabs' PRs (`TabInfo::listed`), and a merged or closed one leaves the list at the lookups' answer after one that found it so with the tab in front, but a merged one the session made while it is still current (the tab in its repository, on its branch or on the default branch with no other PR it made open, `prs::merged_stays_current`), so a landed tab back in the main clone keeps it.
- **Persistence** (`src/mux/persist.rs`): the layout (tabs, splits, each pane's directory and program, its Claude session) and tab options (a tab's number, `@tab_number`, the smallest free when it opened and kept while it is open, and when it opened, `@tab_opened`, which its age in the header and on its card is read from, among them), written on change, a layout with fewer panes than the last written only once it has held a minute, so the shells a shutting-down computer hangs up one by one never reach the file; restored when a server starts with no sessions (`auto_restore` setting; `save_contents` keeps what panes show). The file before each write is kept as `layout.json.1`, and a server starting fresh keeps the larger of the two as `layout.json.start` until its next fresh start, which `switchboard restore-layout` brings back beside the workspace's one tab.

- **The phone app** (`src/phone/`): `switchboard phone run` is a process of its own, as the Slack relay is, serving a web app (`assets/phone/`, plain HTML, CSS and JavaScript, read through `assets::text`, with markdown-it vendored beside it for Claude's replies, built into elements from its tokens with raw HTML off, never through `innerHTML`) over HTTPS with axum and rustls on the computer's Tailscale addresses alone (`web.rs`; Tailscale's `status`, `cert` and `whois` are `platform`'s). Every request passes `guard.rs` (the owner and a listed device by `whois`, kept a minute; the cookie a device was paired with, `pairing.rs`; a write's `Origin`). What it shows comes from the server's `watch` command, a connection the server keeps (`Answer::Keep`) and writes a JSON line of every Claude tab to a moment after anything changes, passed on as server-sent events; a tab's turns are read from its transcript in the phone's process (`turns.rs`). An image from the phone's photo library is kept first in a folder of its own (`images.rs`: a PNG, JPEG, GIF or WebP by its first bytes, up to 20 MB, under a name made there), and a message naming it has its path typed on a line after the text, which the channel reads back from the transcript as the image. It changes anything only through the server's `answer` (a prompt answered with `mission::answer`'s keys, or a message typed), `seen` and `kill-tab -s` (a tab closed, asked about on the phone first), which refuse a pane not running Claude and log what the phone did, with no notification (`serve.rs`); `answer` is refused typed in a pane. Pairing is a code typed in the box `phone-pair` opens. A tab starting to wait sends a Web Push naming it, encrypted (RFC 8291) and signed (VAPID) with aws-lc-rs in `push.rs`, its key a secret, over HTTPS checked against Mozilla's roots (`net::post_bytes`, webpki-roots) rather than macOS's verifier, which panicked under `phone run`; each push's outcome, a panic under it included, goes in its log (`log.rs`), and `phone test` (M-p's "Send a test notification to my phone") sends one from any process. The page's service worker keeps a copy of the app's own files, never `/api/`, so the installed app opens offline, and the tab of a push tapped last, which it keeps for the page to ask for as it starts or comes back, until the page says it took it (`notificationclick` and `openTapped`), since iOS can drop a message posted to a frozen page and open a window at `/`. After `switchboard upgrade`, `upgrade::adopt` has `serve.rs` start the app again in its marked tab when its lock names another binary than the server's (its path and modified time), once the old one has exited, since a pane's program otherwise keeps the build it started with. Tailscale is required here and nowhere else

Each part beyond the multiplexer has the same shape: modules that work on files and plain data, tested without a server, and a `serve.rs` whose `impl Server` puts them on the server (its keys, its tick, the answers of its background tasks as an `Event` of its own). Anything that reads the network, starts a process or reads more than a small file runs in a task and reports back, so nothing on the drawing path waits.

## Tests

Each crate under `crates/` has its own tests (`cargo test -p <package>`): the API's types go round as JSON and refuse a newer protocol, `switchboard-diff`'s `tests/alone.rs` runs its binary in a terminal of its own with no server, under a home made for the test, and reads the branch's files off its screen, and `switchboard-notes`'s does the same on a note of the test's `~/Notes`, asking the running app which note it shows from a second run. The notes app's unit tests are answered by a stand-in for the workspace (`host::tests::Stand`), the workspace's real answers being tested where they are given (`src/notes/host.rs`). What follows is the `switchboard` crate's.

Unit tests sit beside the code. Integration tests are in `tests/`, the modules of `tests/it/` one binary, and the three files that change the process's environment (`tests/day.rs`, `tests/integrations.rs`, `tests/update.rs`) binaries of their own: `tests/common` starts a server of the test's own in a temporary home under `/tmp` (short, since a Unix socket's path can't be over 104 bytes on macOS), runs commands against it, and attaches a client that reads what the server draws through a terminal emulator, so a test looks at the screen as a person would (`ui::headless::Screen`, `switchboard headless`'s). A command the server runs (`mux::commands::NAMES`) is sent over the socket from the test's own process, as the binary would send it (`TestServer::run` through `socket::run_command_at`, from the test's temporary directory), so the thousands a full run asks start no process; the binary is run (`run_binary`, or `run` for a program of its own) only where the process is what a test is about. Services are stand-ins on 127.0.0.1, reached by moving their address (`SWITCHBOARD_GITHUB_API`, `SWITCHBOARD_GITHUB_GRAPHQL`, `SWITCHBOARD_LINEAR_API`); Slack, Claude and the desktop's tools are stand-ins on the test's PATH. Every wait is scaled by `common::patience()`, the load average over the cores (`SWITCHBOARD_TEST_PATIENCE` sets it), so a busy machine makes a test slower rather than failed. No test reaches the real server, the real home or a real service. Each stand-in is as strict as what it stands in for, so a test passes only when the code calls it rightly: `tests/common/stand_in.rs` writes the programs (Claude Code with its options as commander reads them and its prompt on stdin, `gh`, a release of `switchboard` that answers only to that name, the clipboard and opener tools, `security`, `uname` and `sysctl`, `cargo`, lazygit), each refusing a call the real one refuses with its words and exit status before it runs the test's answer, and `src/demo/services.rs` the services (GitHub's REST and GraphQL, Linear, Slack), which `switchboard demo` serves its made-up data through and `tests/common/http.rs` takes from the library, each refusing the wrong method, an unknown path or a missing or wrong token as the real one answers it. Each writes down what it refused, and a test whose stand-ins refused anything fails, however quietly the code took the failure. A test server starts with stand-ins for what its test gave none of (a Claude Code and a gh that aren't signed in, the desktop's clipboard, openers and Chrome), so no test reaches the computer's own. The library's unit tests include both (`crate::stand_in`, `crate::fake_http`), and `tests/it/stand_ins.rs` shows each refusing a wrong call.

Debug builds keep only line tables, and the crates no debug info, since every test binary links all of them; the crates build at opt-level 1, since every test draws through alacritty_terminal and ratatui, and the crate's own code at 0, so its incremental builds stay quick. CI (`.github/workflows/ci.yml`) first sorts a pull request by the files it changes (documentation and skills alone; what only a Mac checks or what the caches are keyed on, as `src/platform/`, the workflows, `Cargo.lock` or a `Cargo.toml`; or anything else), running the macOS jobs only for the second and for every push to a merge queue train's branch, so nothing the queue merges goes in without them (a PR merged otherwise gets them from main's push after it), and skipping them otherwise by each job's own `if:`, so the required checks still report, the third's Linux clippy job running clippy for macOS's paths from Linux (`--no-default-features --target aarch64-apple-darwin`, on main's runs too, so their cache holds that target) so a macOS-only compile error or warning still fails the PR; a push to main runs every job too, unless its tree is that of a train's head whose run passed in the last day (a train's last merge, the queue merging a train's PRs with the heads it tested), when it skips all six jobs, unless the train changes what the caches are keyed on, which only main's runs save; it checks the formatting, and runs clippy with warnings as errors (with the `net` feature and without it) and the tests, as jobs of their own side by side on Linux and in one job on an Apple silicon Mac, since the account runs few macOS jobs at once, the tests through cargo-nextest on 8 threads, since most wait on a deadline (the Linux job checking that nextest lists every test `cargo test` does); Intel Macs are built only by the release. Each job caches the dependencies' builds with `Swatinem/rust-cache`, whose key follows the toolchain, `Cargo.lock` and the profiles, so a change to any of them saves a fresh cache.

## Releases

The diff releases apart from Switchboard: `crates/diff` has a version of its own, and a bump of it on main makes `.github/workflows/release-diff.yml` build `switchboard-diff` alone and publish `switchboard-diff-<version>-<target>.tar.gz` for each target, with its checksum and its signature by the same key, under the tag `diff-v<version>`, never as the repository's latest release, so `install.sh` and `switchboard update` (which reads only `v<version>` tags) still find Switchboard's; a version ending `-dev` is never released. `install.sh --diff` installs the newest `diff-v` release, and `switchboard-diff update` puts a newer one in the binary's place, checked as `switchboard update` checks Switchboard's; its build sets `SWITCHBOARD_RELEASE`, as Switchboard's does, so only a release looks for a newer one by itself. Notes releases the same way: a bump of `crates/notes`'s version makes `.github/workflows/release-notes.yml` publish `switchboard-notes-<version>-<target>.tar.gz` under `notes-v<version>`, which `install.sh --notes` installs. The rest of this section is Switchboard's own releases, whose version is the workspace's (`[workspace.package]`).

A version bump on main is a release: when `Cargo.toml`'s version there has no release, `.github/workflows/release.yml` builds the commit that set it for the three targets with `SWITCHBOARD_RELEASE` set, tags it `v<version>` once they have built, and publishes each as `switchboard-<version>-<target>.tar.gz` with its SHA-256 and its signature (`ssh-keygen -Y sign` with the `release` environment's `RELEASE_SIGNING_KEY` secret, which only main's runs can read, the public halves in `src/update/release-signing-keys.pub`, compiled in, and copied into `install.sh`), its actions pinned by commit. Each release carries the `install.sh` of the commit released, signed and with its checksum beside the archives (every release workflow attaches it, and the diff's and Notes' too), so the README's install runs a release's installer (`releases/latest/download/install.sh`) rather than `main`'s; it installs the newest into `~/.local/bin` and says to run `switchboard setup` next, running it only with `SWITCHBOARD_SETUP=1`; `src/update` finds a newer one, checks its checksum and signature (a debug build also trusting `SWITCHBOARD_RELEASE_KEY`'s key, the tests' own), swaps the binary only once it runs, runs `switchboard setup`, and offers a running workspace a restart on it in place (`upgrade_after_update`). Only a release build looks by itself (`SWITCHBOARD_UPDATES` says otherwise), so a binary built from a clone is never offered a release in its place, nor given one by `M-p`'s "Update Switchboard" without `--force`. What the setup writes is compiled in, so the first run of a new build (`switchboard` attaching, `setup::refresh`) writes the plugin (which the server also writes as it starts) and brings the parts already set up up to date, once per build (`~/.local/share/switchboard/setup-build`), moving nothing between the plugin and `~/.claude`, where `.githooks`' post-merge once ran setup.sh. `switchboard --version` names the commit it was built from. A build from a clone reads `assets/` from that clone while it is there (`src/assets.rs`: the checkout build.rs recorded, else its main clone, `SWITCHBOARD_CHECKOUT` in the environment first, never a clone `trust` finds someone else's, decided on each read with no git run, so a server whose worktree went goes on to the main clone, each file read again only when its size or modified time changes), falling back to what it carries for a file missing or JSON that doesn't parse, with Settings' `assets_from_checkout` on; the skills' walk is `src/skill_files.rs`, which build.rs includes by its path, so the two agree on what ships. The server looks at the clone every 10 seconds off its task (`plugin::follow_clone`) and runs `switchboard setup --refresh` (a process of its own, since a run settles the way setup puts Switchboard once) when its skills, Claude's settings or the part of CLAUDE.md changed, or the setting did, which brings the plugin and every part already set up up to date, its mark hashing what they are made from.

## Conventions

- Each module opens with a comment saying what it is and why it works as it does; a part ported from a Node, shell or Lua file names that file, so its history can be followed.
- Behavior matches the tmux version unless that depended on tmux or macOS; where it changes, the comment says so.
- No tmux, no Node, no external program but Claude Code and git (and the platform's own tools in `src/platform/`). Desktop differences go through `src/platform/`.
- Files written whole go through `util::write_atomic`; JSON numbers through `util::js_number`, so files read as they did. The folders it (and `append_quietly`) makes are their owner's alone (`util::make_dirs`, 0700), and the server makes the config, state and cache folders so as it starts, tightening those an earlier build left open (`util::make_private`).
- Server state is touched only by the server task; anything slow runs elsewhere and reports back with an `Event`.
- Tests: unit tests beside the code; integration tests in `tests/` with a temporary home and a server of their own, never the real one.

### Not ported

What the tmux version did that the binary doesn't yet, so a part that brings one back knows where it stood:

- **The diff**: diffview read the change again by itself when Neovim got the focus back and on a save, as well as on `R`; `M-d`'s diff reads it again on `R` alone (`crates/diff/src/app.rs`'s `refresh`).
- **Commands**: Rename's ticket and shaping shortcuts (tab-name.zsh's `t` and `s`): "Rename the tab" takes a typed name, and the shortcuts are in the name asked for after `M-t` alone (`src/extras/naming.rs`).
- **Sealed tries**: on Linux, which has no sandbox without installing another program (bubblewrap, firejail), `--sealed` refuses. On macOS, the try attaches in the terminal it was run from, or `--print`'s command in another, where the script opened a Ghostty window; `--npm-ci` for lib's packages is `--fetch` for the crates.
- **Elsewhere**: `switchboard setup` adding the worktree commands' shell functions to your shell's startup file (nothing of the workspace's needs them: its keys and mission control's menus start work as the tab's own command, through the binary).
