# The crates and the plugin boundary

**The crates and the plugin boundary.** `switchboard`, the multiplexer and everything built into it, is the package at the workspace's root, and `crates/` holds what an app is built from without it. `crates/ui` (`switchboard-ui`) is what everything draws with (`kit`, `draw`, `text`, `field`, the themes and `Look`, `input`, Markdown, a terminal asked for its colors, and the boxes a program asks in: the `Overlay` trait with `message`, `confirm`, `menu` and `picker`), which `switchboard` gives at the paths it had (`ui::kit`, `ui::menu`, `mux::input`, `sidebar::text`, `status::theme`, `views::markdown`); an overlay draws into cells, and one that places the server's images takes the frame it is handed for the server's (`compose::Frame::of`), drawing nothing more into any other; it knows no settings file, so the few settings it follows are asked of the program (`switchboard_ui::settings`, which `settings::share_with_ui` answers as `cmd::run` starts), and a new one it reads goes in its `DEFAULTS` with the schema's default, which a test in `src/settings.rs` keeps the same. `crates/plugin-api` (`switchboard-plugin-api`) is everything a plugin and the workspace say to each other, as plain serde types under `PROTOCOL_VERSION`: a plugin's `Manifest`, the `Event`s it is told, the `Action`s it asks with their `Answer`s, `Host` (whoever answers) and `Plugin` (one loaded in process), `sdk`, the few helpers both sides need (`util` and `paths` give them from there), and `release` (its `release` feature), what a release is and how one is checked and put in place, which `src/update` and the diff's own update (`crates/diff/src/update.rs`) both run, so a change to how a release is verified is made there, once. `crates/diff` (`switchboard-diff`) is the diff, the first plugin and an app that runs alone: of the workspace's crates it depends on those two, never on `switchboard`, so the compiler holds the boundary, and it reaches the workspace only through the API (`crates/diff/src/host.rs`), which `src/diff/host.rs` answers from the modules that keep each rule (`settings`, `trust`, `integrations`, `requests`, `notes`). Something new the diff needs of the workspace is a new `Action` answered there, never a dependency on `switchboard` or a second copy of a rule; a type changed so that an older reader would misread it bumps `PROTOCOL_VERSION`, and a field added reads with a default. Each setting the diff reads is in its manifest with the schema's default, label and description, which a test in `src/diff/host.rs` keeps the same, and stays listed in `assets/settings.json`: Settings' rows are drawn from `assets/settings.json` and the diff's own settings view, alone (`crates/diff/src/app/own.rs`, M-m), from the manifest, so a new setting of the diff's is added to both with the same words. One only the workspace has a use for is marked `Scope::Workspace` and left out of that view; one that is the diff alone's (`diff_update_check`) is `Scope::Alone` and in no list of the workspace's. A plugin that runs an existing app (git, an editor, a pager) gives it its settings at launch, by flags or environment, and never edits that app's own config files, as "Other apps' configs" says. `crates/notes` (`switchboard-notes`) is the notes app, a plugin and an app that runs alone by the same rules: it depends on those two crates, never on `switchboard`, and reaches the workspace only through the API (`crates/notes/src/host.rs`), which `src/notes/host.rs` answers from the modules that keep each rule (`settings`, `platform`, `links`, `mux::graphics`, `tabs::title`, `autopilot`, `cmd::worktree_from_note`), handing what Notes shares with the diff on to `src/diff/host.rs`; `src/notes` keeps Notes on the server (`serve`) and gives the app's modules at the paths they had (`notes::store`, `notes::id`, `notes::render`), for the parts that read a note themselves. Alone (`switchboard-notes`, its `host::Alone`), what needs a workspace is left out rather than done another way: no tab's note or tab to go to, no work started on an item, no link opened, no pictures, since which browser a site opens in and how a picture reaches a terminal are rules kept in one place. Alone (the `switchboard-diff` binary, `host::Alone`), the diff answers for the workspace itself: no server, no pull request to take a base from (the default branch, or the branch its own tracks), `claude -p` directly, its own folders (`~/.local/state/switchboard-diff`, `~/.cache/switchboard-diff`), and no notion of whose code a directory holds, which stays `src/trust.rs`'s. Alone it has a header line, a Settings button and a settings view of its own, which writes a settings file of its own, `~/.config/switchboard-diff/settings.json` (`host::write_setting`), since the diff alone knows nothing of Switchboard and reads none of its files, a look for a newer release once a day and `switchboard-diff update`; in the workspace none of those are there (`host::is_alone`), the workspace having its own. Its HTTPS client is its `net` feature, which `switchboard` depends on it without, so the build's only C stays behind the `net` features.
