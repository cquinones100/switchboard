# Trying a change, the demo and upgrades

To see a view without anyone's screen, run `switchboard demo --detached` (made-up data, nothing of the person's linked) or `switchboard try --detached`, and drive it with `switchboard headless` under the prefix it prints: `headless` prints a client's id (attached at `ui::layout::SIDE_BY_SIDE`, the narrowest size at which no view stacks its panes, unless `--size` names another), `headless-keys <id> <key>...` types into the whole workspace (mission control, the sidebar, the boxes), and `headless-screen <id> [--ansi | --png <file>]` reads all of it, which `capture-pane` can't; say before starting one, as for any test here. `switchboard demo --tour <dir>` saves every board that way. To show the person a change as a video, run `/walkthrough` on the demo, which records it from the worktree's build with captions and the keys pressed (its `scripts/record-terminal.js`), in a demo of its own under `/tmp` that needs no go-ahead.

To try a change by hand, use `switchboard try` (`src/cmd/try_.rs`, ported from bin/switchboard-try), which builds the worktree with cargo and runs it under a home of its own, `/tmp/sb-<hash>`, with its own settings, state, server and socket, after the build's own `switchboard setup plugin claude claude-md skills` has laid out its plugin there (the hooks, skills, instructions, statusline and permissions its panes' Claude loads; or, with `claude_plugin` off in the settings it copies, its hooks, statusline, permissions, CLAUDE.md and skills in its own `~/.claude`); its `~/.local/bin/switchboard` is the build, first on its PATH, so Claude Code's hooks in its panes reach the try's server. A Claude in the worktree uses `switchboard try --detached`, which starts the try's server with no client and prints the prefix that reaches it (`<prefix> send-keys`, `<prefix> capture-pane`, `<prefix> list`); `--print` prints the environment for a terminal of your own (`eval "$(switchboard try --print)"`, then `switchboard`); `switchboard try --clean` ends it and removes its home when done. It works because everything finds itself through `~`: a module that reaches for an absolute path of your real home breaks it, and a new state, config or cache location under `~` has to be sorted into what it links, copies or leaves fresh. Its settings turn off what would duplicate your real workspace (`TURNED_OFF`: the Slack look and view, the standup note, banners, the update check, restoring saved tabs, removing landed worktrees, with the todo note and meeting notes starter routines made paused). It isn't sealed off: it links your Keychain, dotfiles (`.ssh`, `.gitconfig`, shell history), the `~/.config` folders Switchboard doesn't configure (gh's sign-in among them), `~/.local/share`, Claude's plugins and sign-in, your own Claude hooks and skills, and the programs in `~/.local/bin` that aren't Switchboard's, so keys sent there act with your real credentials, and anything that would change one of those, push, or reach a service still waits for a go-ahead. It refuses a worktree holding someone else's code (a fork's PR, by `src/trust.rs`'s checks) until its path is in `trusted-dirs`, which is asked about first, and a PR `wtpr --untrusted` checked out always: that runs only with `--sealed` (`src/cmd/try_sealed.rs`), on macOS, under a sandbox that reaches none of what this paragraph says it links, in a home made from nothing. A build run with `SWITCHBOARD_STATE_DIR` set never brings its plugin, skills and settings into your home, as a new build attaching (`setup::refresh`) and its server starting otherwise do (`setup::state_of_its_own`).

A skill, Claude's settings or Switchboard's part of CLAUDE.md changed in the clone a build came from needs no rebuild: the build reads them from the clone (`src/assets.rs`), and its server brings the plugin and the parts set up up to date within 10 seconds of a change there. A running server keeps the binary it started with. A rebuilt `switchboard` reaches new commands and hooks at once, but the server only once it restarts: `switchboard upgrade` restarts it on the binary at the path it started from without ending anything (`src/mux/upgrade.rs`: the server execs the new build in its own process, handing it every pane's terminal, every attached terminal's connection and its socket), while `kill-server` ends every pane's program. A change to the protocol between them (`src/mux/proto.rs`, what `switchboard hook` sends) needs both. What a server hands over is `upgrade::Handover` and the pane's replay (`src/mux/replay.rs`): something new on a pane, a tab or a client that should survive an upgrade goes there, read with a default when it is missing, since the build reading the file is newer than the one that wrote it. A change a newer build couldn't take up from an older one's file bumps `upgrade::VERSION`, which the running server checks before it execs a build (`server --handover-version`), so it refuses that build rather than lose its panes.
