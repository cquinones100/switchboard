# Skills

The skills that ship with Switchboard are in `assets/skills/`, compiled into the binary by `build.rs` (a build from a clone reading the clone's `assets/skills` first, `src/assets.rs`) and written into its plugin's `skills/` (`~/.local/share/switchboard/claude/plugin`, by the server as it starts and `switchboard setup`), where the Claude in its panes finds them as `/switchboard:<name>` (and `/<name>` while nothing else has the name); with Settings' `claude_plugin` off, `switchboard setup skills` writes them into `~/.claude/skills` too, a skill of the person's own by the same name kept. A skill's scripts and shared files are named by their place in the plugin (`~/.local/share/switchboard/claude/plugin/skills/<name>/...`), which is there either way, and its permission in `assets/claude-settings.json`, and in the `allowed-tools` of each skill that runs one, names that path. Code that recognises a skill by its name (a loop's prompt, the Skill tool's input) takes `/switchboard:<name>` too (`plugin::bare`), while what Switchboard types into a tab stays the bare `/<name>`. They call the binary's commands (`switchboard codex-review`, `land-lock`, `wait-deploy`, `watch-note`, `respawn`, `tabs`, `setting`, ...), so a change to a command's flags or output belongs in the skills that use it, and the other way round: `review-loop` reads `codex-review`'s JSON (`tests/it/codex_review.rs`), `queue-and-clean` takes the landing lock through `land-lock` and checks the review's `patchId`, `/wt` and `/wtn` hand a tab over with `switchboard respawn`. `plan-item` (`/plan-item <what>`, and Notes' M-Enter in "Add an item") adds a checklist item to the tab's note and writes its plan note in the plans folder beside it, the shape `/wtn` and autopilot build from (`src/cmd/worktree_from_note.rs`'s `items` and `plan_of`; autopilot takes the repository's GitHub issues too, `src/autopilot/issues.rs`, started by `wtn --issue`), the item's first line its title in under 90 characters, `BUG: ` and what is broken or `FEAT: ` and what to build, since the branch, the worktree and the tab are named from it, and an `After: <first line>` line under it for each open item it builds on, which holds it until that item is ticked, so a change to that shape belongs in both (`tests/it/skill_path.rs`). A skill whose scripts need npm packages keeps them in its own `scripts/package.json`, pinned to exact versions with the lockfile beside it, its `node_modules` ignored, and says to run `npm ci` there when they are missing.

A repository may define its own skill by one of these names, and Claude Code may run Switchboard's over it (a personal skill over a project's, the plugin's when named), so every skill here starts by running `switchboard skill-path <name>`, which prints the repository's copy (the worktree's, then its main clone's), else Switchboard's own (the personal one when Switchboard wrote it or it is a copy of Switchboard's made the person's own, else the plugin's, never a skill of theirs that only shares the name), and follows the repository's when there is one; a skill that hands off to another reads the file `skill-path` prints rather than a fixed path, and, where it needs Switchboard's own text whatever copy is installed (`queue-and-clean` reading `ci-loop`'s "When queue-and-clean runs this"), the text `switchboard skill-path --own <name>` prints. That opening paragraph is worded the same in every skill, and `tests/it/skill_path.rs` checks it and the hand-offs, so a new skill gets it and a new hand-off goes through `skill-path`.

`.claude/skills/` holds Switchboard's own project skills, for working on this repository: Claude Code loads them only in sessions here and in its worktrees, and they aren't in `assets/skills/`, so the binary never carries them, `switchboard setup` never writes them and no user gets them; being the repository's own copy, they don't open with `skill-path`. `review-pr` is one, started as `/review-pr <pr>` or from `M-p`'s "Review a contributor's PR", which `src/cmd/work.rs` lists only in a repository with the skill: it reviews and tries someone else's PR without running its code outside the sealed try (`wtpr --untrusted`, `switchboard pr-risk`, `/review-loop` from outside the worktree, `switchboard try --sealed`) and drafts the review, so a change to those commands' flags or output belongs in it too. `design-docs` is another, started as `/design-docs`: it holds each board's source in `docs/design/src/` (a `<Name>.dc.html` each and `canvas.json`, copied once from the UX 2.0 canvas, a claude.ai Design artifact now kept as an archive) to the design's made-up names, writes each board as a static HTML page in `docs/design/` with its own `scripts/render.js`, which GitHub Pages serves from main's `/docs` at https://cquinones100.github.io/switchboard/design/ (leaving the sources out, `docs/_config.yml`), rewrites `docs/design/README.md`, and pushes it to main with `render.js push` (below, "Pushing"); those pages are its output, never edited by hand, and a board changes in its source. `push-unreviewed` is a third, started as `/push-unreviewed` and only by you, for a push past the review rule ("Pushing", below).
