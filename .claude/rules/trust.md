# Trusted directories and someone else's PR

**Trusted directories.** Nothing here runs code that another repository supplies unless you have trusted that repository. Trusted directories are listed in `~/.config/switchboard/trusted-dirs`, one absolute or `~/` path per line (blank lines and lines starting with `#` ignored), which is yours, never committed, and never written for you; a missing file trusts nothing. A directory counts only when its real path equals a listed one's exactly, so trusting `~/code` doesn't trust what is under it. `switchboard try` and `switchboard apply install` (for `~/switchboard` too) check it before building a worktree whose code isn't yours, `wt` and `wtb` before starting Claude on a branch with someone else's commits beyond the default branch (`trust::branch_yours_or_listed`, or `--trusted`), and `switchboard apply-actions` before offering to run a landed repository's install or migrate script, naming them for you to run in a clone not listed; anything new that would execute something from a repository checks this file the same way. `src/trust.rs` is the one place that decides whose code a directory holds (`listed`, `yours_or_listed`, `branch_yours_or_listed`, `is_untrusted`, `trusted`); nothing keeps a notion of its own.

**Someone else's PR.** `wtpr` opens a fork's PR, and a same-repository PR with a commit beyond the default branch someone else wrote, a stacked PR's base included (`trust::others_on`), untrusted by default (`--untrusted` for any, `--trusted` to opt out): a worktree in `~/.cache/switchboard/pr-review/<owner>-<repo>/<n>`, on `pr-review/<n>` from the commits GitHub keeps for it, no remote added, with git's hooks, every filter your config names, the file-system monitor and submodule recursion off in its own worktree config, nothing linked and no Claude started. Such a worktree (in that folder, or marked `switchboard.untrusted` in its own worktree config, which no file in it can change) has its `CLAUDE.md`, `.claude/settings.json`, hooks and skills from its author, so anything that starts Claude in a worktree or lists worktrees to reopen leaves one alone (`trust::is_untrusted`, or on the server's task `trust::in_review_dir`, which reads the path alone): `claude-here`, `worktree-resume`, `worktree-from-branch`, `M-t`, `wt-revive`, Reopen's worktrees and the Slack relay's places do, and a new one does the same. `skill-path` passes over its skills, so no PR can rewrite the review loop that reviews it, and a listing in `trusted-dirs` doesn't make it trusted (`trust::trusted`). `switchboard pr-risk` reads what it changes that runs without being asked from git alone, with no hook, textconv, external diff or file-system monitor, so a git command run on its worktree for a review passes `--text --no-textconv --no-ext-diff` the same way; `codex-review -C <worktree> --pr <n>` reviews it from the main clone, and `/review-loop` given its path does so reporting only. `M-p`'s "Review a contributor's PR" checks it out before opening its tab, whose Claude runs from the main clone while the tab follows the worktree through its `@tab_dir` option (`Server::pane_dir`, which names the tab and points the views and the diff there, never where a program starts, `pane_own_dir`), and lazygit is refused in it; the diff passes `--text` there. Its code runs only in `switchboard try --sealed`, every process of the try (the build with its `build.rs` and proc macros, the server and what it starts, every client) under macOS's `sandbox-exec`; the rules are `src/platform/sandbox.rs`'s, written into `~/.cache/switchboard/sealed/` on each run, where nothing in the try can change them, so a new place the try must read or write goes there, never a rule that opens your home. Nothing outside the sandbox writes in a sealed home once any of its code has run, its crates are fetched outside it only from crates.io with their checksums (a dependency may have a path only to another package of the same workspace, a folder inside the worktree by its real path, as Switchboard's own crates are, `try_sealed::packages_problem`), from a folder outside your home with no rustc wrapper, so none of your cargo config applies (the build inside sets no wrapper either), and Linux, with no sandbox but one to install, has no sealed try.
