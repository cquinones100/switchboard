# Switchboard

Switchboard, called editor-configs until October 2026, is a terminal workspace for working with coding agents, shipped as an opinionated distribution: the dotfiles for the tools listed by directory, and the scripts that tie them together. Everything runs from `~/switchboard`. A clone set up under the old name keeps working: `setup.sh`'s `renamed` links `~/switchboard` to a clone at `~/editor-configs` and moves `~/.config/editor-configs` and `~/.local/state/editor-configs` to their new names, and `repo-update.sh` and `settings.sh` fall back to `~/editor-configs` until it has. Keep that until no clone needs it.

The dotfiles are for the tools listed by directory. `setup.sh` is the one script that puts them in place, and running it again changes only what isn't in place yet: `./setup.sh <part>` (`tmux`, `bin`, `claude`, `git`, …, or one script in `bin/` by name) does just those parts without questions, and `./setup.sh` alone runs the guided setup below. Every link goes through its `put_link`, which leaves a link already pointing at the right file alone and moves a real file or directory in the way to `<name>.bak.<time>` rather than overwriting or deleting it; every other step checks first in the same way, and each part says what it changed or that it was up to date. `--check` with either says what would change and changes nothing. A new step must be just as safe to run twice (`test/setup.test.js` runs the parts twice). `sync.sh`, which it replaced, only runs it, for clones and habits from before. In a clone where `setup.sh git` has set `core.hooksPath`, `.githooks/post-merge` (and `post-rewrite`, after `git pull --rebase`) runs the parts that ask nothing after every pull, `tmux`, `bin` and `git`, `skills` where any of Switchboard's skills is linked, and `claude` where all of `claude/` is linked, then prints the guided setup's "Left to do" list from `--check`, and nothing when all is in place. The guided setup ends with that list too, every ✗ again, so none has to be found among the ticks. `tmux` links every `.sh`, `.zsh` and `.js` in `tmux/` into `~/.config/tmux`, so a new script there needs no line of its own.

The guided setup sets up the tmux workspace on someone else's Mac (see `bin/README.md`): it checks what the workspace needs, installs what is missing with Homebrew after asking, links tmux, Neovim, lazygit and `bin/` (asking the first time, since it moves their configs aside), adds the worktree shell functions (`wt`, `wtpr`, `wtr`, `wtb`, `wtn`) to `~/.zshrc` from each script's `init zsh`, and reports the optional parts. A new tool the tmux scripts or the configs call belongs in its `PACKAGES` (with `command_of` when its command isn't its name), and anything only one feature needs in its optional checks, named for what it unlocks, so a fresh install never finds out by something breaking. Its `terminal` part makes Option act as Alt, which every `M-` key needs, where it can: a `config-file` line reading `ghostty/required` in a Ghostty config of your own (Switchboard's own sets it), and the default profile of Terminal or iTerm2, through `defaults export` and `import` so macOS's own preferences take the change; for another terminal it says what to add (`terminal_hint`), and tmux.conf binds the characters Option+h/j/k/l type without it (`˙ ∆ ˚ ¬`) to pass through and show the `option-alt` tip once. Downloads it makes are pinned and checked, as the font is (`FONT_COMMIT`, `font_sha256`) and nvm (`NVM_VERSION`). The Claude Code and git setup are optional and asked for: by default it adds only the hooks that run `agent-state.sh` to the person's own `~/.claude/settings.json`, since the rest of `claude/` holds this machine's own settings, offers the skills that ship with Switchboard (`setup.sh skills`, a link per skill in `~/.claude/skills`, keeping a skill of the person's own by the same name rather than moving it aside, and a new one linked without asking once any is), and links all of `claude/` (`setup.sh claude`) or sets this clone's git hooks (`setup.sh git`) only when they say yes. Once they have, later runs bring in what was added to those parts without asking.

`README.md` at the root is the front page for someone new: what the workspace is, the requirements, the one-line install (`install.sh`, which clones `main` into `~/switchboard`, the branch the update popup follows, and runs the guided `setup.sh` with the terminal as its input, since a pipe is the script's) or the two commands it stands for, the first keys and where things are, pointing to `bin/README.md` for the full detail. Keep its keys, requirements and setup steps in step with `setup.sh` and `tmux.conf`.

The global `~/.gitconfig` isn't kept here: it holds a machine's git identity and paths, which don't belong in a public repo. `./setup.sh git` only sets this clone's `core.hooksPath`.

Nothing here runs code that another repository supplies unless you have trusted that repository. Trusted directories are listed in `~/.config/switchboard/trusted-dirs`, one absolute or `~/` path per line (blank lines and lines starting with `#` ignored), which is yours, never committed, and never written for you; a missing file trusts nothing. A directory counts only when its real path equals a listed one's exactly, so trusting `~/code` doesn't trust what is under it. Nothing needs it today, since the workspace layout that ran a directory's own `worktree` script is gone. Any new script that would execute something from a repository checks this file the same way, inline.

## Trying a worktree

Your `~/switchboard`, and every link `setup.sh` made from it, is your main clone, so a worktree's changes can't be tried in your own tmux. `bin/switchboard-try` tries them under a home of its own, `/tmp/sb-<hash>`, whose `~/switchboard` is the worktree, laid out by the worktree's `setup.sh`, with a tmux server whose socket is in that home (`TMUX_TMPDIR`), opened in a new Ghostty window. It works because everything here finds itself through `~`: a script that reaches for an absolute path of your real home, or a tmux call that names the default socket, breaks it, and a new state, config or cache location under `~` has to be sorted into what it links, copies or leaves fresh. Its settings turn off what would duplicate your real workspace (the Slack look and view, meeting, standup and todo notes, banners, the update check, restoring saved tabs). Claude Code finds its login only with `~/Library/Keychains` linked in.

## The user layer

Every file of someone's own lives in `~/.config/switchboard/`, never in a directory of a tool's own under `~/.config`: `setup.sh`'s `config` part (run by `tmux` too) moves the ones that used to be elsewhere, and each setting in them has a row in mission control's Settings view, from `OWN_FILES` in `lib/sidebar/own-config.js`, so a new setting in a file there, or a new file, gets an entry there too.

Someone's own settings live in `~/.config/switchboard/`, never in this repository, and each tool reads them after this repo's own config, so they win and an update never touches them: `tmux.conf` (`source-file -q` at the end of `tmux/tmux.conf`, inside the `@conf_check` guard), `nvim.lua` (`dofile` at the end of `nvim/init.lua`), `ghostty` (an optional `config-file` last in `ghostty/config`) and `lazygit.yml` (tmux sets `LG_CONFIG_FILE` to lazygit's config and then it, when it is there, so panes tmux starts read both). A new tool's config gets the same: its own file there, read last, and a row in `README.md`'s "Making it yours".

## Testing in the tmux in use

The tmux server Switchboard runs in is the one being worked in. Before testing anything there, opening or closing a window, moving focus, sending keys, restarting the sidebar daemon to watch it, stop and say that the test needs the session and what it will do, and wait for a go-ahead, since the person may be typing in it. Test in the tests' throwaway server (a socket under `/tmp`, as `test/tmux-sidebar.test.js` sets up) where that can show the same thing. In a worktree, try anything the tests can't show (keys, popups, the sidebar, setup itself) in `switchboard-try --detached`'s server rather than asking for the real one, unless the worktree holds someone else's code (a fork's PR), which it refuses until its path is in `trusted-dirs`, and which is asked about first, but it isn't sealed off: it links your Keychain, dotfiles (`.ssh`, `.gitconfig`, shell history), the `~/.config` folders Switchboard doesn't configure (gh's sign-in among them), `~/.local/share` (Neovim's plugins), Claude's plugins, your own Claude hooks and skills, your sidebar plugins (which its daemon runs) and the programs in `~/.local/bin` that aren't Switchboard's, so keys sent there act with your real credentials, and anything that would change one of those, push, or reach a service still waits for a go-ahead. It starts the worktree's whole workspace with no client and prints the `tmux` prefix that reaches it, for `send-keys` and `capture-pane -p`; `switchboard-try --clean` stops it when done. Every tmux call it makes names its own socket with `-S`, since inside your tmux `$TMUX` points a bare call at your real server, and `--clean` once killed it that way. A try server left running also stops tmux-continuum restoring your tabs when your own server next starts, since it counts every tmux server.

## Pushing

Always ask before pushing this repo, every time, whatever the branch and
whatever an earlier push was allowed. Review each commit as it is made:
run `/review-loop` on it before starting the next, folding the round's fixes
into that commit while it is unpushed, so each commit carries its own
review rather than a pile of commits getting one loop and a batch of fixes
at the end; working through a list, push each once it is clean, before the
next. Before asking, run `/review-loop` on
the unpushed commits, unless Settings' "Review before pushing"
(`review_before_push`) is off, which the hook then follows too: `.githooks/pre-push` refuses a push to main whose tip
isn't the commit the skill last found clean, or whose review started past
where main is on the remote (both recorded in the clone's
`review-loop-clean`, `git rev-parse --git-path review-loop-clean`, from
`codex-review`'s `reviewedCommit` and `mergeBase`), so a fix made after the
review needs a review of its own, and so does a commit the review left out. The skill offers to squash the loop's own commits before the push; a squash that leaves the tree exactly as reviewed records its new commit in their place, with the same base, and one that changes it records nothing. Claude can't skip
it: this repository's own `.claude/settings.json` runs
`claude/hooks/enforce-push-review.sh` before every command in it, which
refuses `git push --no-verify`, and `enforce-git-hooks-run.sh`, which refuses
changing `core.hooksPath`, so it applies to any Claude working here and
nowhere else. The repo is public, so before asking,
check the unpushed commits for anything that identifies the user or their
employer: organization or company names, ticket IDs, PR numbers, internal
hosts, usernames, personal paths, tokens.

A review loop here spends its rounds on what someone would hit in normal use. Start its notes file with this standing line, so the reviewer rates such findings low: `- Known gap: findings that need an unusual case (two events within the same moment, a terminal of unusual size or one resized mid-action, a name holding control characters or odd Unicode, permissions changed underneath, a signal sent by hand) are low here unless normal use hits them (the user's rule for this repository)`. Triage the same way: a medium of that kind is treated as low, so it is neither asked about nor fixed, outside a confirmation round as in it, and goes in the final report with the other lows. A fix that only closes one of them is not worth the round the reviewer then spends on the new code.

## Committing

Commit straight to `main`: there is no PR flow here, so a branch only adds a
merge step. Each change gets a commit of its own, and nothing pushed is amended
or reordered, since that rewrites public history and needs a force-push.

Asked to squash unpushed commits, make one commit per feature, its message a
description of the feature as it now stands, in prose, and keep other features'
commits apart. Check the squashed commits' added lines and the new message for
identifying details, as before a push (a real PR number in a test becomes
12345). Branch a `backup/pre-<what>` first, rebase with `--autostash`, and after
the rebase check that the tree equals the backup's and that the tests pass at
every rewritten commit, run in a temporary worktree.

## Claude Code settings

- `~/.claude/CLAUDE.md` is written by `setup.sh`'s `claude_md`: a short file importing (`@path`) the person's own rules, from a git repository (its `file`, else the CLAUDE.md nested least deep, more than one at that depth or none an error that says so; on GitHub or a gist, its clone can sign in through gh, a credential helper added after its own) or a file named in `~/.config/switchboard/claude.json` or else `~/.config/switchboard/CLAUDE.md`, and Switchboard's part, `claude/switchboard.md` (the tabs, the notes app, repository skills). With no rules named, a CLAUDE.md of their own gets only the import of Switchboard's part. A link into this repo's `claude/CLAUDE.md`, which once held its owner's rules and is gone, is turned into `~/.config/switchboard/CLAUDE.md`, copied from what it linked to or from git history, so a clone set up before keeps its rules; keep that until no clone needs it. No one's own rules live in this repository: what every user's Claude needs to know about the workspace goes in `claude/switchboard.md`.

- `claude/switchboard-settings.json` is Switchboard's part of Claude Code's settings: the hooks that run `agent-state.sh`, the statusline, and the permissions its skills and loops need to run unattended (their scripts, `codex-review`, `slack-relay notify`, the tab-naming tmux calls, read-only git and gh, and the read-only Slack, Calendar and Linear connector tools); anything that writes outside the machine is left to ask. `setup.sh`'s `claude_settings` merges it into the person's own `~/.claude/settings.json`, which is never a link and stays theirs (Claude Code writes `/model` and "always allow" there): its hooks replace any hook running the same command, its statusline replaces none or Switchboard's own, its permissions are added to theirs, and a copy of the old file is left beside it, so a second run changes nothing (`test/setup.test.js`). Claude Code has no settings file read after the user's, so that file is the user layer for Claude. A permission or hook taken out of `switchboard-settings.json` is not taken out of anyone's file.
- `claude/settings.json` is this machine's own settings from before, which the whole setup used to link to `~/.claude/settings.json`; `claude_settings` turns that link into a file of the person's own with what it held. It stays here until no clone links to it (roadmap: moving the owner's layer out of the repo).
- Claude Code reads only four settings files: `~/.claude/settings.json`, the project's `.claude/settings.json` and `.claude/settings.local.json`, and managed settings. There is no user-level `settings.local.json`.
- Anything that describes a specific organization's environment must not live in the tracked file. The auto mode environment profile (the `autoMode` key) belongs in that project's `.claude/settings.local.json`, which is gitignored there. If Claude Code writes `autoMode` back into `claude/settings.json`, move it again before committing. `.githooks/pre-commit` refuses a commit that stages `autoMode` in that file, or any change to its `model`, which Claude Code rewrites whenever `/model` is used; commit the rest of the file with `git add -p`. The hook only runs where `./setup.sh git` has pointed this clone's `core.hooksPath` at `.githooks`, so run that on every new machine. Claude itself can't get around it: `claude/hooks/enforce-git-hooks-run.sh` blocks `git commit --no-verify` (and `-n`) and any change to `core.hooksPath`. The worktree scripts in `bin/` symlink the project-local file into each worktree so it applies there too.

## Neovim plugins

Neovim's colors are Ghostty's: `nvim/colors/ghostty.lua` reads the theme Ghostty uses now (the one `tmux/theme.sh` last wrote to `~/.config/ghostty/theme-mode.conf`, else Ghostty's config) from its theme file and lays it out as a base16 scheme with mini.base16, its background left transparent so tmux's dimming of inactive panes shows, and every Neovim applies it again when `theme.sh` switches Ghostty between dark and light. diffview's lines are git's green and red whatever the theme, mixed over Ghostty's background, the words that changed (`inline:word`) in a stronger shade, and a file opens with the cursor on its first changed word (`to_first_change`), since a paragraph of Markdown is one line and the lines around a change can hide it.

`nvim/lazy-lock.json` is committed, so a new machine gets the same plugin commits (`:Lazy restore`), and `nvim/init.lua` clones lazy.nvim itself at the commit the lockfile records, not its `stable` branch; when lazy.nvim updates itself, bump that commit with the lockfile. The language servers Mason installs (`nvim/lua/plugins/lsp.lua`) are left unpinned, at whatever npm and PyPI hold: pinning them would mean chasing every release for little gain.

`M-d` runs diffview in a Neovim of its own, `nvim -u ~/.config/nvim/diff.lua --noplugin`: only diffview, mini.base16 (for the colorscheme) and the icons, taken from lazy.nvim's directory and set up by calling their specs' `config` in `lua/plugins/`, so it starts in about a second with no language servers, Copilot or gitsigns. lazy.nvim must have installed them first, from a normal `nvim`. A plugin diffview comes to depend on goes in `diff.lua`'s list.

diffview opens on the first file that isn't generated (`generated()` in `nvim/lua/plugins/diffview.lua`: lockfiles, migration snapshots, minified and built output), and shows an added file, or a deleted one as it was, alone in a single pane rather than beside an empty half. A new kind of generated file goes in that list. Its files are a flat list in reading order (`reading_order`), every list diffview is given sorted first so its updates find nothing moved: documentation (`DOCS`), then database changes (`DATABASE`: migrations, SQL, schema files), then the server's side of a web app (`SERVER`: Next.js server actions in `_actions/` or an `actions.ts`, API routes, `*.server.ts`, `server/`), then the rest of the implementation, then tests (`TESTS`), then generated files, Haiku ordering the implementation from most abstract to most concrete in the background (`ask_order`, `claude -p` with no tools, found in `~/.local/bin` by `claude_command` when the PATH tmux gives Neovim lacks it, as `ask_story` finds it too), its answer cached in Neovim's cache under `diff-order/`. The `diff_order` setting turns it off, back to the folder tree. With the `diff_story` setting on (the default), and no merge conflict unresolved, the order is told as a story instead (`ask_story`, `nvim/lua/diffstory.lua`): Haiku reads the whole diff (up to `TOTAL_CHARS`, files that fit kept whole and the rest sharing what is left, a cut file keeping every hunk's header) and the commits' messages (`git log` from the left side, trailers left out, `diffstory.commits`), and groups the hunks, each labelled with its id, into a few chapters from the change's core to its edges, tests beside their code, a file in the chapter holding most of its changed lines and on the page of every chapter it has a hunk in (`touches`), each headed in the list by its number, title and a why of two or three sentences from the commit messages (its first sentence alone in a list narrower than `SHORT_WHY`, the whole in the diff's bar), each hunk worth it carrying a note over it in the diff (`draw_notes`, `diff_story_notes` setting), a hunk of another chapter named so and, on a page, dimmed; `yS` copies the story as Markdown (`diffstory.markdown`), as M-p's "Copy the diff's story" does by pressing it (extmark virtual lines over its first file in each section of the list it is in, since a working tree's unstaged and staged changes are sorted apart, drawn again after every redraw of diffview's list, which is otherwise left as it is), named in the right side's bar, `]c` and `[c` moving between the headings as drawn (`diffstory.starts` and `jump`); `]p` and `[p` opening the chapters a page at a time, each a diffview of its own on the same revisions limited to its files, `[p` from the first back to the whole diff, a page told the whole diff's story rather than asking Haiku again (`turn_page`, `view.page`, `diff_story_pages` setting, Vim's own keys with it off or no story told); a spinner and "telling the story" on a line under the list's first while Haiku reads the change, and the whole diff under a cover saying so (`cover`, after 300ms, so a story already known opens at once; Esc shows the diff now) until the story is known or can't be (`settle`), the cover showing what Haiku reads, the time taken and each chapter as Haiku names it, from its answer streamed (`stream-json`, `diffstory.partial` and `progress`), `t` there showing the answer itself so far (`diff_story_progress` setting, a spinner alone with it off); the answer so far kept beside the story's cache file as `<key>.partial` while it is asked for, rewritten at least every two seconds, so another Neovim asked for the same story (M-d while it is told ahead, or the other way round) follows that ask, its progress on its own cover, rather than asking again, and asks only once the file is gone or 30 seconds old with no story kept; told ahead of time for each tab's new commit by `tmux/diff-story-ahead.sh`, a headless Neovim opening the same diff M-d would (`g:diff_ahead`, quitting once settled), which the sidebar daemon runs one branch at a time when a tab's branch has a commit not yet told (`lib/sidebar/story-ahead.js`, read from git's files, a commit told only once its story is and a failed one tried again after half an hour, `diff_story_ahead` setting), M-d's base from `tmux/diff-base.sh`, which both share so both tell the same story; generated files last whatever it says; its answer cached in Neovim's cache under `diff-story/`, keyed by the diff, the commits' messages and `diffstory.VERSION` (`diffstory.key`), so a new prompt tells every story again, and the kinds' order when it can't answer (`test/diff-story.test.js`). Since the list has no folders, the diff's right side carries the file's path from the repository root in its winbar, the left's too only for a renamed file. The view is kept quiet: no help line or icons in the list, its heading, path and counts faint, no lines between windows and nothing drawn past a buffer's end. In the file tree or history, `J` and `K` scroll the diff beside it without leaving the tree, and the file list opens wide enough for its longest path, at most half the screen, once its files are known (`fit_width`, `set_width`, the whole diff only, a page keeping its width, `diff_list_wide` setting), `E` narrowing it and widening it again (`widen_list`, diffview's own `file_panel.win_config.width`, which it reads whenever it lays a list out). In it, `yp` copies the cursor's `path:line` and `yl` a GitHub link to that line at the side's commit (a range in visual mode), taken from diffview's own file and rev, since its buffers are named `diffview:///…`.

## Window names and accent colors

`tmux/accent-color.sh` produces two different strings from the same directory.
The color key is hashed into the accent color, and `claude/statusline-command.sh`
builds the same key independently, so changing its shape in one place silently
gives tmux and the Claude statusline two different colors for one project. The window name is
only ever read, so it is free to change.

`tmux/window-names.sh` owns the tab: the label from `tmux/tab-label.sh`, whole,
prefixed with `#<number>` when the branch has a pull request.
`wt-jump` reads that prefix back to find PRs, so it stays at the front. `rename-window` expands formats in the name it is given, so `window-names.sh` doubles every `#` in the name it sets (`##12` for the PR prefix, which tmux stores as `#12`); anything else that renames a window from a title, branch or directory must do the same. `@tab_label`, set with `setw`, is stored as given. The
label is the name set with "Rename the tab" in `M-p` (the window's `@tab_name`), else the Linear
ticket and its title when the branch names one Linear confirms, else
`accent-color.sh --name`. The same name, PR prefix included, goes in
the window's `@tab_label` with its `#` as they are, which `bin/slack-relay` shows in Slack. The second status line (off by default, the `second_status` setting), `tmux/tab-status.sh`, starts
with the same label, so any change to what a window is called belongs in
`tab-label.sh` and reaches both.

A tab is named from its active pane's directory, skipping the sidebar and the notes pane `M-e` moves beside your work (which runs in your home directory), so typing in the notes doesn't rename the tab; the notes pane names only a tab that has no other pane. `window-names.sh` keeps the directory each name came from in the window's `@tab_path`, and at the end of a Claude turn `agent-state.sh` names the tabs again (one tmux format check, then `run-shell -b`) when the pane is no longer there, since a command can take the pane's terminal somewhere else between focus changes.

All of this runs on every pane focus, for every window in the session, or on
every status redraw, so none of it may wait on the network.
`tmux/window-pr.sh` and `tmux/ticket-title.sh` answer from a cache and refresh
it in the background, then rename the tabs when the answer changes, so a PR
number or ticket title that was not known yet appears a second later rather
than delaying the focus. Anything else that wants to add to the tab belongs in
`window-names.sh` under the same rule.

It must not start many processes either. A security agent on this Mac inspects
every process that starts, and the status line and focus hook used to start
dozens per window, which made tmux sluggish. `tmux/path-facts.sh` therefore
answers a directory's color, ticket label and PR from a cache that holds only
while the branch stays the same (ten minutes once there is a PR, one minute
before), and `window-pr.sh` and `ticket-title.sh` clear that cache when they
learn something new. `tab-status.sh` keeps a Claude pane's session name and
prompt the same way, until the session file or prompt history changes. Anything that
depends only on the directory and its branch belongs there, and should be read
from there.

## Claude session state in tmux

`tmux/agent-state.sh` records what each Claude session in tmux is doing, from
Claude Code's hooks in `claude/settings.json`: `UserPromptSubmit`,
`PostToolUse`, and `PostToolUseFailure` mark the pane working,
`PermissionRequest` and the question kinds of `Notification` mark it waiting,
`Stop` marks it done, and `SessionStart` and `SessionEnd` clear it. `PreCompact` marks it working ("compacting context"), and the `SessionStart` a compaction restarts the session with (`source` `compact`) leaves the state and loop alone, since it is the same session going on; `PostCompact` hands an automatic compaction's tab back as it was before (`@agent_compact_from`): working in the middle of a turn, done or idle, with its old `@agent_since`, when Claude Code compacted while idle; it clears it after a `/compact` you typed, which nothing follows. The
`Notification` hook also sends the macOS banner, titled with the tmux window.
The state lives on the pane (`@agent_state`, `@agent_since`) and is rolled up
into the window's `@agent`, most urgent first (waiting, done, working), which
the `@agent_marker` format in `tmux.conf` shows in the tab. From the same hooks' JSON
the pane also carries `@agent_activity`, the tool call in a few words, set by
a `PreToolUse` hook as each tool starts, and `@agent_wait`, what a permission
request or an `AskUserQuestion` waits on (a question is a wait from the moment
it is asked); and `@agent_loop`, the loop the session runs (review, ci, queue or deploy) from the
moment `/review-loop`, `/ci-loop`, `/queue-and-clean`, `/deploy-test` or `/preview-test` is asked for, typed
or through the Skill tool, until a new prompt or session. The sidebar shows
all three. One `jq` reads them, as the relay's event already does. No hook
fires when a background task ends, so the sidebar still counts running tasks
from the transcript. Nor does one when an API error cuts a turn short ("API Error: Connection lost mid-response"), which Claude Code records as a message of its own (`isApiErrorMessage`), so the sidebar reads that from the transcript too (`backgroundWork`'s `apiError`) and shows the tab waiting on the error until the conversation goes on. Every
window-status format in `tmux.conf`, `theme.sh`, `update-colors.sh`, and
`window-names.sh` expands that marker, so a new one has to as well.

A conversation moved into the background keeps running in a job with no tmux
of its own, so its hooks have no `TMUX_PANE`. The tab it came from holds a
parked Claude whose session file names the job (`parkedJobId`, matching the
job's `jobId` in `~/.claude/sessions/`), and `agent-state.sh` follows that
link to mark the tab, so a backgrounded conversation still shows as working,
waiting or done there rather than idle.

A headless Claude (`entrypoint` `sdk-cli` in its session file), such as one a
review loop's script starts, inherits the tab's `TMUX_PANE` and names its pane
in its session file too. `agent-state.sh` ignores its hooks, and the sidebar
reads the tab's own interactive session for the pane, so a tab running a loop
shows the loop's background work rather than the helper's turns.

A tab holds one Claude: the sidebar, mission control, the Slack relay, `M-c` and `M-m` each take a tab's Claude to be one pane, so a session starting in a tab that already runs one is moved to a tab of its own as it starts (`tmux/one-claude.sh`, run in the background by `agent-state.sh` on `SessionStart`, saying so in a box; `one_claude_per_tab` setting). Whether a pane runs Claude is decided in `tmux/claude-pane.sh`, which
`agent-state.sh` and `tab-status.sh` source, and again in
`lib/slack-relay/tabs.js`, so a change to one belongs in the other. tmux names
a pane after its foreground program: Claude Code's executable is named after
its version, but Claude started by `claude-here` runs as a Node script's child
and the pane reads `node`. A pane counts as Claude when a foreground process on
its terminal has a session file in `~/.claude/sessions/`.

"done" means finished and not yet seen: the pane-focus-in hook clears it once
the tab is still in front a second later, so passing over a tab, as moving the
sidebar's cursor does, leaves it, and a session that finishes in the tab you
are looking at never gets it. A pane that
is no longer running Claude loses its state on the next focus, so a session
that died without `SessionEnd` leaves nothing behind. Pressed from a sidebar, `M-a` and `M-1`…`M-9` leave the cursor in the new tab's sidebar (`sidebar.sh refocus`), as the sidebar's own number keys do. `M-a` walks the sidebar's
Needs you in its order (pinned, then waiting, then done, then the notifications while there are any, opened as `sidebar.sh notices` opens them, `needs_notices` setting), from a finished tab
going to a pinned or waiting one first, from the list the
sidebar daemon writes to `~/.local/state/tmux-sidebar/needs` (each tab's window, Claude pane, session and why it needs you) whenever it
changes, since only the daemon knows a tab that looks done is still looping
or working in the background; without the daemon it falls back to the panes'
own states. `agent-state.sh` runs before every tool call of every Claude
session, so a syntax error in it blocks them all, the fix included: check a
change with `bash -n` on a copy before it replaces the file. `wt-jump` and the
second status line show the same state.

Claude Code waits on these hooks, so the script only makes tmux calls: no
network, and no output, since Claude Code adds `UserPromptSubmit` and
`SessionStart` output to the conversation. Outside tmux it does only one thing:
while `bin/slack-relay` runs, the prompt-submit, turn-end and waiting hooks
append an event naming the session's transcript (and, for a prompt, its text) to `~/.local/state/slack-relay/events.jsonl`,
which the relay creates and removes only when stopped on purpose, so a crashed
relay picks up where it left off. That is how the relay knows a request
it typed into a tab has been answered, even by a session outside tmux.

## The sidebar and mission control

`bin/tmux-sidebar` (code in `lib/sidebar/`) is one daemon that draws a sidebar
pane on the left of every window, reached with `M-s` from any pane or `C-w h`
from the one beside it, and the mission control popup (`M-Space`). Every sidebar pane and the popup run `tmux/sidebar-pane.zsh`, which
uses only zsh builtins so a sidebar starts no processes however long it runs;
keep it that way. The daemon reads tmux in one `list-panes` per refresh and
`~/.claude` as files, so its drawing path starts no process and never waits on
the network either; only plugins (`lib/sidebar/plugins.js`) may, and they run
off it. It refreshes when something appends to
`~/.local/state/tmux-sidebar/nudge`: `agent-state.sh` and `window-names.sh` do
with a shell builtin, and anything else that changes what a tab shows should
too.

It shows what the tab bar shows, from the same places: the label from
`@tab_label` (PR prefix included) and the accent color parsed out of the
`window-status-format` `window-names.sh` sets, so a change to either shape
belongs in `lib/sidebar/model.js` too. States are `@agent`, `@agent_state`
and `@agent_since` from `agent-state.sh`. It finds a pane's Claude session from
the `tmux` field (`main:@27.%28`) in `~/.claude/sessions/<pid>.json`, not from
`claude-pane.sh`.

Moving a sidebar's cursor onto its notifications (or clicking one) brings the session's Notifications window to the front, as moving onto a tab does (`noticesWindow`): a window marked `@notices_window`, made the first time it is wanted, which `state.tabs` leaves out, `window-names.sh` leaves alone and the tab bar shows only while it is in front, holding a `notices` client (`sidebar-pane.zsh notices`, by its pane, so it reconnects) that lists them whole (`noticeItems`, `noticeListLines`) with the session's `noticeCursor`, and, as every window, a sidebar. Enter there opens the chosen one's menu over it (`noticeChoices`, the views' own `itemChoices` and `boardChoices`); Esc goes back to the tab it came from (`noticeFrom`); `notice_list` setting.

Sidebar panes carry the `@sidebar` pane option. Anything that walks every pane
to find a worktree, a Claude session or a pane to type into skips them, as
`wt-jump` does. A binding that acts on the current pane starts with
`leave-sidebar` (a command alias in `tmux.conf`), so it acts on your pane
rather than the sidebar when the sidebar has focus. tmux-resurrect restores
sidebars as shells titled `tmux-sidebar`, and the daemon gives them their
client back; its restore hooks set `@sidebar_hold` so nothing is added while
it lays windows out.

Its lookups of GitHub, Linear and the calendar feed pause while you're away (no tmux client, or the Mac idle `AWAY_MS` or locked, checked once a minute) and all run on return (`pause_when_away` setting); the standup and meeting notes don't. Anything that has just asked GitHub about a PR appends to `github` in the state directory, as `M-m`'s `pr-ready.sh` does, and the daemon asks again for the PRs, CI, Merge queues (`lib/sidebar/queues.js`, every PR in the queues of the tabs' repositories, `view_merge_queues` setting) and Work map views, at most every 15 seconds. The PR board asks for merged PRs only every `MERGED_EVERY_MS`.

A reminder (`tmux/remind.sh`, `M-p`'s "Remind me about this tab") is the window's `@remind_at` (seconds) and `@remind_note`: still to come, `reminderLater` puts the tab in the Reminders group and stage with the time left; come due, `reminderDue` puts it in Needs you with the pinned ones, `writeNeeds` gives `reminder` as why, the daemon says so once (`announceReminders`), and `agent-state.sh seen` clears it once you are at the tab (`reminders` setting). tmux-resurrect saves no window options, so `tmux/window-options.sh` keeps a reminder and a tab's note (`@tab_note`, `@tab_note_last`, `@tab_note_asked`, `@tab_note_arrived`) across a restart: after each save it writes the windows holding one to `window-options.tsv` in resurrect's directory, under the name of the save `last` points at, and after a restore it sets them again on the window at the same session and index, only from the file written for that save; another window option to carry over goes in its `OPTIONS`. A tab whose open PR has a failing check, from `prs.js`'s per-minute query of every tab's PR (`tab.checks`), is a kind of tab of its own: `buildFailing` in `model.js` puts it in the Build failing group and stage, after Needs you and before everything else but the merge queue, Merged and Testing Deploy (in mission control a tab in `/ci-loop` keeps that stage), and an idle one wears the `failing` badge (`build_failing` setting).

Plugins load only when named in `~/.config/switchboard/sidebar.json`, from
`~/.config/switchboard/sidebar-plugins/` (yours) or `lib/sidebar/plugins/`. Its tests,
`test/tmux-sidebar.test.js`, run against a throwaway tmux server and a
temporary HOME under `/tmp`, since a Unix socket's path can't be over 104 bytes
on macOS. Document it in `bin/README.md`.
`lib/sidebar/text.js`'s `width` must count what a terminal draws as two columns as two (wide characters, emoji-presentation symbols, a symbol followed by U+FE0F); one counted short shifts every border after it on a mission control line.

## tmux plugins

The plugins are pinned in `tmux/plugins.txt`. `./setup.sh tmux` installs each
into `~/.config/tmux/plugins/<name>` at that exact commit, and `tmux.conf` runs
each plugin's `.tmux` file itself. There is no TPM: it can only follow branches,
so it ran whatever each default branch held on every start. Updating a plugin
means reading what changed and putting the new commit in `plugins.txt`.

`M-v` (`tmux/pr-view.sh`) shows the branch's PR description in a pane to the
right, the copy last read (`~/.cache/switchboard/pr-view`) at once and then the one read again in the background, which the pager is told of as a resize, so it draws it again where it was (`M-i`'s `ticket-view` and the image view, `pr-image`, the same): `glow` draws the Markdown and `mermaid-ascii` each Mermaid diagram as
text, a diagram it can't draw (only flowcharts and sequence diagrams) kept as
its source. `M-i` (`tmux/ticket-view.sh`) does the same for the Linear ticket the
branch or tab name gives, read from Linear's API with worktree-from-ticket's
key and laid out by `pr-view.js ticket`: the facts from its side panel, the
description, sub-issues, related tickets, links, and the comments with their
replies. Both draw with `tmux/glow-style.json`, glow's dark style without the #s before headings, and show a link as its text alone: `pr-view.js` hands glow the text between Private Use markers and splice makes it an OSC 8 link again, since glow prints a link's URL after its text. `pr-view.sh page` runs less in the background under a WINCH trap, so a resize lays the description out again at the new width and reopens it at the line that was on top; the image view (`pr-image.js`) keeps its headless Chrome open to do the same with its pages. `mermaid-ascii` is pinned the same way, by version and checksum in
`setup.sh` (`mermaid_ascii`), which `./setup.sh tmux` installs. Beside it, `M-p`'s "View the branch's PR
description as an image" (`tmux/pr-image.js`), draws the
description as GitHub does (its `body_html`, read with a GET, GitHub's
stylesheet, Mermaid in mermaid-cli's headless Chrome) and shows it a page at a
time as images, each of several marked "Page 2 of 3" ("↓ more" while more follow) in its top-right corner, through tmux's passthrough for that pane alone. It opens in
place of the pane, as `M-d`'s diff does (`pane-in-place.sh`'s `pr-image`), and
`q` or asking for it again puts the pane back. M-p's "View the branch's Linear ticket as an image" is the same script with `--ticket <ID>` (`pane-in-place.sh`'s `ticket-image`, the ID from the branch or the tab's name as `M-i` finds it): the ticket from Linear's API, its facts, description, sub-issues and comments, the Markdown drawn in the page by marked and cleaned by DOMPurify, both pinned by version, since nothing has made Linear's Markdown safe the way GitHub's `body_html` is.

`M-r` and `M-p`'s "Open the repository in the browser" go through `tmux/gh-open.sh`, which opens GitHub's page for the branch's PR or the repository, or else says in a box which any key closes why it can't: not a git repository, no remote on GitHub, `gh` missing or signed out, a repository GitHub doesn't have or won't show you, or a branch with no PR yet. tmux's own message for a failed `run-shell` says only that it returned 1, so anything else that opens a page from a binding should say why it can't the same way.

## The notes app

`notes/` is a Neovim plugin, the notes app `bin/notes` opens: `lua/notes/` has one module per part (`store` for the files on disk, `render` for drawing a note's Markdown the way macOS Notes shows it, `format` for the Format menu's commands and the typing it does, `table`, `fold`, `links`, `sidebar`, `sync` for notes changed from outside, and `init`, which wires them into the note and sidebar windows). `bin/notes` runs your normal Neovim config and adds the plugin with `-c`, after the config has loaded, because lazy.nvim resets the runtimepath while it starts and would drop anything added with `--cmd`; the plugin is never part of `nvim/`, so plain `nvim` doesn't load it. Notes live in `$NOTES_DIR` or `~/Notes`, never in this repository, which is public. Copilot is not loaded in the notes app at all: `bin/notes` sets `g:notes_app` with `--cmd`, before the config, and `nvim/lua/plugins/copilot.lua` has `cond = not vim.g.notes_app`. As a second layer, a note's buffer is made with `bufadd` and marked `b:copilot_enabled = false` before it is loaded, since Copilot attaches on `FileType`, which fires while the file loads; nvim-cmp is turned off in it, and it keeps no undo file. So a note's text isn't sent anywhere and Tab and Enter are the app's; keep it that way for anything else that would read a buffer, and give anything that attaches on `FileType` a `g:notes_app` condition too. The exceptions are squashing notes (`s` and `S` in the sidebar, `notes/lua/notes/squash.lua`), which sends only the marked notes to a headless Claude after you say yes, and the `note-tickets` and `note-watch` skills, which you start yourself and which read only the notes you name or confirm; both are `disable-model-invocation`, so Claude never reads your notes on its own. The third is today's todo note (`lib/sidebar/todo.js`), which sends your notes' unticked items to Claude only once you turn its `todo_note` setting on. `note-watch` keeps a Monitor on one note (`claude/skills/note-watch/scripts/watch-note.js`, plain Node with no packages) and works each item added to it. Changes made to a note's file from outside reach the open app through `sync.lua`: each note buffer remembers its file as last read or written, every save first brings in any change since (merged line by line with unsaved typing, both versions kept where the same lines changed), and a watch on the notes directory brings changes in as they happen. So nothing outside the app has to wait for it to close, and nothing in the app may write a note without going through `M.save`. A note's images (`notes/lua/notes/images.lua`, the Format menu's Paste image, or Ctrl-V in Insert mode, Neovim's own Ctrl-V when the clipboard holds no image, the `notes_ctrl_v_image` setting) are saved from the clipboard beside the note in `.attachments/<note>/` in its folder and written as `![name](path)` under the item the cursor is on; `images.draw`, from `render.draw`, draws each picture under its line (a JPEG, GIF, WebP or HEIC made a PNG in Neovim's cache with macOS's `sips` first, since the terminal reads PNG alone) with the kitty graphics protocol's Unicode placeholders, as `tmux/pr-image.js` does (the file's path given to the terminal once through tmux's passthrough, which `bin/notes` allows for its own pane alone, and virtual lines of placeholder cells coloured with the image's id, which tmux places like text, so a popup over them covers the picture too; sized from tmux's `client_cell_width` and `_height`, `notes_images` setting); Enter opens one in Quick Look, only a file inside the notes directory (`images.file`). Ctrl-Shift-P opens its command palette (`notes/lua/notes/palette.lua`, fzf in a floating window, `notes_palette` setting): the list's commands, the Format menu's (`format_items`, which the menu draws from too), folding, and Switchboard's for Notes, pressed in tmux as their keys (`send-keys -K`, the `palette` table for those with no hotkey), so a new command in the app, or a new `#notes` binding, gets a row there. For anyone who doesn't know Vim's keys (`notes/lua/notes/easy.lua`): a toolbar in the note window's winbar, a button per Format menu item named in its `BUTTONS` (by the item's label, so it runs what the menu runs, on the selection or the cursor's word or line) and `⋯` for the menu, lit under the mouse through `mousemoveevent` (`notes_toolbar` setting, on); and easy mode (`easy_keys`, off by default, since it changes what keys do): `keymodel` and `selectmode` so Shift-arrows and the mouse select and typing replaces, and Cmd-S, Cmd-Z, Cmd-Shift-Z and Cmd-X, which `ghostty/config` sends as Ctrl+Alt+Shift keys (tmux reads a Cmd key as Alt, so Cmd-S would be `M-s`) and `tmux.conf` passes only to a pane Notes marks `@notes_cmd_keys` while it runs in easy mode, with a key help line in the statusline, lualine hidden (`key_help_line`). M-d's diff gets the same in `nvim/diff.lua`: buttons for the list's keys in the statusline, each pressing its key in the file list, and the keys named after them. Vim's keys stay the default, and docs and tips name them first, the click or arrow after. Its tests are in `test/notes.test.js` and run with the relay's under `node --test test/*.test.js`: each runs Lua in a headless `nvim -u NONE` with a temporary `NOTES_DIR` and HOME, so it never reads your config or your notes. The user-facing description and keys are in `bin/README.md`. Only one app runs on a notes directory at a time: `M.start` takes `.notes.lock` there (`store.lock`), and a second one shows a message instead of opening, since two would write over each other; a note renamed (its title, `R` in the list, `init.retitle`), moved, squashed or in a renamed folder takes the tabs linked to it along (`store.relink`: `@tab_note`, `@tab_note_last`, `@tab_note_arrived`, and the `@tab_name` of a tab named after it), through tmux, so the tests run with no `TMUX` but a throwaway server's; `.notes.json` is written to a temporary file and renamed into place. `M-N` runs `tmux/notes-open.sh`, which finds the notes pane by its `@notes_pane` option (a tab of its own also carries `@notes`), not its name, and `M-e` runs it to move that same pane beside the one you are in (`join-pane`), or back to a tab of its own (`break-pane`), or to start it there; moved out of its own tab, it leaves `tmux/notes-away.sh` in its place (a pane marked `@notes_placeholder`) saying which tab has it, and goes back into that tab when put away; beside another tab's pane the app's own sidebar is put away and shown again in Notes' tab, through the socket (`show_sidebar`, or `NOTES_SIDEBAR=off` for an app started beside one, `notes_hide_sidebar` setting), and left alone in a tab not its own when that tab's last pane closes, it goes back to its own (`notes-open.sh orphan`, from the `pane-exited` and `after-kill-pane` hooks, only in a tab M-e marked `@notes_beside`, since a Notes tab tmux-resurrect restored without its marks looks the same); it shows each tab its own note, the one the tab's Claude settled with `pick-note.md` (`@tab_note`) else the last one opened beside that tab (`@tab_note_last`, kept as Notes leaves, only once the tab has a note or another was opened there than the one Notes came with, `@tab_note_arrived`, so a note carried over from the last tab isn't taken as this one's), opened in the running app through the socket `bin/notes` listens on (`NOTES_SOCKET`, `~/.local/state/switchboard/notes.sock`) or, for an app not yet running, by making it `.notes.json`'s last note; a note's own tab is opened from Notes' `t` or `M-p` (`tmux/note-tab.sh`): the tab linked to it, else a question in a popup (`note-tab.sh choose`): an open tab, linked to it then, or a new one through `new-tab.zsh` with `NEW_TAB_NOTE` and `NEW_TAB_NAME`, so you still pick its directory, its Claude told the note's title and file with `--append-system-prompt` (`NEW_TAB_CONTEXT`, in the tab's environment, `note_tab_prompt` setting; `test/new-tab.test.js`), and whichever it goes to, Notes moves beside the tab's Claude showing the note, as `M-e` puts it there (`note-tab.sh beside`, `NEW_TAB_CLIENT` passing the client to `new-tab.zsh`, `note_tab_beside` setting); a tab with neither is asked which note is its until told to keep what is open (`tmux/note-pick.sh`, the likeliest first, so Enter takes it, ranked by its ticket and PR, its name against the notes' titles, and its repository, `ask_tab_note` setting), which reads the notes' text only to rank them, on the Mac; and starts notes from `zsh -i` for the PATH the tmux server lacks; there is only ever one, because every note saves itself as you type and two Neovims would write over each other.

## Checking tmux.conf

`test/tmux-conf.test.js` loads `tmux.conf` into a throwaway server and checks it loads without an error and that every `bind` runs as many commands as the file gives it, which a `\;` that lost its backslash breaks silently. The file skips what reaches beyond that server (starting the sidebar daemon, the plugins, the theme) while `@conf_check` is set, inside `%if`; anything new it runs at load belongs inside one too.

## The Calendar and Slack views

Mission control's Calendar view (`lib/sidebar/calendar.js`) reads your Google Calendar's secret iCal address straight from its feed when it is in the Keychain (service `google-calendar-ical`, `lib/sidebar/calendar-feed.js`), every five minutes and when you go to the view, with ical.js working out repeats and time zones, and each event's Google ID (a moved occurrence's by when it was meant to start), which the event's menu answers an invitation by through `lib/connector.js` (`respond_to_event`, `calendar_rsvp` setting); pinned with lib's other Node packages in `lib/package.json`, which `./setup.sh tmux` installs with `npm ci` (`lib_packages`). When the feed is lost, every look failing for 15 minutes (`feedDown`, `FEED_DOWN_MS`), it falls back to `/today` as if there were no address, the daemon opening a Calendar tab to loop it, and goes back to the feed once a look succeeds. Without the address, it draws the day `/today` last saved with its `scripts/save.js` to `~/.local/state/tmux-sidebar/calendar.json`, since the daemon can't reach the Google Calendar connector; a change to the file's shape belongs in both. The Calendar tab is opened by `tmux/loop-tab.sh Calendar 30m /today`, which `M-p`'s command runs and the daemon runs with `--background` when the saved day is out of date and no tab is keeping it, at most every ten minutes. `loop-tab.sh` marks the window `@loop_tab`, so the Slack relay alerts on its waits but not on the turn each tick finishes. With the `slack_background` setting on (the default), the daemon looks at Slack itself every minute while you're here (`lib/sidebar/slack-look.js`): one search through `lib/connector.js` for everything since the last look, sorted as the skill sorts it and saved through the skill's own `save.js`, so no Slack tab is needed; `resultsFrom` parses the connector's text, so a change to its layout belongs there. With it off, the Slack view (`lib/sidebar/slack.js`) works as the Calendar's does, from what `/slack-updates` saves with its `scripts/save.js` to `slack.json` beside it, its tab opened by `loop-tab.sh Slack 5m /slack-updates`; that script drops anything in the relay's DM or from its bot, keeps each message's lines (drawn as Slack draws them by `slackLines` in `render.js`, in Enter's menu and the Notifications view, the row showing it on one line), and keeps the newest message you wrote in each DM and thread (`replied`), which the view takes as having read what came before it there, as named in the relay's state file, and going to the view types `/slack-updates` into the Slack tab's Claude while it sits between ticks (`slackNow` in the daemon). The skill only reads Slack. Every link mission control and the link view open goes through `tmux/open-url.sh`, in the Chrome profile `~/.config/switchboard/browser.json` gives its host (Linear's and Slack's), else the default browser (GitHub's); that file is never in this repository. `tmux/link-view.sh` reads a link in a pane beside the current one (and, with `media`, opens an image or video file or link the pane shows, in its app through `open`, `M-p`'s "Open an image or video from this pane"): a PR through `pr-view.sh page prepare`, a Linear ticket through `ticket-view.sh show`, a Notion page or Google Doc or Slides deck through `lib/link-view.js doc`, which runs `claude -p` with Haiku, no built-in tools and only the one connector tool allowed, and takes the page from that tool call's result in the stream, never from what Haiku writes (`link_view_docs` setting), a note `search.sh` found as a `file://` link, read only from the notes directory, any other page as Markdown from `lib/link-view.js` (turndown, in `lib/package.json`) through `pr-view.sh page page`.

`lib/connector.js` is the one way a script reaches Claude's connectors. A connector Claude doesn't have, or one whose sign-in lapsed, fails with `notConnected` and a message naming the service and `/mcp`, and every call records its service's state in the sidebar's state directory (`connectors.json`, and `connectors-down` for the health light), so a feature that is on says where it shows that its connector is missing rather than failing quietly (the Slack view, search's Slack row, the link view, RSVP); a new feature that uses a connector shows `connectorDown(<service>)` the same way. Each call (the link view's Notion and Google Docs, search's Slack, and the rest) is `claude -p` with Haiku, no built-in tools but tool search (which keeps the other connectors' tool definitions out of its context, a fiftieth of the cost) and the one tool allowed, its stdin closed and no session kept, the answer taken from the tool call's result in the stream, never from what Haiku writes, and read back from the file Claude Code saves a result too large to show in. `M-S-f`'s `tmux/search.sh` runs `lib/search.js` under `zsh -i` (a popup has no nvm) and streams its rows into fzf as each source answers. The link view takes its link in `LINK_VIEW_URL`, set with `split-window -e`, which passes it as written, never in the pane's command line, where zsh would read a link's `&` or `(`.

A view that is on is always in mission control: before its integration is set up it says what is missing and how to set it up, in words from `lib/sidebar/setup-help.js` (the Calendar, Linear, GitHub) or `lib/connector.js` (a connector), drawn whole rather than cut to a line; a new view that reads from something needing setup does the same.

What changed on today's calendar since you last looked (an event added, moved, renamed or gone) goes in the sidebar's notifications (`lib/sidebar/calendar-changes.js`, `notice:calendar`, `calendar_changes` setting): today as last seen is kept in `calendar-seen.json` in the state directory, taken again when you press a key with the Calendar view in front and whole (Esc to close it included), since a terminal can sit behind another app while it draws, or dismiss one, and an event is known by its Google ID from the feed, else its title and start.

## The standup note

`lib/sidebar/standup.js` writes `Standups/Standup <date>.md` into the notes directory each weekday morning, from the daemon (`standup`, checked every minute, `standup_note` setting): the last working day's PRs and reviews (one `gh api graphql` search), Linear tickets assigned to or made by you that changed state (a ticket closed by a merge often has no assignee), and your commits in the tabs' repositories, then today's work, the day's list summed up over it in a few sentences by Haiku (`claude -p` through todo.js's `askClaude`, given only that list, `summaryPrompt`, `standup_summary` setting), the note written without them when Claude can't. It writes a new file only (`wx`), never one that is there, since the note is yours to edit once written; it, the meeting notes and today's todo note are the only things outside the notes app that create a note, and the app's directory watch takes them in. `standupFrom` builds the Markdown from the fetched data alone, so its test needs no network.

`lib/sidebar/todo.js` writes `Todos/Today's Todo <date>.md` each weekday from the hour `todo_note_time` names (`todo` in the daemon, checked every minute), only with the `todo_note` setting on, which is off by default: unlike the standup, it sends your notes' text to Claude (their unticked top-level items, from `openItems`, parked sections left out), so it is one of the exceptions to the notes app's rule that a note's text goes nowhere, and stays opt-in. The daemon hands it what its views last read (the PR and Tickets boards, CI, the Inbox, Slack's messages that need you, today's calendar), each only while its setting is on, and it asks GitHub only for the reviews asked of you; `todoPrompt` builds the prompt from that alone, and `writeTodo` takes the call to Claude as an argument, so its test needs neither the network nor Claude. Claude runs as `claude -p --model sonnet --tools ""`, the prompt on its stdin.

## Settings

The workspace's options, the ones a person might want off (banners, the sidebar, lookups, the theme, saving pane contents, the update check and the rest), are listed in `tmux/settings.json`, each with its key, category, label, description and default: on/off, or one of its `choices`. What someone changes is kept in `~/.config/switchboard/settings.json`, only the keys that differ from their defaults, which they may also edit by hand; it is never in this repository. Neither writer (`writeSetting`, `settings.sh set`) writes over a file there that can't be read as a JSON object, since starting from nothing would lose every other setting, and each keeps the version before as `settings.json.bak`. `lib/settings.js` reads and writes it for Node (the sidebar daemon, the Slack relay), and `tmux/settings.sh apply` sets each value as a global tmux option, `@setting_<key>` (on/off or the choice), plus the few that are tmux's own (`status`, resurrect's and continuum's). tmux.conf runs it with `--load` before the plugins, since continuum reads its restore setting as it loads, and `settings.sh theme` where theme.sh ran before; the sidebar daemon watches the file and runs `apply` whenever it changes, so a change takes effect at once. The scripts and hooks read the tmux option, in a format or in a tmux call they already make, never by starting a process of their own on a hot path. Mission control's Settings view (`M-p`, "Settings") lists them under their categories; Enter or Space changes one, and `/` filters by name, description, category or value. Its last row, "Your CLAUDE.md" (`claudeMdItems` in `lib/sidebar/views.js`), isn't a setting of `settings.json`: Enter offers the local file, another file or a repository, the last two typed in (`client.asking`, `askModal`), writes `~/.config/switchboard/claude.json` and runs `setup.sh claude_md`, the one part that does only that step, so a change to `claude.json`'s shape belongs in `setup.sh`'s `claude_md`, `claudeMdSource` and the daemon's `claudeMdChoices`. A new option is one entry in `tmux/settings.json` and the code that reads it. Every new feature gets one, on by default, so someone can turn each part off and have a plain workspace: a view, a sidebar block, a background check, a key that changes what an existing one does. Anything new that takes a choice (a menu, a question, a list to pick from, a box that closes) takes a click too: a box in mission control through `modalBox`'s tags and `modalMouse`, a bash menu in a popup through `tmux/menu.sh`, an fzf list as fzf does. The `github` and `linear` options turn each service off as a whole: `settings.sh` binds every key whose description carries `#github` or `#linear` (root, prefix and palette tables) to do nothing, which also drops it from `M-p`, and reloads tmux.conf to give the keys back when the service is turned on again, so a new binding that uses either service must carry its tag; `palette.sh` leaves out the tagged ones as well; mission control drops the PRs, CI and Merge queues views (github, `lib/sidebar/ciboard.js`, `lib/sidebar/queues.js`) and the Tickets and Inbox views (linear, `lib/sidebar/ticketboard.js`, `lib/sidebar/inbox.js`), `prs.js` stops asking about merge states, the Work map shows no PR or ticket, and `path-facts.sh` asks neither for the tab's name. Anything new that reaches GitHub or Linear from tmux checks its setting the same way.

## Menus

Every menu, question and list in a popup looks one way, mission control's boxes' (`modalBox` in `lib/sidebar/render.js`): a rounded edge in colour81 (tmux's `popup-border-lines` and `popup-border-style` give every popup that frame, each `display-popup` title written `-T '#[bold] … '`), the chosen option on the highlight with a yellow bold `›`, the keys dim on a row of their own at the bottom. A full-screen popup of the daemon's is a box filling it (`framed`), a bash menu draws its rows with `tmux/menu.sh`'s `menu_option` and `menu_keys` in the theme's colors, and an fzf list adds `tmux/fzf-style.sh`'s options to `FZF_DEFAULT_OPTS`, with no border of its own inside the popup's. A new one uses them. A button is drawn alike everywhere: `SwitchboardButton` and `SwitchboardButtonHover` in Neovim (`nvim/colors/ghostty.lua`), `@button_style` in tmux, and mission control's menus light the option under the mouse (any-motion reporting, `?1003h`, with `menu_mouse` on).

## Yes/no questions

Every yes/no question takes Enter as yes and shows it as `[Y/n]`: `setup.sh`'s `ask`, `confirm.sh`, mission control's `confirmModal` and `worktree-done`. A closed input (no terminal, end of file) is always no, so nothing piped or run unattended says yes. A new question does the same. The update popup (`repo-update.sh prompt`) is a menu instead, moved through with j and k and taken with Enter, "Update now" first so Enter alone still updates; Esc or q is "Not now", and a closed input answers nothing.

## Messages

What a key or script has to say (nothing needs you, a link copied, no ticket in this branch) goes through `tmux/say.sh`, never `tmux display-message`: a small box in the middle of the client's screen, as wide and tall as the text, which any key closes and which closes itself after five seconds (`-t`), opened in the background so nothing waits on it, its text passed in the environment (`SAY_TEXT`). The sidebar daemon calls it as `sayBox`. A client shows one popup at a time, so a script that says something and then opens a popup of its own closes the box first (`say.sh close`), or waits for it to be read (`say.sh wait`, as `pane-in-place.sh` does before diffview when its fetch failed), as `repo-update.sh` and `linear-project.sh` do, and a script running in a popup says it with `-a`, which has the tmux server open the box a moment after that popup closes (`link-view.sh pick`), since tmux takes a popup asked for while one is open as a change to that one. With the `message_boxes` setting off, it is the status-line message again (its `#` doubled for tmux's format).

## Tips

`tmux/tip.sh` shows a tip in a small box in the top-right corner, once each, at the moment its key would help. From `agent-state.sh`: `waiting` and `done` when a tab first waits on you or finishes while you look elsewhere (`set_state`), `worktree` when Claude first starts in a worktree (its PR keys, with GitHub on). From tmux.conf: `jump` on a tab switch with five tabs or more (the `session-window-changed` hook), `pinned` on the first `M-f`. From the sidebar daemon (`tipsFor`), which alone can tell: `merged`, `loop` (a tab looping in the background) and `sidebar` (first focused). `in-place` when a tool first takes a pane's place (`pane-in-place.sh`), `updates` after the first update popup (`repo-update.sh`), `github_off` and `linear_off` when a key of a service turned off in Settings is pressed (the binding `settings.sh` gives it), and `key-<keys>` after a palette pick that has a hotkey of its own (`palette.sh`, `tip.sh key`), once for each key. A client shows one popup at a time, so a tip that can't open behind another popup is left unshown for next time; mission control, a popup itself, says its tip in its own footer on its first opening instead. Any key closes the box and goes on to tmux as if the box hadn't been there (`send-keys -K`, a moment after it closes), so nothing typed is lost, and it closes itself after eight seconds. Never put a tip in the status line: one that goes on the next key press is missed. What was shown is kept in `~/.local/state/switchboard/tips` and as `@tip_seen_<tip>` options, which `tip.sh load` sets when tmux starts; a trigger checks that option in a format, so it starts nothing once the tip has been shown, and doing what a tip teaches (`M-a`, `M-j`) marks it shown. The `tips` setting turns them off, and "Show the tips again" in `M-p` resets them. A new tip is its text in `text_of` and a trigger gated the same way.

## The health light

It runs every `status-interval`, so it is one tmux call and file checks. Anything else that can stop without a word belongs in it.

## Key bindings and the M-p palette

Lazygit (in `M-p`, with no hotkey) and `M-d` (diffview.nvim, `nvim/lua/plugins/diffview.lua`, showing the branch's committed changes against its PR's base, fetched first unless the branch is at the commit it last compared (`~/.cache/switchboard/diff-base`), since its merge base can't have moved, as GitHub's "Files changed" does) put a tool in the pane's place without touching the rest of the window (`tmux/pane-in-place.sh`): the tool starts in a window of its own and `swap-pane` trades places, the pane waiting in that window, marked `@pane_parked` so the sidebar gives it no sidebar and lists it as no tab, and the tool's pane naming it in `@parked_pane` and itself in `@in_place`, which the key uses to quit its own tool, since the tool's pane reads as the shell that runs it. The shell swaps the pane back when the tool exits, and `confirm.sh` swaps back any `@parked_pane` before it kills a pane, so closing the tool's pane with `M-w` never strands it. `M-p`'s "Show the pane a tool stands in for beside it" and "Show a tool in place of a pane alone again" (`pane-in-place.sh side` and `full`, from either pane) bring the parked pane into the tool's window on its left, half the width (`join-pane`), and park it again (`break-pane`, `@pane_parked`), so a Claude session and its lazygit, diff or image view sit side by side. Another tool in place goes in `pane-in-place.sh`'s list.

`M-p` opens `tmux/palette.sh`, an fzf list of the custom bindings that picks
one and presses its key. The list is read from tmux, not kept anywhere: a
binding shows up when `tmux.conf` gives it a description with
`bind -N "<what it does> #tag #tag"`, so every new custom binding needs one,
ending in tags: a few `#words` for what it is about (`#git`, `#pr`, `#tabs`),
which the palette shows dimmed and matches and ranks as any other word. In the
prefix table only keys `tmux.conf` binds with `-N` are listed, since tmux's own
prefix bindings carry descriptions too. A command that belongs in the palette
but has no hotkey is bound with `-N` in the `palette` key table, which no key
leads to, as the branch-copy commands (`tmux/branch-copy.sh`) are: the palette
lists that table with no key shown, and the `M-p` binding switches the client
to it before pressing the key.

The palette lists the commands picked last first, newest first, from
`~/.local/state/tmux-palette/recent` (the last six keys, written by
`palette.sh` after each pick), then the rest by description. As you type, a command picked before after the same words comes first, then one picked after longer words starting with them (`~/.local/state/tmux-palette/queries`, `<query>\t<key>`, the last 300, read by `--rank`; the `palette_learn` setting). Its columns are
fitted to the popup, 60% of the screen, so a description or tag list too long
for its column is cut with an ellipsis. `tmux.conf` empties the `palette`
table before binding it (`unbind -aq -T palette`), so a command taken out of
the file leaves the palette on the next reload; a binding removed from the
root or prefix table still needs `tmux unbind` by hand.

The ⌘ Commands button in `status-left` (`@palette_button`, a `range=user|palette` in `@button_style`, which `theme.sh` sets for dark and light; `palette_button` setting) opens the palette: `MouseDown1Status` presses `M-p` when `mouse_status_range` is `palette` and does tmux's own `switch-client -t =` otherwise, and `update-colors.sh` rewrites `status-left` with it, so a change to one belongs in both. `M-Left`, `M-Down`, `M-Up` and `M-Right` move between panes as `C-w` does, passed on to Neovim (`is_vim`), where vim-tmux-navigator, and `diff.lua` in M-d's diff, moves between windows and hands off to tmux at the edges (`pane_arrows` setting).

A terminal that reports Shift as a modifier of its own sends Alt+Shift+J as `M-S-J` or `M-S-j`, which tmux takes for a key other than `M-J`, so each `M-<capital>` binding has two lines after the split bindings that press it with `send-keys -K`; a new `M-<capital>` binding gets the same two.

Every format inside a shell command (`run-shell`, `if-shell` without `-F`,
`#(...)`) is written `#{q:...}`, never bare or in quotes. tmux pastes the value
into the command before the shell parses it, so a directory named
`repo$(...)` would run that code, and the pane-focus-in hook would do it
without a keypress. `q:` shell-quotes the value. Values tmux makes itself
(`#{window_id}`, `#{client_name}`) are quoted too, so the rule has no
exceptions to remember. Formats given to tmux options such as `-c` or `-d` are
not shell and are fine as they are.

`display-popup` does not expand formats in its command: `#{pane_id}` reaches
the shell as written, and the shell reads the `#` as the start of a comment, so
the script gets no argument at all. Its `-d` start directory is expanded, so a
popup that needs the pane's path takes it from `-d '#{pane_current_path}'` and
the script defaults to `$PWD`, as `M-m` does with `pr-ready.sh`.

## Skills and the scripts they call

Its cleanup is `clean-worktree`'s, read the same way, which also runs on its own on any worktree whose commits are all on GitHub. It waits for the deploy (`scripts/wait-deploy.js`, GitHub deployments or a deploy workflow, plain Node) and records a browser test of the feature on the deployed site with `walkthrough`'s recorder (`claude/skills/walkthrough/scripts/record.js`, Playwright in the system Chrome, a captioned video converted to mp4 with ffmpeg, named by `--name`, a few words the skill writes saying what the feature does, else after the tmux tab; a test's video stays in the session's scratchpad under `/tmp`, and only `walkthrough` keeps one, in `~/Movies/Walkthroughs/`, offering each time to move videos there over 30 days old to the Trash). `walkthrough` records a feature as a video to keep or share, from the site's home page through its own navigation, and owns the recorder and its rules ("Recording", "Reviewing the video"), which `deploy-test` and `preview-test` read and follow, so a change to how videos are made belongs there: an init script draws a `highlight(locator)` outline and a cursor that moves to each click with a ripple into every page, and the caption and an address bar (each address the page shows, `pushState` ones too, from Playwright's `framenavigated`) are drawn as images by Chrome and laid round the recording by ffmpeg, above and below the page, so neither covers it (`frame`, the times kept in the result's `timeline`); `--pace demo` holds each step longer and walks on past a failed `expect`, `--pace test` (theirs) stops at it; each run also writes a contact sheet (ffmpeg's `tile`) that the skills look over before asking you; `test/walkthrough.test.js` records against a page it serves, skipped where the skill's packages or Chrome are missing. Each site keeps a Chrome profile in `~/.cache/deploy-test/profiles/<host>` (the path from before `walkthrough` owned the recorder, so no one signs in again), signed into by hand with `record.js --login`, so no session ever lives in a repository; a test there must change nothing real unless the environment is a test one or you say so. `oncall` watches a team's Slack alert channels while you're on call, as `/loop /oncall`, and reaches you only through `slack-relay notify`, so its notices come from the relay's bot and Slack notifies you of them; the channels and the team's own rules are in `~/.config/switchboard/oncall.json` and the rules file it names, never in this repository, which keeps only the general rules and `config.example.json` with made-up IDs. `bin/slack-relay` reads the `@agent_state` and `@agent_since` pane options that `tmux/agent-state.sh` keeps, to tell the user which tabs need them, so a change to those names or states has to reach it. `slack-relay` is a Slack app talking to its owner in the app's DM, over Socket Mode and the Web API, with its tokens in the Keychain and its owner's member ID in `~/.config/switchboard/slack-relay.json`. Two rules in `lib/slack-relay/slack.js` keep it from being anyone else's remote control, and every new Slack call must go through them: an incoming message is acted on only if `fromOwner` passes (the owner, in that DM, in that workspace, not a bot) and `typedByYou` does (Slack's `client_msg_id` and no `app_id`, since other apps can post as the owner), a button press only if `pressFrom` passes (the owner, on a message in that DM, or on the Home tab or a tab's screen, which take only their own buttons), a form sent from one of its screens (Rename, Message, Skill, New tab) only if `submissionFrom` does, and nothing else Slack sends, reactions included, controls anything, and `slack.api` refuses any call that names a conversation other than the DM. The owner never comes from a message. Its code is in `lib/slack-relay/`, one module per part, and `bin/slack-relay` only picks the command and exports every part for the tests; a module that needs another's name requires it directly, and none may require one that leads back to it, since a cycle hands it an empty module. Its tests, `node --test test/*.test.js`, run against a throwaway tmux server, a temporary HOME and Slack stand-ins; a test must never reach your real tmux server or Slack, so keep any new one inside that setup. A test that reads a tab's skills opens the tab in the tests' temporary directory: one opened in the repository would walk up to your real `~/.claude`, since the temporary HOME isn't above it. Document each script in `bin/README.md`.

`M-j` and `M-o` open mission control's Work map as a picker, a filter
typing, scoped to open tabs or to the worktrees no tab has open. The second
comes from `bin/wt-revive --json`, which the sidebar daemon runs in the
background (`refreshRevived` in `lib/sidebar/views.js`), so a change to the
rows it prints belongs there too. Enter on one reopens it with `claude-here` (`bin/claude-here`, `test/claude-here.test.js`),
the same handoff `wtr` makes, so a change to how `claude-here` resumes a
directory reaches both. Neither `wt-revive` nor `wt-jump` has a picker of its
own any more: `wt-revive` prints the rows, and `wt-jump` takes a ticket, PR or
branch to jump to. It finds a worktree's last
session from the `cwd` in Claude Code's transcripts, and keeps what each
transcript says in `~/.cache/wt-revive/index.json` against its size and
modified time, so a press reads only the transcripts that changed. Reading the
end of every transcript on every press, one pipeline each, started about a
thousand processes and took three seconds.

`wt-jump` builds its picker rows from `tmux/tab-status.sh`, so a
change to what the second status line prints shows up in the picker, and the
line has to stay fast enough to run for every window at once.

Anything in `bin/` called from a tmux binding needs a wrapper like that one. The
tmux server keeps the environment it was started with, and nvm is set up in
`~/.zshrc`, which only interactive shells read — so a node script run straight
from a binding dies on `env: node: No such file or directory`, and with
`display-popup -E` it closes so fast it reads as a flicker rather than an error.
Scripts that parse `tmux -F` output want `LC_ALL` set to a UTF-8 locale too:
without one, tmux rewrites control characters in its output, tab delimiters
included.
