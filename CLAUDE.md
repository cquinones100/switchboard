# Switchboard

Switchboard, called editor-configs until October 2026, is a terminal workspace for working with coding agents: one Rust binary, `switchboard`, that is its own terminal multiplexer with a server, and has the sidebar, mission control, the palette, the PR and ticket views, the diff viewer, the notes app and the Slack relay built in. `switchboard` alone starts the workspace or attaches to it; `switchboard <command>` runs everything else. It was a tmux setup with Node, shell and Lua scripts until the rewrite, which replaced every part and removed them; each module's opening comment names the files it came from, which git's history still has.

[README.md](README.md) is the front page for someone new (what it is, the requirements, installing, the first keys, the files of your own); [docs/guide.md](docs/guide.md) describes every feature, key and command; [ARCHITECTURE.md](ARCHITECTURE.md) describes the code, and ends with what the binary doesn't do yet. Keep all three in step with the code: a new or changed key (`src/mux/keys.rs`, a part's `Command`), command (`src/cmd/mod.rs`'s `COMMANDS`, `src/mux/commands.rs`), setting (`assets/settings.json`) or file of your own belongs in the guide, and the README's keys, requirements and install steps follow `keys.rs` and `install.sh`.

## Building and testing

The Rust is pinned in `rust-toolchain.toml` (`rustup toolchain install` in the clone). Before every commit:

- `cargo fmt`;
- `cargo clippy --all-targets`, with no warnings (CI runs it with `-D warnings`);
- `cargo test`, all passing;
- `cargo check --no-default-features --target aarch64-apple-darwin` (`rustup target add aarch64-apple-darwin` once), which type-checks every macOS path from Linux, since the `net` feature holds the only C the build compiles.

CI (`.github/workflows/ci.yml`) runs the first three on Linux and an Apple silicon Mac and builds for Intel Macs. Every integration test is a binary linking every crate, so the target directory is large: debug builds keep only line tables, and a worktree's build should not leave extra copies of `target/` about.

Unit tests sit beside the code. Integration tests are in `tests/`, and `tests/common` gives each a server of its own in a temporary home under `/tmp` (short, since a Unix socket's path can't be over 104 bytes on macOS), commands run against it, and a client that reads what the server draws through a terminal emulator. A test server starts with the day's notes and the Slack lookups off (`common::QUIET`), since a standup note made on a Monday shows in the sidebar, and `common::write_settings` writes a test's settings over them, so a test of one of them turns it on. Services are stand-ins on 127.0.0.1 (`SWITCHBOARD_GITHUB_API`, `SWITCHBOARD_GITHUB_GRAPHQL`, `SWITCHBOARD_LINEAR_API`), and `claude`, `gh`, Slack and the desktop's tools are stand-ins on the test's PATH. A test must never reach the real server, the real home or a real service, so a new one stays inside that setup: one that reads a tab's skills opens the tab in the test's temporary directory, since one in the repository would walk up to your real `~/.claude`.

## Testing in the workspace in use

The Switchboard you work in is the one in use, and the person may be typing in it. Before testing anything there (opening or closing a tab, moving focus, sending keys, `switchboard kill-server`, `switchboard upgrade` or restarting the server to load a new build), stop, say that the test needs the workspace and what it will do, and wait for a go-ahead. Test in a server of the tests' own where that can show the same thing.

To try a change by hand, use `switchboard try` (`src/cmd/try_.rs`, ported from bin/switchboard-try), which builds the worktree with cargo and runs it under a home of its own, `/tmp/sb-<hash>`, with its own settings, state, server and socket, after the build's own `switchboard setup plugin claude claude-md skills` has laid out its plugin (the hooks, skills and instructions its panes' Claude loads), statusline and permissions there (or, with `claude_plugin` off in the settings it copies, its hooks, CLAUDE.md and skills in its own `~/.claude`); its `~/.local/bin/switchboard` is the build, first on its PATH, so Claude Code's hooks in its panes reach the try's server. A Claude in the worktree uses `switchboard try --detached`, which starts the try's server with no client and prints the prefix that reaches it (`<prefix> send-keys`, `<prefix> capture-pane`, `<prefix> list`); `--print` prints the environment for a terminal of your own (`eval "$(switchboard try --print)"`, then `switchboard`); `switchboard try --clean` ends it and removes its home when done. It works because everything finds itself through `~`: a module that reaches for an absolute path of your real home breaks it, and a new state, config or cache location under `~` has to be sorted into what it links, copies or leaves fresh. Its settings turn off what would duplicate your real workspace (`TURNED_OFF`: the Slack look and view, meeting, standup and todo notes, banners, the update check, restoring saved tabs). It isn't sealed off: it links your Keychain, dotfiles (`.ssh`, `.gitconfig`, shell history), the `~/.config` folders Switchboard doesn't configure (gh's sign-in among them), `~/.local/share`, Claude's plugins and sign-in, your own Claude hooks and skills, and the programs in `~/.local/bin` that aren't Switchboard's, so keys sent there act with your real credentials, and anything that would change one of those, push, or reach a service still waits for a go-ahead. It refuses a worktree holding someone else's code (a fork's PR, by `src/trust.rs`'s checks) until its path is in `trusted-dirs`, which is asked about first, and a PR `wtpr --untrusted` checked out always: that runs only with `--sealed` (`src/cmd/try_sealed.rs`), on macOS, under a sandbox that reaches none of what this paragraph says it links, in a home made from nothing. A build run with `SWITCHBOARD_STATE_DIR` set never brings its plugin, skills and settings into your home, as a new build attaching (`setup::refresh`) and its server starting otherwise do (`setup::state_of_its_own`).

A running server keeps the binary it started with. A rebuilt `switchboard` reaches new commands and hooks at once, but the server only once it restarts: `switchboard upgrade` restarts it on the binary at the path it started from without ending anything (`src/mux/upgrade.rs`: the server execs the new build in its own process, handing it every pane's terminal, every attached terminal's connection and its socket), while `kill-server` ends every pane's program. A change to the protocol between them (`src/mux/proto.rs`, what `switchboard hook` sends) needs both. What a server hands over is `upgrade::Handover` and the pane's replay (`src/mux/replay.rs`): something new on a pane, a tab or a client that should survive an upgrade goes there, read with a default when it is missing, since the build reading the file is newer than the one that wrote it. A change a newer build couldn't take up from an older one's file bumps `upgrade::VERSION`, which the running server checks before it execs a build (`server --handover-version`), so it refuses that build rather than lose its panes.

When a change is ready to try, build it and put it in place of the binary the server runs without asking: `cargo build --release --locked`, then `install -m 755 target/release/switchboard ~/.local/bin/`, where the README and `install.sh` install it, both of which this repository's `.claude/settings.json` allows as these exact commands. When `command -v switchboard` names another path (`SWITCHBOARD_BIN_DIR`, or a binary put elsewhere on the PATH), install it there instead, which asks. With `CARGO_TARGET_DIR` (or cargo's `build.target-dir`) set, the build is that directory's `release/switchboard`, so install from there, which asks too. Work that lands through `/queue-and-clean` (a `/wtn` tab, autopilot) is ready to try once it has landed: build the landing target as it now is (the branch `switchboard landing` names), never the worktree before the landing, which would put code that hasn't landed into the binary the workspace runs. That is the commit the landing pushed (the target's branch on its remote, or the local branch when the target has none), not the local branch when it lags behind. Build it in the main clone when the main clone has the target checked out at that commit with nothing uncommitted (`git status --porcelain` printing nothing), as it normally does after the landing; otherwise in a detached worktree at that commit (`git worktree add --detach <dir> <commit>`), removed once the build is installed, whose install asks since it isn't the exact command allowed. Work tried before it lands, with no landing step, is built in the checkout it is in. Then say how to put it into the running workspace: `M-p`'s "Restart Switchboard on the latest build on disk", which builds the checkout the running binary was built from again (a second, with nothing new), puts the result in place of the binary the server runs, and restarts the server on the path it started from. Restarting it is still the person's to do, as above.

## Architecture

ARCHITECTURE.md has the whole picture; what follows is what a change has to keep.

**One task owns the server's state.** `src/mux/server.rs`'s `Server` holds the sessions, tabs, panes, clients and overlays, and everything else (client sockets, each pane's reader thread, timers, background lookups, file watches) sends it `Event`s. It handles them in order and draws the clients that changed, so nothing is shared or locked. Server state is touched only by that task: anything that reads the network, starts a process or reads more than a small file runs in a task of its own (or `spawn_blocking`) and answers with its part's event (`Event::Sources`, `Event::Day`, ...).

**Each part has the same shape**: modules that work on files and plain data, tested without a server, and a `serve.rs` whose `impl Server` puts them on the server: its keys, its share of the tick, the answers of its tasks. `src/lib.rs` lists the parts with a line each, and every module opens with a comment saying what it is and why it works as it does, naming the tmux-version file it was ported from; a new module does the same.

**Panes** are a PTY and an alacritty_terminal emulator each (`src/mux/pane.rs`). Every pane's environment carries `SWITCHBOARD` (the socket) and `SWITCHBOARD_PANE` (its id), which the commands and hooks use to reach the server and name their pane. Only the notes pane passes kitty's graphics commands to the terminal, and takes easy mode's Cmd keys (`src/mux/passthrough.rs`), since a graphics command can have the terminal read any file of yours. The server sends graphics commands of its own for the image atoms (`src/ui/images.rs`), always with the image's data inline (`t=d`), never a path.

**Apps in panes.** The views (`switchboard pr-view`, `ticket-view`, `link-view`, `view`), the diff (`switchboard diff`) and the notes app (`switchboard notes`) are programs of their own, drawn with ratatui and crossterm, which the server runs in a split or in a pane's place (the pane parked until the program ends, `src/diff/in_place.rs`). The server stays a multiplexer; each app is built and tested on its own.

**Commands.** What scripts and skills ask of the workspace (list the tabs, open one, send keys, read a pane's screen, set an option, say something) is a server command in `src/mux/commands.rs`, sent over the socket; a program of its own goes in `src/cmd/` and `COMMANDS`. A link to the binary named after a command runs it too.

**Claude's state.** Claude Code's hooks (`assets/claude-settings.json`'s) run `switchboard hook <Event>`, which sends the hook's JSON and `SWITCHBOARD_PANE` to the server (`src/agent/`). They reach Claude as Switchboard's plugin (`src/setup/plugin.rs`, `~/.local/share/switchboard/plugin`: the hooks, a SessionStart hook running `switchboard claude-context` for `assets/switchboard.md`, and the skills), which every pane names in `CLAUDE_CODE_PLUGIN_DIRS` while Settings' `claude_plugin` is on, so only the Claude in Switchboard's panes loads it; with it off, `switchboard setup` puts them in `~/.claude` as before (`src/setup/way.rs` decides which, and keeps the setting and `~/.claude` agreeing, since both at once would run each hook twice). A `claude -p` Switchboard starts for itself goes through `plugin::headless`, which takes the plugin out of the variable, and `claude-context` says nothing to a headless session. Claude Code waits on its hooks and runs them before and after every tool call, and adds some hooks' output to the conversation, so `switchboard hook` prints nothing, waits at most a second, and always exits 0; the one exception is autopilot's hands-free mode (`src/agent/hands_free.rs`), where the server answers PreToolUse for `AskUserQuestion` and Stop in a marked tab with the JSON Claude Code reads (a deny, a block), which the hook prints as it came. A tab holds one Claude: the sidebar, mission control, the Slack relay, `M-c` and `M-m` each take a tab's Claude to be one pane.

**Persistence.** The layout and tab options are saved as they change and restored when a server starts with none (`src/mux/persist.rs`); a new tab or pane option that should outlive a restart is saved there.

**Where things live.** Your own files in `~/.config/switchboard/`; Switchboard's state in `~/.local/state/switchboard/` (`SWITCHBOARD_STATE_DIR` moves it); caches in `~/.cache/switchboard/` (and `wt-revive`'s in `~/.cache/wt-revive/`); what setup writes for Claude Code (the plugin `plugin/`, `switchboard.md` the old way, the rules' clone `claude-md/`, `setup-build`) in `~/.local/share/switchboard/`; the Slack relay's state in `~/.local/state/slack-relay/`, and `/oncall`'s in `~/.local/state/oncall/`. Everything finds itself through `~` (`src/paths.rs`), so a test or a try can give a run a home of its own: a script or module that reaches for an absolute path of your real home breaks that. What the binary carries (the settings schema, Claude's settings, Switchboard's part of CLAUDE.md, the skills) is in `assets/`, compiled in, so the binary needs no clone.

## Rules the code keeps

**Nothing on the drawing path waits or starts a process.** Naming the tabs, the status line, the sidebar and mission control run on every focus, tick or draw, and a security agent on the computer this was written on inspects every process that starts, which once made the workspace sluggish. So they read what the server already holds: a directory's branch from git's own files (`src/tabs/git.rs`), not by running git; a PR, a ticket's title or a view's data from what a background lookup last answered, shown once it is known and kept while a look fails. A process is read only while a view that shows it is in front (the Resources view). A lookup that is due while the same one still waits is skipped (`src/sources/schedule.rs`), and the lookups pause while you're away (`pause_when_away`). Anything new that wants to add to a tab, the sidebar or a card follows the same rule.

**Settings.** Every option is in `assets/settings.json`, with its key, category, label, description and default (on/off, or one of its `choices`); what someone changes is kept in `~/.config/switchboard/settings.json`, only the keys that differ from their defaults, which they may also edit by hand. `src/settings.rs` reads it (`settings::is_on`, `settings::setting`) and writes it (`write_setting`), never over a file it can't read as a JSON object, keeping the version before as `settings.json.bak`; the server reads it again whenever it changes. A new option is one entry there and the code that reads it; its description says what it does now, and what turning it off does. Every new feature gets one, on by default unless it sends something of yours somewhere (as `todo_note` sends your notes' items to Claude), so each part can be turned off for a plain workspace: a view, a sidebar block, a background check, a key that changes what an existing one does. A new view with a setting goes in `src/usage/habits.rs`'s `VIEWS`, and a feature worth suggesting in `TRIES`.

**GitHub and Linear.** The `github` and `linear` settings turn off what the workspace does with each service by itself: its lookups, views and keys. Anything that reaches them goes through `src/integrations/`, which refuses while its setting is off, except in a program you run yourself (`codex-review`, `wt`, `wtpr`, `wait-deploy`, `wt-jump`, `worktree-done`), which calls `integrations::run_by_you` first, since the tmux version's scripts never read the settings; a key or palette command that uses one carries its `#github` or `#linear` tag, which takes it out of the palette and makes its key say the service is off.

**The user layer.** Every file of someone's own lives in `~/.config/switchboard/`, never in this repository, and nothing writes over one but Settings: `settings.json`, `keys.json` (bindings over the defaults), `sidebar.json` and `sidebar-plugins/`, `browser.json`, `linear.json`, `claude.json` and `CLAUDE.md`, `slack-updates.json`, `slack-relay.json`, `oncall.json` and `oncall-rules.md`, `repos.json`, `leak-check.txt`, `trusted-dirs`, and `secrets.json` where Linux has no keyring. Each setting in one has a row in mission control's Settings view, from `OWN_FILES` in `src/usage/own.rs`, so a new setting in a file there, or a new file, gets an entry there and a row in the README's and the guide's tables. No one's own rules live here: what every user's Claude needs to know about the workspace goes in `assets/switchboard.md`, which `switchboard setup` imports into `~/.claude/CLAUDE.md`.

**Claude Code's settings.** `assets/claude-settings.json` is Switchboard's part: the hooks, the statusline (`switchboard statusline`) and the permissions its skills and loops need to run unattended (their `switchboard` commands, read-only git and gh, the read-only connector tools); anything that writes outside the computer is left to ask. The plugin's `hooks/hooks.json` is made from its hooks, never kept as a second copy. `switchboard setup claude` merges the statusline and permissions (which a plugin can't carry) into the person's own `~/.claude/settings.json`, with the hooks only the old way and taking out the ones an earlier version added as a plugin; that file is never a link and stays theirs (Claude Code writes `/model` and "always allow" there), and a second run changes nothing (`tests/setup.rs`). A permission or hook taken out of the asset is not taken out of anyone's file. Moving between the plugin and `~/.claude` takes out exactly what Switchboard put there and nothing of the person's; a new build's first run never moves anything by itself. Claude Code reads only four settings files: `~/.claude/settings.json`, the project's `.claude/settings.json` and `.claude/settings.local.json`, and managed settings. Anything that describes a specific organization's environment, such as the auto mode profile (`autoMode`), belongs in that project's gitignored `.claude/settings.local.json`, never in a tracked file; the worktree commands link the main clone's into each worktree.

**Messages, menus and questions.** What a key or command has to say goes through `Server::say` (`src/ui/message.rs`; `switchboard say` from a script), which shows it in a box in the middle of the screen, or, with Settings' `message_boxes` off, as a line in the status bar; nothing says anything another way. Every menu, question and list looks one way, mission control's: a box drawn by `src/ui/draw.rs`'s `draw_box`, the chosen option on the highlight with a yellow `›`, the keys dim on a row of their own; a new one uses `src/ui/`'s menu, question and picker. What a part draws with UX 2.0 on (a state's mark, a section's label, a chip, a stage's cell, a key and what it does, a card, a list's chosen row, the keys on a footer or bar) comes from `src/ui/kit.rs`'s atoms rather than spans of its own, so one state has one mark and one color everywhere. Anything that takes a choice takes a click too (`menu_mouse`), lights under the mouse (`hover_highlight`), is a Tab stop (`tab_focus`), and gets easy mode's × (`easy_keys`), as the boxes there do. Every yes/no question takes Enter as yes and shows `[Y/n]`, and a closed input is always no, so nothing piped or unattended says yes. Text is measured with `ui::draw::width` (or `sidebar::text::width`), which counts what a terminal draws as two columns as two; one counted short shifts every border after it.

**Tips.** A tip is its text in `src/ui/tip.rs`'s `text_of` and a trigger calling `Server::tip`, shown once each in the top-right corner, its key passed on to what was under it; never in the status line, where one that goes on the next key press is missed. Doing what a tip teaches marks it shown.

**Keys and the palette.** A new key is an `Action` in `src/mux/keys.rs` (or a part's `Command`, with its `key()`), with `about()` and `tags()`: the palette lists every action by them, and an action no key is bound to by default is in `Action::palette_only`, listed with no key. The defaults are the keys tmux.conf bound. A new binding's tags say what it is about (`#git`, `#pr`, `#tabs`), and one that uses GitHub or Linear carries that service's tag.

**Links.** Every link Switchboard opens goes through `src/links.rs` (`open_url`), which opens it in the Chrome profile `browser.json` gives its site; anything new that opens a link does too.

**The request audit.** Every request to a service outside the computer is counted as it is made (`src/requests.rs`, a line a request in `~/.local/state/switchboard/requests/<day>.tsv`), for mission control's Usage view. `src/net.rs` counts every HTTPS request itself; anything else that reaches out (a `claude -p`, a git fetch, a connector) calls `requests::count(service, protocol, source)`.

**Claude's connectors.** `src/connector.rs` is the one way to reach a Claude connector: a headless Haiku allowed only the one tool, the answer taken from the tool's own result, never from what Haiku writes. A connector that isn't connected fails with `not_connected` and a message naming `/mcp`, and every call records its service's state for the views and the health light, so a feature that is on says where it shows that its connector is missing (`connector_down`) rather than failing quietly. A call nobody waits on goes through `call_in_background`, which while its connector is down asks `claude mcp get` (no model) at most every 15 minutes instead of running Haiku again. A view that is on is always in mission control, and before what it reads from is set up it says what is missing and how to set it up.

**Whether you're at the computer** is `src/presence.rs`'s, from `src/platform`; the Slack relay and the server each pick how long idle counts as away. Anything else that needs to know uses it too.

**macOS and Linux.** What differs goes through `src/platform/` (secrets, the clipboard, notifications, presence, opening a file or link), never a `cfg` of its own elsewhere. Crates are fine and system packages are not: pure-Rust crates (rustls, zbus), so a build needs rustup and a C compiler and a user needs nothing. No new external program but Claude Code and git, and the platform's own tools inside `src/platform/`.

**Files.** A file written whole goes through `util::write_atomic`, and JSON numbers through `util::js_number`, so files read as they did when Node wrote them.

**Tab names and colors.** A tab's color is hashed from a key `src/tabs/color.rs` builds, and `switchboard statusline` takes the same color from the same code, so Claude's statusline and the tab agree; the key's shape stays byte for byte as it is, since every project's color hangs on it, while the name the tab shows is free to change. The `#<number>` at the front of a tab's label is its PR, which `wt-jump` reads back, so it stays at the front.

**Notes stay on the computer.** Notes live in `$NOTES_DIR` or `~/Notes`, never in this repository, which is public. Nothing in a note is sent anywhere, with four exceptions, each one you start or turn on: squashing notes, after a yes; the `note-tickets`, `note-watch` and `plan-item` skills, which read only the notes you name or confirm (`plan-item` the tab's own note too) and are `disable-model-invocation`; today's todo note, off by default; and the tab's own note, which `switchboard claude-context` points each interactive session in the tab at by its path for Claude to read (`tab_note_context`, off by default), never passing its words itself. Anything new that reads a note keeps it that way. Only one notes app runs on a notes directory at a time (`.notes.lock`), and nothing writes a note but through the app's save, which merges in changes made from outside, with one exception: a note's stable ID, its last line (`src/notes/id.rs`), which the app writes as it opens a note that has none, and which `wtn` and autopilot give a note that has none, or give back to one rewritten without it, through `id::ensure_id` and `id::give_id` alone, one process at a time under the ID's lock and with the note's modified time kept, a change the app takes in as it takes in any made from outside. Whatever shows, searches or sends a note's words leaves its ID out (`id::strip`).

**The Slack relay answers to one person.** `src/relay/slack.rs` holds the rules every Slack call goes through: an incoming message is acted on only if `from_owner` (the owner named in `slack-relay.json`, in the app's DM, in that workspace, not a bot) and `typed_by_you` (Slack's `client_msg_id` and no `app_id`) pass, a button press only if `press_from` does, a form only if `submission_from` does, reactions control nothing, and `refuse` stops any call that names a conversation other than the DM. The owner never comes from a message.

**Trusted directories.** Nothing here runs code that another repository supplies unless you have trusted that repository. Trusted directories are listed in `~/.config/switchboard/trusted-dirs`, one absolute or `~/` path per line (blank lines and lines starting with `#` ignored), which is yours, never committed, and never written for you; a missing file trusts nothing. A directory counts only when its real path equals a listed one's exactly, so trusting `~/code` doesn't trust what is under it. `switchboard try` checks it before building a worktree whose code isn't yours, and `switchboard apply-actions` before offering to run a landed repository's install or migrate script, naming them for you to run in a clone not listed; anything new that would execute something from a repository checks this file the same way. `src/trust.rs` is the one place that decides whose code a directory holds (`listed`, `yours_or_listed`, `is_untrusted`, `trusted`); nothing keeps a notion of its own.

**Someone else's PR.** `wtpr` opens a fork's PR untrusted by default (`--untrusted` for any, `--trusted` to opt out): a worktree in `~/.cache/switchboard/pr-review/<owner>-<repo>/<n>`, on `pr-review/<n>` from the commits GitHub keeps for it, no remote added, with git's hooks, every filter your config names, the file-system monitor and submodule recursion off in its own worktree config, nothing linked and no Claude started. Such a worktree (in that folder, or marked `switchboard.untrusted` in its own worktree config, which no file in it can change) has its `CLAUDE.md`, `.claude/settings.json`, hooks and skills from its author, so anything that starts Claude in a worktree or lists worktrees to reopen leaves one alone (`trust::is_untrusted`, or on the server's task `trust::in_review_dir`, which reads the path alone): `claude-here`, `worktree-resume`, `worktree-from-branch`, `M-t`, `wt-revive`, the Work map and the Slack relay's places do, and a new one does the same. `skill-path` passes over its skills, so no PR can rewrite the review loop that reviews it, and a listing in `trusted-dirs` doesn't make it trusted (`trust::trusted`). `switchboard pr-risk` reads what it changes that runs without being asked from git alone, with no hook, textconv, external diff or file-system monitor, so a git command run on its worktree for a review passes `--text --no-textconv --no-ext-diff` the same way; `codex-review -C <worktree> --pr <n>` reviews it from the main clone, and `/review-loop` given its path does so reporting only. Its code runs only in `switchboard try --sealed`, every process of the try (the build with its `build.rs` and proc macros, the server and what it starts, every client) under macOS's `sandbox-exec`; the rules are `src/platform/sandbox.rs`'s, written into `~/.cache/switchboard/sealed/` on each run, where nothing in the try can change them, so a new place the try must read or write goes there, never a rule that opens your home. Nothing outside the sandbox writes in a sealed home once any of its code has run, its crates are fetched outside it only from crates.io with their checksums, and Linux, with no sandbox but one to install, has no sealed try.

## Skills

The skills that ship with Switchboard are in `assets/skills/`, compiled into the binary by `build.rs` and written into its plugin's `skills/` (`~/.local/share/switchboard/plugin`, by the server as it starts and `switchboard setup`), where the Claude in its panes finds them as `/switchboard:<name>` (and `/<name>` while nothing else has the name); with Settings' `claude_plugin` off, `switchboard setup skills` writes them into `~/.claude/skills` too, a skill of the person's own by the same name kept. A skill's scripts and shared files are named by their place in the plugin (`~/.local/share/switchboard/plugin/skills/<name>/...`), which is there either way, and its permission in `assets/claude-settings.json` names that path. Code that recognises a skill by its name (a loop's prompt, the Skill tool's input) takes `/switchboard:<name>` too (`plugin::bare`), while what Switchboard types into a tab stays the bare `/<name>`. They call the binary's commands (`switchboard codex-review`, `land-lock`, `wait-deploy`, `watch-note`, `respawn`, `tabs`, `setting`, ...), so a change to a command's flags or output belongs in the skills that use it, and the other way round: `review-loop` reads `codex-review`'s JSON (`tests/codex_review.rs`), `queue-and-clean` takes the landing lock through `land-lock` and checks the review's `patchId`, `/wt` and `/wtn` hand a tab over with `switchboard respawn`. `plan-item` (`/plan-item <what>`, and Notes' M-Enter in "Add an item") adds a checklist item to the tab's note and writes its plan note in the plans folder beside it, the shape `/wtn` and autopilot build from (`src/cmd/worktree_from_note.rs`'s `items` and `plan_of`), the item's first line its outcome in under 90 characters, since the branch, the worktree and the tab are named from it, so a change to that shape belongs in both (`tests/skill_path.rs`). A skill whose scripts need npm packages keeps them in its own `scripts/package.json`, pinned to exact versions with the lockfile beside it, its `node_modules` ignored, and says to run `npm ci` there when they are missing.

A repository may define its own skill by one of these names, and Claude Code may run Switchboard's over it (a personal skill over a project's, the plugin's when named), so every skill here starts by running `switchboard skill-path <name>`, which prints the repository's copy (the worktree's, then its main clone's), else Switchboard's own (the personal one when Switchboard wrote it or it is a copy of Switchboard's made the person's own, else the plugin's, never a skill of theirs that only shares the name), and follows the repository's when there is one; a skill that hands off to another reads the file `skill-path` prints rather than a fixed path, and, where it needs Switchboard's own text whatever copy is installed (`queue-and-clean` reading `ci-loop`'s "When queue-and-clean runs this"), the text `switchboard skill-path --own <name>` prints. That opening paragraph is worded the same in every skill, and `tests/skill_path.rs` checks it and the hand-offs, so a new skill gets it and a new hand-off goes through `skill-path`.

`.claude/skills/` holds Switchboard's own project skills, for working on this repository: Claude Code loads them only in sessions here and in its worktrees, and they aren't in `assets/skills/`, so the binary never carries them, `switchboard setup` never writes them and no user gets them; being the repository's own copy, they don't open with `skill-path`. `review-pr` is one, started as `/review-pr <pr>` or from `M-p`'s "Review a contributor's PR", which `src/cmd/work.rs` lists only in a repository with the skill: it reviews and tries someone else's PR without running its code outside the sealed try (`wtpr --untrusted`, `switchboard pr-risk`, `/review-loop` from outside the worktree, `switchboard try --sealed`) and drafts the review, so a change to those commands' flags or output belongs in it too.

## This repository's own tooling

`.githooks/pre-push` refuses a push to `main` that `/review-loop` hasn't found clean (below). It runs only where the clone's `core.hooksPath` points at its `.githooks` by its full path, so run `git config core.hooksPath "$PWD/.githooks"` at the top of every new clone, and once in a clone set up with the relative `.githooks` this once said. The full path because git reads a relative hooks path from the top of the worktree a command runs in: in a worktree on someone else's branch (a fork's PR opened `wtpr --trusted`) a relative one runs the hooks that branch carries, on your next checkout, commit or push there, where the full path runs the main clone's own; a worktree `wtpr --untrusted` makes has hooks off in its own config whatever this says. The hook asks `switchboard` (the one on the PATH, else the build of the clone the hook is in, never the worktree's) for the `review_before_push` setting and the reviewed patch.

This repository's `.claude/settings.json` runs `.claude/hooks/enforce-push-review.sh`, which refuses `git push --no-verify`, a push that names `hooksPath` and `switchboard setting review_before_push` with a value, and `.claude/hooks/enforce-git-hooks-run.sh`, which refuses `git commit --no-verify` (or `-n`) and any change to `core.hooksPath`, before every command, so they apply to any Claude working here and nowhere else. They read Claude Code's JSON with `jq`, which a clone working on Switchboard needs.

A release is a version bump on main: bump `Cargo.toml` in a commit of its own (`cargo check` updates `Cargo.lock`), and once that commit is on main `.github/workflows/release.yml`, finding no release of that version, builds it, tags it `v<version>` and publishes the release. So the bump's commit is the release: pushing or merging it publishes, and is asked about as the push to main it is. A tag `v<version>` pushed by hand to a commit whose `Cargo.toml` says the same still releases, and is a push, asked about as one.

## Pushing

Always ask before pushing this repo, every time, whatever the branch and whatever an earlier push was allowed, but for one case: a tab of autopilot with its "Land without asking" on (`@autopilot_land`), landing on main through queue-and-clean a commit that passed the tests, two clean review rounds (the pre-push hook's check) and `switchboard leak-check` with nothing found. Such a tab's Claude is started with that one command, `git push origin HEAD:main`, allowed for its session (`wtn`'s `push_rule`, Settings' `autopilot_push_rule`), so Claude Code's auto mode doesn't refuse it; the rule spares Claude Code's own judgment of that command (auto mode's, or its permission prompt in another mode), never the landing's question, which queue-and-clean still asks with "Land without asking" off. Review each commit as it is made: run `/review-loop` on it before starting the next, folding the round's fixes into that commit while it is unpushed, so each commit carries its own review rather than a pile of commits getting one loop and a batch of fixes at the end; working through a list, push each once it is clean, before the next. Before asking, run `/review-loop` on the unpushed commits, unless Settings' "Review before pushing" (`review_before_push`) is off, which the hook then follows too: `.githooks/pre-push` refuses a push to main whose tip isn't the commit the skill last found clean, or whose review started past where main is on the remote (both recorded in the clone's `review-loop-clean`, `git rev-parse --git-path review-loop-clean`, from `codex-review`'s `reviewedCommit` and `mergeBase`), so a fix made after the review needs a review of its own, and so does a commit the review left out. The one exception is the reviewed change rebased onto a newer main: a push of one commit, straight on main on the remote, whose change from main on the remote has the review's `patchId` (the third field, `switchboard codex-review --patch-id`, context lines included) and whose message is the reviewed commit's counts as reviewed. The skill offers to squash the loop's own commits before the push; a squash that leaves the tree exactly as reviewed records its new commit in their place, with the same base, and one that changes it records nothing. Claude can't skip it: this repository's `.claude/settings.json` refuses `git push --no-verify` and changing `core.hooksPath`, so it applies to any Claude working here and nowhere else. The repo is public, so before asking, check the unpushed commits for anything that identifies the user or their employer: organization or company names, ticket IDs, PR numbers, internal hosts, usernames, personal paths, tokens. `switchboard leak-check <range>` finds the kinds a script can (the words in `~/.config/switchboard/leak-check.txt`, never in this repository, ticket IDs, PR numbers, home paths, addresses, token shapes), and queue-and-clean runs it before every direct landing's push question; reading the diff by eye stays the second check.

A review loop here spends its rounds on what someone would hit in normal use. Start its notes file with this standing line, so the reviewer rates such findings low: `- Known gap: findings that need an unusual case (two events within the same moment, a terminal of unusual size or one resized mid-action, a name holding control characters or odd Unicode, permissions changed underneath, a signal sent by hand) are low here unless normal use hits them (the user's rule for this repository)`. Triage the same way: a medium of that kind is treated as low, so it is neither asked about nor fixed, outside a confirmation round as in it, and goes in the final report with the other lows. A fix that only closes one of them is not worth the round the reviewer then spends on the new code.

## Committing

Commit straight to `main`: there is no PR flow here, so a branch only adds a merge step. Each change gets a commit of its own, and nothing pushed is amended or reordered, since that rewrites public history and needs a force-push. A commit's message is a short subject line, a blank line, and a paragraph in prose on what changed and why.

Asked to squash unpushed commits, make one commit per feature, its message a description of the feature as it now stands, in prose, and keep other features' commits apart. Check the squashed commits' added lines and the new message for identifying details, as before a push (a real PR number in a test becomes 12345). Branch a `backup/pre-<what>` first, rebase with `--autostash`, and after the rebase check that the tree equals the backup's and that the tests pass at every rewritten commit, run in a temporary worktree.
