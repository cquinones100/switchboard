# Switchboard

Switchboard, called editor-configs until October 2026, is a terminal workspace for working with coding agents: one Rust binary, `switchboard`, that is its own terminal multiplexer with a server, and has the sidebar, mission control, the palette, the PR and ticket views, the diff viewer, the notes app and the Slack relay built in. `switchboard` alone starts the workspace or attaches to it; `switchboard <command>` runs everything else. It was a tmux setup with Node, shell and Lua scripts until the rewrite, which replaced every part and removed them; each module's opening comment names the files it came from, which git's history still has.

[README.md](README.md) is the front page for someone new (what it is, the requirements, installing, the first keys, the files of your own); [docs/guide.md](docs/guide.md) describes every feature, key and command; [ARCHITECTURE.md](ARCHITECTURE.md) describes the code, and ends with what the binary doesn't do yet. Keep all three in step with the code: a new or changed key (`src/mux/keys.rs`, a part's `Command`), command (`src/cmd/mod.rs`'s `COMMANDS`, `src/mux/commands.rs`), setting (`assets/settings.json`) or file of your own belongs in the guide, and the README's keys, requirements and install steps follow `keys.rs` and `install.sh`.

## Building and testing

The Rust is pinned in `rust-toolchain.toml` (`rustup toolchain install` in the clone). Before every commit:

- `cargo fmt`;
- `cargo clippy --all-targets`, with no warnings (CI runs it with `-D warnings`);
- off a Mac, `cargo check --no-default-features --target aarch64-apple-darwin` (`rustup target add aarch64-apple-darwin` once), which type-checks every macOS path from Linux, since the `net` feature holds the only C the build compiles. On a Mac, clippy already checks those paths, and a check naming the target would compile every crate again in a directory of its own.

The repository is a Cargo workspace whose `default-members` are every crate (`switchboard` at its root, and `crates/ui`, `crates/plugin-api`, `crates/diff` and `crates/notes`), so `cargo fmt`, `cargo clippy --all-targets` and `cargo test` cover them all with no flag, and `cargo build --release` still makes `target/release/switchboard`, with `switchboard-diff` and `switchboard-notes` beside it. `switchboard-ui` and `switchboard-plugin-api` take the workspace's version (`[workspace.package]`, Switchboard's); the diff and Notes each have their own.

Each worktree builds into its own `target/`, never one shared with another checkout: cargo keys the `switchboard` crate's own units without the checkout's path, so one worktree's build would count as fresh for another. With Settings' `worktree_clone_build` on (off by default), a new worktree's `target/` starts as a copy-on-write clone of the main clone's (`src/cmd/clone_build.rs`), still its own: cargo rebuilds the worktree's crates, whose sources are newer than the clone, and reuses the dependencies without a build script, which share the main clone's blocks until a build changes them; build scripts and their output aren't cloned, so those dependencies (aws-lc-sys's C among them) and the ones built on them build again. Beyond that, a computer with many worktrees may set sccache as cargo's `rustc-wrapper` in `~/.cargo/config.toml`, which serves the crates another worktree compiled.

Builds, test runs and package installs run in a pane go through the queue for heavy work (`src/slots.rs`; the `cargo`, `npm` and `pnpm` first on a pane's PATH are the binary, `src/cmd/slot.rs`), so only Settings' caps of each go at once across the tabs, and one may print "Waiting for a build slot" before it starts.

The tests run once per change, before it reaches `main`, not before every commit, since a full run starts thousands of processes on a computer with a security agent and the review loop's rounds would each run it again: a change lands through a PR ("Committing", below), and the PR's CI is its full test run, the six jobs `main` requires (Formatting, Clippy (Linux x86_64), Tests (Linux x86_64), Build the tests (macOS arm64), and Tests (macOS arm64) in two halves), which GitHub's auto-merge waits on. repos.json's `testIn`, `afterRebase` and the `ci/land-<id>` branch belong to a direct landing, straight on a default branch, which this repository doesn't make (`switchboard landing` prints `pr`): there, queue-and-clean runs the tests at the landing, in CI on a `ci/land-<id>` branch of its own with `testIn` `ci`, and runs `afterRebase` after a clean rebase in place of a second run. A build older than the skills it reads from the clone (`src/assets.rs`) stops a landing rather than working around a command it lacks: `switchboard skill-path` says on stderr which `switchboard` commands a skill's `allowed-tools` name that the build doesn't have (`cmd::SUBCOMMANDS` lists the subcommands it knows), and queue-and-clean stops there, as it does on any of its commands printing a usage line, so build and install from main and land again. The tests for the files a change touches are run while working on it (`cargo test --test it <file>::` for a file of `tests/it/`, `cargo test --test <file>` for one of the three apart from it, or a unit test's module), and the whole suite when a change reaches `tests/common`, the server's core or the protocol.

CI (`.github/workflows/ci.yml`) runs on every pull request, merged into main, and on a push to `main` only, so a PR's commit runs once rather than again on its branch alone; it runs fmt, clippy and the tests in parallel jobs on Linux, and on an Apple silicon Mac clippy and the tests' build in one job, whose archive two jobs then test half each (three macOS jobs a run, since the account runs few at once and the whole suite on one Mac was slow and timed out screen waits), the tests through cargo-nextest on 8 threads (the Linux job checks that nextest lists every test `cargo test` does); Intel Macs are built only by the release; each job's cache of the dependencies' builds is saved again whenever the toolchain, `Cargo.lock` or the profiles change. Each test binary links every crate, so the target directory is large: debug builds keep only line tables (the dependencies at opt-level 1, since the tests spend their time in alacritty_terminal and ratatui, and the crate's own code at 0, so its incremental builds stay quick), and a worktree's build should not leave extra copies of `target/` about.

Unit tests sit beside the code, in each crate. A crate under `crates/` is tested alone with `cargo test -p <its package>` (`switchboard-ui`, `switchboard-plugin-api`, `switchboard-diff` and `switchboard-notes`, each of the last two with a `tests/alone.rs` that runs its binary in a terminal of its own, a PTY, under a home made for the test, with no server; the notes app's unit tests are answered by a stand-in for the workspace, `host::tests::Stand`, so a test of what the workspace really answers goes in `src/notes/host.rs`, and one that needs the server's own code, as the sixel reader, in `src/notes/tests.rs`). The rest of this section is the `switchboard` crate's. Integration tests are in `tests/`: the files of `tests/it/` are modules of one binary (`tests/it/main.rs`), so cargo links one test binary rather than one a file, and a new test file is a module added there; the three that change the process's environment (`tests/day.rs`, `tests/integrations.rs`, `tests/update.rs`) are binaries of their own, since `set_var` would race the other tests' threads, and a new test that changes it is one too. `tests/common`, shared by all four, gives each test a server of its own in a temporary home under `/tmp` (short, since a Unix socket's path can't be over 104 bytes on macOS), commands run against it, and a client that reads what the server draws through a terminal emulator. A command the server runs (`mux::commands::NAMES`: `list`, `new-tab`, `press`, `set`, ...) is sent over the socket from the test's own process (`TestServer::run`, `ok` and `list`, through `socket::run_command_at`, from the test's temporary directory), never by running the binary, since a full run asks thousands and every process started is inspected on a computer with a security agent; a new test asks the same way, and runs the binary (`run_binary`, or `run` for a program of its own such as `setup`) only where the process is what it tests. Every wait in the tests is a deadline from `common::deadline`, its base times `common::patience()`, the one-minute load average over the cores as the wait starts (1 to 8, `SWITCHBOARD_TEST_PATIENCE=<n>` to set it by hand), so a busy computer makes a test slower rather than failed; a new wait, or a sleep for something with nothing to wait on, scales the same way. A wait is for what the next step needs, not for the first sign of it: a view to have its data (no "Loading…"), a menu its cursor rather than its label (which the view behind may show), a box to have closed before a command sent on its own connection, which can overtake a key sent on the client's. A test server starts with the day's notes and the Slack lookups off (`common::QUIET`), since a standup note made on a Monday shows in the sidebar, and `common::write_settings` writes a test's settings over them, so a test of one of them turns it on; it starts with the starter routines marked as made, so its routines are the test's own (`TestServer::start_with_starters` for a test of them). Services are stand-ins on 127.0.0.1 (`SWITCHBOARD_GITHUB_API`, `SWITCHBOARD_GITHUB_GRAPHQL`, `SWITCHBOARD_LINEAR_API`), from `tests/common/http.rs`, which is the demo's services (`src/demo/services.rs`) taken from the library, and `claude`, `gh`, Slack and the desktop's tools are stand-ins on the test's PATH. A test must never reach the real server, the real home or a real service, so a new one stays inside that setup: one that reads a tab's skills opens the tab in the test's temporary directory, since one in the repository would walk up to your real `~/.claude`.

## Testing in the workspace in use

The Switchboard you work in is the one in use, and the person may be typing in it. Before testing anything there (opening or closing a tab, moving focus, sending keys, `switchboard kill-server`, `switchboard upgrade` or restarting the server to load a new build), stop, say that the test needs the workspace and what it will do, and wait for a go-ahead. Test in a server of the tests' own where that can show the same thing.

To see a view without anyone's screen, run `switchboard demo --detached` (made-up data, nothing of the person's linked) or `switchboard try --detached`, and drive it with `switchboard headless` under the prefix it prints: `headless` prints a client's id (attached at `ui::layout::SIDE_BY_SIDE`, the narrowest size at which no view stacks its panes, unless `--size` names another), `headless-keys <id> <key>...` types into the whole workspace (mission control, the sidebar, the boxes), and `headless-screen <id> [--ansi | --png <file>]` reads all of it, which `capture-pane` can't; say before starting one, as for any test here. `switchboard demo --tour <dir>` saves every board that way. To show the person a change as a video, run `/walkthrough` on the demo, which records it from the worktree's build with captions and the keys pressed (its `scripts/record-terminal.js`), in a demo of its own under `/tmp` that needs no go-ahead.

To try a change by hand, use `switchboard try` (`src/cmd/try_.rs`, ported from bin/switchboard-try), which builds the worktree with cargo and runs it under a home of its own, `/tmp/sb-<hash>`, with its own settings, state, server and socket, after the build's own `switchboard setup plugin claude claude-md skills` has laid out its plugin there (the hooks, skills, instructions, statusline and permissions its panes' Claude loads; or, with `claude_plugin` off in the settings it copies, its hooks, statusline, permissions, CLAUDE.md and skills in its own `~/.claude`); its `~/.local/bin/switchboard` is the build, first on its PATH, so Claude Code's hooks in its panes reach the try's server. A Claude in the worktree uses `switchboard try --detached`, which starts the try's server with no client and prints the prefix that reaches it (`<prefix> send-keys`, `<prefix> capture-pane`, `<prefix> list`); `--print` prints the environment for a terminal of your own (`eval "$(switchboard try --print)"`, then `switchboard`); `switchboard try --clean` ends it and removes its home when done. It works because everything finds itself through `~`: a module that reaches for an absolute path of your real home breaks it, and a new state, config or cache location under `~` has to be sorted into what it links, copies or leaves fresh. Its settings turn off what would duplicate your real workspace (`TURNED_OFF`: the Slack look and view, the standup note, banners, the update check, restoring saved tabs, removing landed worktrees, with the todo note and meeting notes starter routines made paused). It isn't sealed off: it links your Keychain, dotfiles (`.ssh`, `.gitconfig`, shell history), the `~/.config` folders Switchboard doesn't configure (gh's sign-in among them), `~/.local/share`, Claude's plugins and sign-in, your own Claude hooks and skills, and the programs in `~/.local/bin` that aren't Switchboard's, so keys sent there act with your real credentials, and anything that would change one of those, push, or reach a service still waits for a go-ahead. It refuses a worktree holding someone else's code (a fork's PR, by `src/trust.rs`'s checks) until its path is in `trusted-dirs`, which is asked about first, and a PR `wtpr --untrusted` checked out always: that runs only with `--sealed` (`src/cmd/try_sealed.rs`), on macOS, under a sandbox that reaches none of what this paragraph says it links, in a home made from nothing. A build run with `SWITCHBOARD_STATE_DIR` set never brings its plugin, skills and settings into your home, as a new build attaching (`setup::refresh`) and its server starting otherwise do (`setup::state_of_its_own`).

A skill, Claude's settings or Switchboard's part of CLAUDE.md changed in the clone a build came from needs no rebuild: the build reads them from the clone (`src/assets.rs`), and its server brings the plugin and the parts set up up to date within 10 seconds of a change there. A running server keeps the binary it started with. A rebuilt `switchboard` reaches new commands and hooks at once, but the server only once it restarts: `switchboard upgrade` restarts it on the binary at the path it started from without ending anything (`src/mux/upgrade.rs`: the server execs the new build in its own process, handing it every pane's terminal, every attached terminal's connection and its socket), while `kill-server` ends every pane's program. A change to the protocol between them (`src/mux/proto.rs`, what `switchboard hook` sends) needs both. What a server hands over is `upgrade::Handover` and the pane's replay (`src/mux/replay.rs`): something new on a pane, a tab or a client that should survive an upgrade goes there, read with a default when it is missing, since the build reading the file is newer than the one that wrote it. A change a newer build couldn't take up from an older one's file bumps `upgrade::VERSION`, which the running server checks before it execs a build (`server --handover-version`), so it refuses that build rather than lose its panes.

When a change is ready to try, build it and put it in place of the binary the server runs without asking: `cargo build --release --locked`, then `install -m 755 target/release/switchboard ~/.local/bin/`, where the README and `install.sh` install it, both of which this repository's `.claude/settings.json` allows as these exact commands. When `command -v switchboard` names another path (`SWITCHBOARD_BIN_DIR`, or a binary put elsewhere on the PATH), install it there instead, which asks. With `CARGO_TARGET_DIR` (or cargo's `build.target-dir`) set, the build is that directory's `release/switchboard`, so install from there, which asks too. Work that lands through `/queue-and-clean` (a `/wtn` tab, autopilot) is ready to try once it has landed: build the landing target as it now is (the branch `switchboard landing` names), never the worktree before the landing, which would put code that hasn't landed into the binary the workspace runs. That is the commit the landing pushed (the target's branch on its remote, or the local branch when the target has none), not the local branch when it lags behind. Build it in the main clone when the main clone has the target checked out at that commit with nothing uncommitted (`git status --porcelain` printing nothing), as it normally does after the landing; otherwise in a detached worktree at that commit (`git worktree add --detach <dir> <commit>`), removed once the build is installed, whose install asks since it isn't the exact command allowed. Work tried before it lands, with no landing step, is built in the checkout it is in. Then say how to put it into the running workspace: `M-p`'s "Restart Switchboard on the latest main", which brings the main clone of the checkout the running binary was built from up to date with origin (refusing when it is off its default branch, has uncommitted changes or commits origin lacks) and builds it (a second, with nothing new; not at all when the build installed since the server started was made from that commit or one ahead of it), puts the result in place of the binary the server runs, and restarts the server on the path it started from, or, when that is in a cargo target directory, on `~/.local/bin/switchboard` or else the server's own copy in `~/.cache/switchboard/build`. Restarting it is still the person's to do, as above.

## Architecture

ARCHITECTURE.md has the whole picture; what follows is what a change has to keep.

**One task owns the server's state.** `src/mux/server.rs`'s `Server` holds the sessions, tabs, panes, clients and overlays, and everything else (client sockets, each pane's reader thread, timers, background lookups, file watches) sends it `Event`s. It handles them in order and draws the clients that changed, so nothing is shared or locked. Server state is touched only by that task: anything that reads the network, starts a process or reads more than a small file runs in a task of its own (or `spawn_blocking`) and answers with its part's event (`Event::Sources`, `Event::Day`, ...).

**Each part has the same shape**: modules that work on files and plain data, tested without a server, and a `serve.rs` whose `impl Server` puts them on the server: its keys, its share of the tick, the answers of its tasks. `src/lib.rs` lists the parts with a line each, and every module opens with a comment saying what it is and why it works as it does, naming the tmux-version file it was ported from; a new module does the same.

**Panes** are a PTY and an alacritty_terminal emulator each (`src/mux/pane.rs`). Every pane's environment carries `SWITCHBOARD` (the socket) and `SWITCHBOARD_PANE` (its id), which the commands and hooks use to reach the server and name their pane. Only the notes pane passes kitty's graphics commands to the terminal, and takes easy mode's Cmd keys (`src/mux/passthrough.rs`), since a graphics command can have the terminal read any file of yours. The server sends graphics commands of its own for the image atoms (`src/ui/images.rs`), the pictures `switchboard look` shows beside a narrow lone pane among them (`src/ui/pictures.rs`), always with the image's data inline (`t=d`), never a path.

**Apps in panes.** The views (`switchboard pr-view`, `ticket-view`, `link-view`, `view`), the diff (`switchboard diff`) and the notes app (`switchboard notes`) are programs of their own, drawn with ratatui and crossterm, which the server runs in a split or in a pane's place (the pane parked until the program ends, `src/diff/in_place.rs`). The server stays a multiplexer; each app is built and tested on its own. The diff and the notes app are crates of their own besides (below), which `switchboard diff` and `switchboard notes` load as plugins.

**The crates and the plugin boundary.** `switchboard`, the multiplexer and everything built into it, is the package at the workspace's root, and `crates/` holds what an app is built from without it. `crates/ui` (`switchboard-ui`) is what everything draws with (`kit`, `draw`, `text`, `field`, the themes and `Look`, `input`, Markdown, a terminal asked for its colors, and the boxes a program asks in: the `Overlay` trait with `message`, `confirm`, `menu` and `picker`), which `switchboard` gives at the paths it had (`ui::kit`, `ui::menu`, `mux::input`, `sidebar::text`, `status::theme`, `views::markdown`); an overlay draws into cells, and one that places the server's images takes the frame it is handed for the server's (`compose::Frame::of`), drawing nothing more into any other; it knows no settings file, so the few settings it follows are asked of the program (`switchboard_ui::settings`, which `settings::share_with_ui` answers as `cmd::run` starts), and a new one it reads goes in its `DEFAULTS` with the schema's default, which a test in `src/settings.rs` keeps the same. `crates/plugin-api` (`switchboard-plugin-api`) is everything a plugin and the workspace say to each other, as plain serde types under `PROTOCOL_VERSION`: a plugin's `Manifest`, the `Event`s it is told, the `Action`s it asks with their `Answer`s, `Host` (whoever answers) and `Plugin` (one loaded in process), `sdk`, the few helpers both sides need (`util` and `paths` give them from there), and `release` (its `release` feature), what a release is and how one is checked and put in place, which `src/update` and the diff's own update (`crates/diff/src/update.rs`) both run, so a change to how a release is verified is made there, once. `crates/diff` (`switchboard-diff`) is the diff, the first plugin and an app that runs alone: of the workspace's crates it depends on those two, never on `switchboard`, so the compiler holds the boundary, and it reaches the workspace only through the API (`crates/diff/src/host.rs`), which `src/diff/host.rs` answers from the modules that keep each rule (`settings`, `trust`, `integrations`, `requests`, `notes`). Something new the diff needs of the workspace is a new `Action` answered there, never a dependency on `switchboard` or a second copy of a rule; a type changed so that an older reader would misread it bumps `PROTOCOL_VERSION`, and a field added reads with a default. Each setting the diff reads is in its manifest with the schema's default, label and description, which a test in `src/diff/host.rs` keeps the same, and stays listed in `assets/settings.json`: Settings' rows are drawn from `assets/settings.json` and the diff's own settings view, alone (`crates/diff/src/app/own.rs`, M-m), from the manifest, so a new setting of the diff's is added to both with the same words. One only the workspace has a use for is marked `Scope::Workspace` and left out of that view; one that is the diff alone's (`diff_update_check`) is `Scope::Alone` and in no list of the workspace's. A plugin that runs an existing app (git, an editor, a pager) gives it its settings at launch, by flags or environment, and never edits that app's own config files, as "Other apps' configs" says. `crates/notes` (`switchboard-notes`) is the notes app, a plugin and an app that runs alone by the same rules: it depends on those two crates, never on `switchboard`, and reaches the workspace only through the API (`crates/notes/src/host.rs`), which `src/notes/host.rs` answers from the modules that keep each rule (`settings`, `platform`, `links`, `mux::graphics`, `tabs::title`, `autopilot`, `cmd::worktree_from_note`), handing what Notes shares with the diff on to `src/diff/host.rs`; `src/notes` keeps Notes on the server (`serve`) and gives the app's modules at the paths they had (`notes::store`, `notes::id`, `notes::render`), for the parts that read a note themselves. Alone (`switchboard-notes`, its `host::Alone`), what needs a workspace is left out rather than done another way: no tab's note or tab to go to, no work started on an item, no link opened, no pictures, since which browser a site opens in and how a picture reaches a terminal are rules kept in one place. Alone (the `switchboard-diff` binary, `host::Alone`), the diff answers for the workspace itself: no server, no pull request to take a base from (the default branch, or the branch its own tracks), `claude -p` directly, its own folders (`~/.local/state/switchboard-diff`, `~/.cache/switchboard-diff`), and no notion of whose code a directory holds, which stays `src/trust.rs`'s. Alone it has a header line, a Settings button and a settings view of its own, which writes a settings file of its own, `~/.config/switchboard-diff/settings.json` (`host::write_setting`), since the diff alone knows nothing of Switchboard and reads none of its files, a look for a newer release once a day and `switchboard-diff update`; in the workspace none of those are there (`host::is_alone`), the workspace having its own. Its HTTPS client is its `net` feature, which `switchboard` depends on it without, so the build's only C stays behind the `net` features.

**Commands.** What scripts and skills ask of the workspace (list the tabs, open one, send keys, read a pane's screen, set an option, say something) is a server command in `src/mux/commands.rs`, sent over the socket; a program of its own goes in `src/cmd/` and `COMMANDS`. A link to the binary named after a command runs it too.

**Claude's state.** Claude Code's hooks (`assets/claude-settings.json`'s) run `switchboard hook <Event>`, which sends the hook's JSON and `SWITCHBOARD_PANE` to the server (`src/agent/`). They reach Claude as Switchboard's plugin (`src/setup/plugin.rs`, `~/.local/share/switchboard/claude/plugin`: the hooks, a SessionStart hook running `switchboard claude-context` for `assets/switchboard.md`, and the skills), which every pane names in `CLAUDE_CODE_PLUGIN_DIRS` while Settings' `claude_plugin` is on, so only the Claude in Switchboard's panes loads it; with it off, `switchboard setup` puts them in `~/.claude` as before (`src/setup/way.rs` decides which, and keeps the setting and `~/.claude` agreeing, since both at once would run each hook twice). A `claude -p` Switchboard starts for itself goes through `plugin::headless`, which takes the plugin out of the variable, and `claude-context` says nothing to a headless session. Claude Code waits on its hooks and runs them before and after every tool call, and adds some hooks' output to the conversation, so `switchboard hook` prints nothing, waits at most a second, and always exits 0; the one exception is autopilot's hands-free mode (`src/agent/hands_free.rs`), where the server answers PreToolUse for `AskUserQuestion` and Stop in a marked tab with the JSON Claude Code reads (a deny, a block), which the hook prints as it came. A tab holds one Claude: the sidebar, mission control, the Slack relay, `M-c` and the PR view's /resolve-conflicts each take a tab's Claude to be one pane.

**Persistence.** The layout and tab options are saved as they change and restored when a server starts with none (`src/mux/persist.rs`); a new tab or pane option that should outlive a restart is saved there.

**Where things live.** Your own files in `~/.config/switchboard/`; Switchboard's state in `~/.local/state/switchboard/` (`SWITCHBOARD_STATE_DIR` moves it), the notifications' history among it (`notifications/`, a file a day); caches in `~/.cache/switchboard/` (and `wt-revive`'s in `~/.cache/wt-revive/`); what setup writes for Claude Code (the plugin `claude/plugin/`, `switchboard.md` the old way, the rules' clone `claude-md/`, `setup-build`) in `~/.local/share/switchboard/`; the Slack relay's state in `~/.local/state/slack-relay/`, and `/oncall`'s in `~/.local/state/oncall/`. Everything finds itself through `~` (`src/paths.rs`), so a test or a try can give a run a home of its own: a script or module that reaches for an absolute path of your real home breaks that. What the binary carries (the settings schema, Claude's settings, Switchboard's part of CLAUDE.md, the skills) is in `assets/`, compiled in, so the binary needs no clone; a build from a clone reads the clone's copy first while it is there (`src/assets.rs`, Settings' `assets_from_checkout`), so code reaches an asset through `assets::text`, `assets::json` or `assets::skills` rather than the compiled constant.

## Rules the code keeps

**Nothing on the drawing path waits or starts a process.** Naming the tabs, the status line, the sidebar and mission control run on every focus, tick or draw, and a security agent on the computer this was written on inspects every process that starts, which once made the workspace sluggish. So they read what the server already holds: a directory's branch from git's own files (`src/tabs/git.rs`), not by running git; a PR, a ticket's title or a view's data from what a background lookup last answered, shown once it is known and kept while a look fails. A process is read only while a view that shows it is in front (the Resources view). A lookup that is due while the same one still waits is skipped (`src/sources/schedule.rs`), and the lookups pause while you're away (`pause_when_away`). Anything new that wants to add to a tab, the sidebar or a card follows the same rule.

**Settings.** Every option is in `assets/settings.json`, with its key, category, label, description and default (on/off, or one of its `choices`); what someone changes is kept in `~/.config/switchboard/settings.json`, only the keys that differ from their defaults, which they may also edit by hand. `src/settings.rs` reads it (`settings::is_on`, `settings::setting`) and writes it (`write_setting`), never over a file it can't read as a JSON object, keeping the version before as `settings.json.bak`; the server reads it again whenever it changes. A new option is one entry there and the code that reads it; its description says what it does now, and what turning it off does. An option of one mission control view goes in that view's category, `Mission control: <view>`, after the view's on/off switch, which leads it: a category named `group: name` is drawn under its group's heading in Settings (`settings::categories`), and "Mission control" itself keeps only what belongs to every view. Every new feature gets one, on by default unless it sends something of yours somewhere (as the todo note routine sends your notes' items to Claude), so each part can be turned off for a plain workspace: a view, a sidebar block, a background check, a key that changes what an existing one does. A new view with a setting goes in `src/usage/habits.rs`'s `VIEWS`, and a feature worth suggesting in `TRIES`.

**GitHub and Linear.** The `github` and `linear` settings turn off what the workspace does with each service by itself: its lookups, views and keys. Anything that reaches them goes through `src/integrations/`, which refuses while its setting is off, except in a program you run yourself (`codex-review`, `wt`, `wtpr`, `wait-ci`, `wait-deploy`, `wt-jump`, `worktree-done`), which calls `integrations::run_by_you` first, since the tmux version's scripts never read the settings; a key or palette command that uses one carries its `#github` or `#linear` tag, which takes it out of the palette and makes its key say the service is off.

**The user layer.** Every file of someone's own lives in `~/.config/switchboard/` (or, with Settings' `files_from_repo` on and `files.json` naming a git repository, in the folder of its clone under `~/.local/share/switchboard/files`, which `src/files` pulls, and pushes as it changes, after `leak-check` and a question about anything it finds), never in this repository, and nothing writes over one but Settings: `settings.json`, `keys.json` (bindings over the defaults), `sidebar.json` and `sidebar-plugins/`, `browser.json`, `linear.json`, `claude.json` and `CLAUDE.md`, `slack-updates.json`, `slack-relay.json`, `oncall.json` and `oncall-rules.md`, `repos.json`, `files.json`, `leak-check.txt`, `trusted-dirs`, `autopilot-claim.json`, and `secrets.json` where Linux has no keyring. Code reaches one through `paths::config_dir()`, which is the clone's folder while the files come from a repository, never a path of its own; `files.json`, `trusted-dirs`, `repos.json`, `sidebar-plugins/`, `slack-relay.json`, `linear.json`, `oncall.json`, `oncall-rules.md`, `slack-updates.json`, `autopilot-claim.json` (autopilot's claim ID, each computer's own), `secrets.json`, `leak-check.txt`, the `.bak` copies and the `files_from_repo` setting itself (`files::LOCAL`, `settings::LOCAL`) never leave the computer, so they are read through `paths::local_config_dir()` (or `files::file`), and a new file that decides what code runs with no one asked, names who Switchboard answers to, holds a secret or is read by a skill by its path goes there too. Each setting in one has a row in mission control's Settings view, from `OWN_FILES` in `src/usage/own.rs`, so a new setting in a file there, or a new file, gets an entry there and a row in the README's and the guide's tables. No one's own rules live here: what every user's Claude needs to know about the workspace goes in `assets/switchboard.md`, which `switchboard setup` imports into `~/.claude/CLAUDE.md`.

**Claude Code's settings.** `assets/claude-settings.json` is Switchboard's part: the hooks, the statusline (`switchboard statusline`) and the permissions its skills and loops need to run unattended (their `switchboard` commands, read-only git and gh, the read-only connector tools); anything that writes outside the computer is left to ask. A rule allows only a command whose words are written out in it, never a wildcard over a command whose options could run code or write a file of Claude's choosing: no skill script is allowed (each takes a path or a file Claude writes), no `git log` or `git diff` (Claude Code runs git's read-only forms itself, by its own checks), `git fetch` only bare or from `origin`, and the options that make git write a file, run a program or fetch from an address of its choosing (`--output`, `--ext-diff`, `--upload-pack`, `--multiple`) are denied besides, by the asset and the plugin's permissions module, against a rule of the person's own. The plugin's `hooks/hooks.json` is made from its hooks, and its statusline (`hooks/statusline.js`, a `settings.read` hook of the plugin's hooks module that layers the statusline over the settings Claude Code merged, in memory) from its statusline, never kept as a second copy. As a plugin, nothing of Switchboard's goes in the person's own `~/.claude/settings.json`: `switchboard setup claude` only takes out the hooks and statusline an earlier version added there (the permissions it added stay, since a rule it added can't be told from the same rule of the person's, which Claude Code's "always allow" writes, except the allow rules Switchboard dropped, `RETIRED_RULES` in `src/setup/claude_settings.rs`, which either way are taken out as written); the old way it merges the hooks, statusline and permissions in; that file is never a link and stays theirs (Claude Code writes `/model` and "always allow" there), and a second run changes nothing (`tests/it/setup.rs`). As a plugin, the permissions reach its panes' Claude through Claude Code's own permission decision, never a file (`src/setup/permissions.rs`): each skill carries the asset's rules for what it and the skills it reads and follows name, in its `allowed-tools` front matter, which `permissions.rs`'s tests check, so a skill that starts running a command adds its rule to the asset and to its own list; and the plugin's hooks module (`hooks/switchboard.js`, the one Claude Code runs a plugin, which imports `hooks/statusline.js` and `hooks/permissions.js`) has a `tool.check` hook, from `src/setup/permissions.js`, that allows the asset's `switchboard` commands that `assets/switchboard.md` names, alone and only where Claude Code's verdict is the plain ask no rule, hook, check or limit decided, and refuses what the asset's deny rules name, Settings' `pane_permissions` off leaving both to Claude Code. A permission or hook taken out of the asset is not taken out of anyone's file, unless an allow rule that let Claude do more than it should goes in `RETIRED_RULES` too. Moving between the plugin and `~/.claude` takes out exactly what Switchboard put there and nothing of the person's; a new build's first run never moves anything by itself. Claude Code reads only four settings files: `~/.claude/settings.json`, the project's `.claude/settings.json` and `.claude/settings.local.json`, and managed settings. Anything that describes a specific organization's environment, such as the auto mode profile (`autoMode`), belongs in that project's gitignored `.claude/settings.local.json`, never in a tracked file; the worktree commands link the main clone's into each worktree.

**Messages, menus and questions.** What a key or command has to say goes through `Server::say` (`crates/ui/src/message.rs`; `switchboard say` from a script), which shows it in a box in the middle of the screen, or, with Settings' `message_boxes` off, as a line in the status bar; nothing says anything another way. Every menu, question and list looks one way, mission control's: a box drawn by `crates/ui/src/draw.rs`'s `draw_box`, the chosen option on the highlight with a yellow `›`, the keys dim on a row of their own (but M-F's search box, which board 78 draws with no keys, so its results get the room); a new one uses `src/ui/`'s menu, question and picker, so `/` searches it as it searches every menu (a box with a list of its own, such as the answer box and Notes' Format menu, takes `ui::menu::Filter`). What a part draws with UX 2.0 on (a state's mark, a section's label, a chip, a stage's cell, a key and what it does, a card, a list's chosen row, the keys on a footer or bar) comes from `crates/ui/src/kit.rs`'s atoms rather than spans of its own, so one state has one mark and one color everywhere. A row is laid out with `kit::columns` (fixed, stretching and right-edge columns, dropped in the view's order), never at a board's own offsets, so a view fills any width as UX 2.0 board 45 says. Anything that takes a choice takes a click too (`menu_mouse`), lights under the mouse (`hover_highlight`), is reached by Tab (`tab_focus`: in mission control Tab moves a section at a time, wrapping, through `Mission::sections` and the view's panes, a section's rows reached with `j` and `k`), and gets easy mode's × (`easy_keys`), as the boxes there do. A notification's menu is its item's menu in the view it came from, built by `choices::notice_choices` from that view's `item_choices` with dismissing added, so a new kind of notification names its view in `notices::view_of` (or, when no view lists it as an item, goes in `notices::NO_VIEW` with what it leads to in `choices::notice_leads`) and lists no choices of its own, and a choice added to a view's menu reaches its notifications by itself. Every yes/no question takes Enter as yes and shows `[Y/n]`, and a closed input is always no, so nothing piped or unattended says yes. A pane beside a board scrolls with `J` and `K` and the wheel over it, and resizes with the pane resize keys and a drag of its edge, through `About::window` and `side_width` (`src/mission/render.rs`), so a new pane does too. A sidebar resizes the same way while Settings' `sidebar_resize` is on, by a drag of its edge and the pane resize keys while it has the keys, its width kept and "Use the default width" in its menu clearing it: the workspace's, with mission control's list of views in its place (`Session::sidebar_width`, saved with the layout). Text is measured with `ui::draw::width` (or `sidebar::text::width`), which counts what a terminal draws as two columns as two; one counted short shifts every border after it.

**Keyboard first, mouse complete.** Everything the mouse does, a key does too, a menu a right click opens included; nothing is the mouse's alone. Everything a key does, a click does too, on something drawn that lights under the mouse and is reached by Tab. In every mission control view, Enter (and Space, and a click on an item) opens the chosen item's menu, what Enter did by itself before being its first option, chosen as it opens, and `m` opens the view's own menu; a view has no keys of its own that act on an item, only moving (`j`/`k`, `h`/`l`, `H`/`L`, Tab, and `C-w` and a direction between a view's panes, as Vim's windows), `/` to filter and mission control's own keys stay keys, and an action is an option of a menu. A right click on an item opens what Enter opens, on a view's background what `m` opens; `m` in the sidebar and `S-F10` anywhere open the menu a right click on what is chosen would. A menu or box a click opens appears beside the click (`Place::Near`), one a key opens in the middle, or, for a box about the tab in front (`Server::about_tab`: its links, renaming it, answering its Claude, its menu), as a pane in the empty columns beside a narrow lone pane when it fits there (`Look::middle`). Every mission control view is listed in `M-p`, and every action a view has is an option of one of its menus.

**One look per thing.** A card, a board of columns, a person's avatar, a chip, a meter or a mark is drawn by its one atom in `crates/ui/src/kit.rs` (`kit::board`, `kit::avatar` and the rest), never by a view's copy of it, so Slack's, Linear's and GitHub's people look alike and every board the same. The pane with the keys is drawn at full strength and every other pane greyed, through `kit::unfocused` over the pane's cells once it is drawn, the look a tab's pane without the focus has: mission control's panes and its list of views (`Mission::without_keys`, which finds a view's panes by the hit boxes it drew, a pane beside by its `Spot::Side` rows, and among several views at once the views without the focus by their `Spot::Cell` rows), Notes' list, note and plan; a new view with panes does the same, and gives a pane beside its `Spot::Side` rows. The one exception is a pane that shows what the pane with the keys has chosen, a list's preview, which is not greyed, since it is what is being read from the list: the diff, which greys neither its list (or the Story view's outline) nor its file, whichever has the keys, so the side the reader steps through stays as readable; a mission control view's pane beside while its list has the keys and its list while the panel over it (Settings' categories, Slack's sections) does (`Mission::previews`); and Notes' plan while the note has the keys and its cursor is in the plan's item. A change to what something looks like is drawn first as a board in `docs/design/src/` (the UX 2.0 canvas, where the boards started, is kept as a read-only archive), published with `/design-docs` and reviewed on the site, and its item waits under its plan's "Decision needed" until the drawing is approved; the plan names the boards it follows by number, in that option too, so autopilot holds the item, and hands-free never decides it (`Plan::Review`).

**Tips.** A tip is its text in `src/ui/tip.rs`'s `text_of` and a trigger calling `Server::tip`, shown once each in the top-right corner, its key passed on to what was under it; never in the status line, where one that goes on the next key press is missed. Doing what a tip teaches marks it shown.

**Keys and the palette.** A new key is an `Action` in `src/mux/keys.rs` (or a part's `Command`, with its `key()`), with `about()` and `tags()`: the palette lists every action by them, and an action no key is bound to by default is in `Action::palette_only`, listed with no key. The defaults are the keys tmux.conf bound. A new binding's tags say what it is about (`#git`, `#pr`, `#tabs`), and one that uses GitHub or Linear carries that service's tag.

**Links.** Every link Switchboard opens goes through `src/links.rs`, which opens it in the Chrome profile `browser.json` gives its site and says where it is going until the browser comes to the front, since a profile's Chrome can take seconds to start: on the server through `Server::open_link` (src/views/serve.rs), in an app in a pane on its own message line with `links::opening_words`. `tests/it/links.rs` fails when any other file calls `links::open_url`, `open_url_as` or `open_in_background`, so anything new that opens a link goes through `Server::open_link` or says the words itself.

**The request audit.** Every request to a service outside the computer is counted as it is made (`src/requests.rs`, a line a request in `~/.local/state/switchboard/requests/<day>.tsv`), for mission control's Usage view. `src/net.rs` counts every HTTPS request itself; anything else that reaches out (a `claude -p`, a git fetch, a connector) calls `requests::count(service, protocol, source)`.

**Claude's connectors.** `src/connector.rs` is the one way to reach a Claude connector: a headless Haiku allowed only the one tool, the answer taken from the tool's own result, never from what Haiku writes. A connector that isn't connected fails with `not_connected` and a message naming `/mcp`, and every call records its service's state for the views and the health light, so a feature that is on says where it shows that its connector is missing (`connector_down`) rather than failing quietly. A call nobody waits on goes through `call_in_background`, which while its connector is down asks `claude mcp get` (no model) at most every 15 minutes instead of running Haiku again. A view that is on is always in mission control, and before what it reads from is set up it says what is missing and how to set it up. The Slack view reaches Slack through the connector, and directly, with a user token of your own (`src/day/slack_user.rs`, stored by `switchboard setup slack-user` as a secret and read only off the server's task), for the two things the connector can't do: your reminders and marking what you open read in Slack. With that token stored and Settings' `slack_token_reads` on, its reads (the look, threads, files, search everything's Slack results) go through Slack's Web API with it too (`src/day/slack_api.rs`), each falling back to the connector when Slack refuses it; with none, they go through the connector. Anything else it needs of Slack goes through the connector, and anything that changes your state in Slack is off by default or asks first.

**Whether you're at the computer** is `src/presence.rs`'s, from `src/platform`; the Slack relay and the server each pick how long idle counts as away. Anything else that needs to know uses it too.

**macOS and Linux.** What differs goes through `src/platform/` (secrets, the clipboard, notifications, presence, opening a file or link), never a `cfg` of its own elsewhere. Crates are fine and system packages are not: pure-Rust crates (rustls, zbus), so a build needs rustup and a C compiler and a user needs nothing. No new external program but Claude Code and git, and the platform's own tools inside `src/platform/`.

**Other apps' configs.** An app Switchboard runs gets Switchboard's settings at launch, by flags or environment, never by changing its config files: lazygit in a pane's place is given `LG_CONFIG_FILE` naming Switchboard's copy and then your config, so yours wins (`src/setup/lazygit.rs`), and a plugin follows the same rule.

**Files.** A file written whole goes through `util::write_atomic`, and JSON numbers through `util::js_number`, so files read as they did when Node wrote them.

**Tab names and colors.** A tab's hue is its own, chosen as it opens to stand apart from the open tabs' (in one of two lightness steps) and kept with the layout (`@tab_hue`, `@tab_step`), and `switchboard statusline` asks the server for it, so Claude's statusline and the tab agree; the hash of a key `src/tabs/color.rs` builds is only the tie-break, a lone tab's color, the color with Settings' `tab_colors_apart` off, and the statusline's outside the workspace; Settings' `tab_colors` picks how the hue is drawn (soft or vivid), never the key or the hue; the key's shape stays byte for byte as it is, since every project's color hangs on it, while the name the tab shows is free to change. The `#<number>` at the front of a tab's label is its PR, which `wt-jump` reads back, so it stays at the front.

**Notes stay on the computer.** Notes live in `$NOTES_DIR` or `~/Notes`, never in this repository, which is public. Nothing in a note is sent anywhere, with six exceptions, each one you start or turn on: squashing notes, after a yes; the `note-tickets`, `note-watch` and `shape` skills, which read only the notes you name or confirm (`shape` the tab's own note too, for a note's item), all three `disable-model-invocation`; the Today's todo note routine, paused unless you turn it on; the tab's own note, which `switchboard claude-context` points each interactive session in the tab at by its path for Claude to read (`tab_note_context`, off by default), never passing its words itself; the tab's plan note, which M-d's story gives Haiku as its context (`diff_story_plan`, off by default); and the `diff-artifact` skill, which publishes the story and the diff as a private Claude artifact, a story drawn from the plan reaching it only after the skill shows the plan's words it found in the page and you say yes. Anything new that reads a note keeps it that way. Each note is open for editing in one notes app at a time: with an app in each tab (`notes_per_tab`), the app with a note open holds its lock (`.locks/<note id>`, `Store::lock_note`) and another shows it read-only, and with the setting off one app runs on a notes directory at a time (`.notes.lock`); `.notes.json` is written through `Store::update_meta`, a read-merge-write under a lock of a moment. Nothing writes a note but through the app's save, which merges in changes made from outside, with three exceptions: a note's stable ID, its last line (`crates/notes/src/id.rs`), which the app writes as it opens a note that has none, and which `wtn` and autopilot give a note that has none, or give back to one rewritten without it, through `id::ensure_id` and `id::give_id` alone, one process at a time under the ID's lock and with the note's modified time kept, a change the app takes in as it takes in any made from outside; the server's `Decided hands-free` lines for a hands-free tab's question box, at the end of its item's plan note or under the item in its note, written off its task through `id::rewrite` alone (`src/agent/hands_free.rs`), under the same lock and with the modified time kept; and `switchboard item-done`, which ticks the item a landed worktree's branch was started for and writes its `Done:` line under it (`format::toggle_check` on the file's text), under the same lock, its modified time changing as any edit's does so autopilot sees the tick, a change the app takes in the same way. Whatever shows, searches or sends a note's words leaves its ID out (`id::strip`).

**The Slack relay answers to one person.** `src/relay/slack.rs` holds the rules every Slack call goes through: an incoming message is acted on only if `from_owner` (the owner named in `slack-relay.json`, in the app's DM, in that workspace, not a bot) and `typed_by_you` (Slack's `client_msg_id` and no `app_id`) pass, a button press only if `press_from` does, a form only if `submission_from` does, reactions control nothing, and `refuse` stops any call that names a conversation other than the DM. The owner never comes from a message.

**Trusted directories.** Nothing here runs code that another repository supplies unless you have trusted that repository. Trusted directories are listed in `~/.config/switchboard/trusted-dirs`, one absolute or `~/` path per line (blank lines and lines starting with `#` ignored), which is yours, never committed, and never written for you; a missing file trusts nothing. A directory counts only when its real path equals a listed one's exactly, so trusting `~/code` doesn't trust what is under it. `switchboard try` and `switchboard apply install` (for `~/switchboard` too) check it before building a worktree whose code isn't yours, `wt` and `wtb` before starting Claude on a branch with someone else's commits beyond the default branch (`trust::branch_yours_or_listed`, or `--trusted`), and `switchboard apply-actions` before offering to run a landed repository's install or migrate script, naming them for you to run in a clone not listed; anything new that would execute something from a repository checks this file the same way. `src/trust.rs` is the one place that decides whose code a directory holds (`listed`, `yours_or_listed`, `branch_yours_or_listed`, `is_untrusted`, `trusted`); nothing keeps a notion of its own.

**Someone else's PR.** `wtpr` opens a fork's PR, and a same-repository PR with a commit beyond the default branch someone else wrote, a stacked PR's base included (`trust::others_on`), untrusted by default (`--untrusted` for any, `--trusted` to opt out): a worktree in `~/.cache/switchboard/pr-review/<owner>-<repo>/<n>`, on `pr-review/<n>` from the commits GitHub keeps for it, no remote added, with git's hooks, every filter your config names, the file-system monitor and submodule recursion off in its own worktree config, nothing linked and no Claude started. Such a worktree (in that folder, or marked `switchboard.untrusted` in its own worktree config, which no file in it can change) has its `CLAUDE.md`, `.claude/settings.json`, hooks and skills from its author, so anything that starts Claude in a worktree or lists worktrees to reopen leaves one alone (`trust::is_untrusted`, or on the server's task `trust::in_review_dir`, which reads the path alone): `claude-here`, `worktree-resume`, `worktree-from-branch`, `M-t`, `wt-revive`, Reopen's worktrees and the Slack relay's places do, and a new one does the same. `skill-path` passes over its skills, so no PR can rewrite the review loop that reviews it, and a listing in `trusted-dirs` doesn't make it trusted (`trust::trusted`). `switchboard pr-risk` reads what it changes that runs without being asked from git alone, with no hook, textconv, external diff or file-system monitor, so a git command run on its worktree for a review passes `--text --no-textconv --no-ext-diff` the same way; `codex-review -C <worktree> --pr <n>` reviews it from the main clone, and `/review-loop` given its path does so reporting only. `M-p`'s "Review a contributor's PR" checks it out before opening its tab, whose Claude runs from the main clone while the tab follows the worktree through its `@tab_dir` option (`Server::pane_dir`, which names the tab and points the views and the diff there, never where a program starts, `pane_own_dir`), and lazygit is refused in it; the diff passes `--text` there. Its code runs only in `switchboard try --sealed`, every process of the try (the build with its `build.rs` and proc macros, the server and what it starts, every client) under macOS's `sandbox-exec`; the rules are `src/platform/sandbox.rs`'s, written into `~/.cache/switchboard/sealed/` on each run, where nothing in the try can change them, so a new place the try must read or write goes there, never a rule that opens your home. Nothing outside the sandbox writes in a sealed home once any of its code has run, its crates are fetched outside it only from crates.io with their checksums (a dependency may have a path only to another package of the same workspace, a folder inside the worktree by its real path, as Switchboard's own crates are, `try_sealed::packages_problem`), from a folder outside your home with no rustc wrapper, so none of your cargo config applies (the build inside sets no wrapper either), and Linux, with no sandbox but one to install, has no sealed try.

## Skills

The skills that ship with Switchboard are in `assets/skills/`, compiled into the binary by `build.rs` (a build from a clone reading the clone's `assets/skills` first, `src/assets.rs`) and written into its plugin's `skills/` (`~/.local/share/switchboard/claude/plugin`, by the server as it starts and `switchboard setup`), where the Claude in its panes finds them as `/switchboard:<name>` (and `/<name>` while nothing else has the name); with Settings' `claude_plugin` off, `switchboard setup skills` writes them into `~/.claude/skills` too, a skill of the person's own by the same name kept. A skill's scripts and shared files are named by their place in the plugin (`~/.local/share/switchboard/claude/plugin/skills/<name>/...`), which is there either way, and its permission in `assets/claude-settings.json`, and in the `allowed-tools` of each skill that runs one, names that path. Code that recognises a skill by its name (a loop's prompt, the Skill tool's input) takes `/switchboard:<name>` too (`plugin::bare`), while what Switchboard types into a tab stays the bare `/<name>`. They call the binary's commands (`switchboard codex-review`, `land-lock`, `wait-deploy`, `watch-note`, `respawn`, `tabs`, `setting`, ...), so a change to a command's flags or output belongs in the skills that use it, and the other way round: `review-loop` reads `codex-review`'s JSON (`tests/it/codex_review.rs`), `queue-and-clean` takes the landing lock through `land-lock` and checks the review's `patchId`, `/wt` and `/wtn` hand a tab over with `switchboard respawn`. `shape` (`/shape [--notes | --github | --linear] <what>`) files new work where the repository keeps it, `switchboard tickets` printing repos.json's `tickets` (`github`, `linear`, or `notes`; Linear when unset), a GitHub issue only after `switchboard leak-check --file` on it and a yes. For `notes` (and Notes' M-Enter in "Add an item", which runs `/shape --notes`), it adds a checklist item to the tab's note and writes its plan note in the plans folder beside it, the shape `/wtn` and autopilot build from (`src/cmd/worktree_from_note.rs`'s `items` and `plan_of`; autopilot takes the repository's GitHub issues too, `src/autopilot/issues.rs`, started by `wtn --issue`), the item's first line its title in under 90 characters, `BUG: ` and what is broken or `FEAT: ` and what to build, since the branch, the worktree and the tab are named from it, and an `After: <first line>` line under it for each open item it builds on, which holds it until that item is ticked, so a change to that shape belongs in both (`tests/it/skill_path.rs`). A skill whose scripts need npm packages keeps them in its own `scripts/package.json`, pinned to exact versions with the lockfile beside it, its `node_modules` ignored, and says to run `npm ci` there when they are missing.

A repository may define its own skill by one of these names, and Claude Code may run Switchboard's over it (a personal skill over a project's, the plugin's when named), so every skill here starts by running `switchboard skill-path <name>`, which prints the repository's copy (the worktree's, then its main clone's), else Switchboard's own (the personal one when Switchboard wrote it or it is a copy of Switchboard's made the person's own, else the plugin's, never a skill of theirs that only shares the name), and follows the repository's when there is one; a skill that hands off to another reads the file `skill-path` prints rather than a fixed path, and, where it needs Switchboard's own text whatever copy is installed (`queue-and-clean` reading `ci-loop`'s "When queue-and-clean runs this"), the text `switchboard skill-path --own <name>` prints. That opening paragraph is worded the same in every skill, and `tests/it/skill_path.rs` checks it and the hand-offs, so a new skill gets it and a new hand-off goes through `skill-path`.

`.claude/skills/` holds Switchboard's own project skills, for working on this repository: Claude Code loads them only in sessions here and in its worktrees, and they aren't in `assets/skills/`, so the binary never carries them, `switchboard setup` never writes them and no user gets them; being the repository's own copy, they don't open with `skill-path`. `review-pr` is one, started as `/review-pr <pr>` or from `M-p`'s "Review a contributor's PR", which `src/cmd/work.rs` lists only in a repository with the skill: it reviews and tries someone else's PR without running its code outside the sealed try (`wtpr --untrusted`, `switchboard pr-risk`, `/review-loop` from outside the worktree, `switchboard try --sealed`) and drafts the review, so a change to those commands' flags or output belongs in it too. `design-docs` is another, started as `/design-docs`: it holds each board's source in `docs/design/src/` (a `<Name>.dc.html` each and `canvas.json`, copied once from the UX 2.0 canvas, a claude.ai Design artifact now kept as an archive) to the design's made-up names, writes each board as a static HTML page in `docs/design/` with its own `scripts/render.js`, which GitHub Pages serves from main's `/docs` at https://cquinones100.github.io/switchboard/design/ (leaving the sources out, `docs/_config.yml`), and rewrites `docs/design/README.md`, whose commits land through a PR as any change does ("Committing", below); those pages are its output, never edited by hand, and a board changes in its source. `push-unreviewed` is a third, started as `/push-unreviewed` and only by you, for a push past the review rule ("Pushing", below).

## This repository's own tooling

`.githooks/pre-push` refuses a push to `main` that `/review-loop` hasn't found clean ("Pushing", below), which guards a push straight to `main` by an admin and nothing else. It runs only where the clone's `core.hooksPath` points at its `.githooks` by its full path, so run `git config core.hooksPath "$PWD/.githooks"` at the top of every new clone, and once in a clone set up with the relative `.githooks` this once said. The full path because git reads a relative hooks path from the top of the worktree a command runs in: in a worktree on someone else's branch (a fork's PR opened `wtpr --trusted`) a relative one runs the hooks that branch carries, on your next checkout, commit or push there, where the full path runs the main clone's own; a worktree `wtpr --untrusted` makes has hooks off in its own config whatever this says. The hook asks `switchboard` (the one on the PATH, else the build of the clone the hook is in, never the worktree's) for the `review_before_push` setting and the reviewed patch.

This repository's `.claude/settings.json` runs `.claude/hooks/enforce-push-review.sh`, which refuses `git push --no-verify`, a push that names `hooksPath`, `switchboard setting review_before_push` with a value, and a command that finds or writes the review's record (`review-loop-clean`, `review-loop-streak`), and `.claude/hooks/enforce-git-hooks-run.sh`, which refuses `git commit --no-verify` (or `-n`) and any change to `core.hooksPath` (`git -c`, `--config-env`, `GIT_CONFIG_KEY_<n>`, `GIT_CONFIG_PARAMETERS`, `git config`), before every command, so they apply to any Claude working here and nowhere else. Both run from the main clone (`${CLAUDE_PROJECT_DIR%/.claude/worktrees/*}`), never a worktree's copy, so they keep running in a session whose worktree a landing removed, and a branch can't run its own version of them. Both read every line of a command, and refuse when `jq`, which they read Claude Code's JSON with and a clone working on Switchboard needs, is missing or the JSON can't be read. The same file denies Claude's Edit and Write on `.githooks/`, `.claude/hooks/`, itself and the review's record. The record is `switchboard codex-review`'s to write, after two clean rounds of the same commit and base, the second its confirmation round; the skills read it with `codex-review --recorded` and move it to a squashed commit of the same tree with `--record-squash`. `.claude/settings.local.json` is each clone's own and ignored, never tracked, since what it allows would reach every clone.

A release is a version bump on main: bump `Cargo.toml` in a commit of its own (`cargo check` updates `Cargo.lock`), and once that commit is on main `.github/workflows/release.yml`, finding no release of that version, builds it, signs each archive with the release key, tags it `v<version>` and publishes the release, with the `install.sh` of the commit released beside the archives, signed (in a namespace of its own, `switchboard-installer`) and with its checksum, which is the one the README installs from (`releases/latest/download/install.sh`), never `main`'s; `install.sh` installs the binary and leaves `switchboard setup` as a step of its own, unless `SWITCHBOARD_SETUP=1` is set. Switchboard is under the MIT license (`LICENSE`, and `license` in every crate's manifest). The key's private half is the `RELEASE_SIGNING_KEY` secret of the repository's `release` environment (an OpenSSH Ed25519 key, unencrypted), which only `main` may deploy from, and never a repository-wide secret, since only the environment keeps it from a workflow someone rewrote on another branch; and its public half is in `src/update/release-signing-keys.pub`, which the binary compiles in, and in `install.sh`'s `RELEASE_KEYS`, which a unit test keeps the same; a run without the secret, or with a key not listed there, fails before publishing. `switchboard update` offers only the newest release, so a binary trusts only the keys it was built with: replace the key only when it is lost or leaked, by listing the new public key beside the old one (in the installer checks the README and the diff's and Notes' READMEs show too, one `allowed_signers` line a key, which a unit test keeps listing every key), releasing with the old, then signing with the new, and know that a binary which skipped that release refuses every one after it, so its user installs again with `install.sh`, which carries the new key. So the bump's commit is the release: merging its PR publishes, so the push that adds it is always asked about as a release, to an open PR too. The version bumped is the workspace's (`[workspace.package]`, the first line of `Cargo.toml` that sets a version, which the workflow reads).

The diff releases apart from Switchboard, by the same rule: a bump of `crates/diff/Cargo.toml`'s version in a commit of its own, once on main, makes `.github/workflows/release-diff.yml` build `switchboard-diff` alone, sign `switchboard-diff-<version>-<target>.tar.gz` for each target with the same key in the same `release` environment, tag it `diff-v<version>` and publish it, never as the repository's latest release, which stays Switchboard's (`install.sh` reads that one, and `switchboard update` reads only `v<version>` tags). So that bump is a release too, the push that adds it asked about as one. A version ending `-dev` is never released, which is how the crate sits between releases; `install.sh --diff` installs the newest `diff-v` release, and `switchboard-diff update` a newer one over it, the workflow building with `SWITCHBOARD_RELEASE` set so only a release looks for one by itself. Notes releases the same way: a bump of `crates/notes/Cargo.toml`'s version makes `.github/workflows/release-notes.yml` publish `switchboard-notes-<version>-<target>.tar.gz` under `notes-v<version>`, which `install.sh --notes` installs, so that bump is a release too, asked about the same way. A tag pushed by hand releases nothing: the workflow runs only for main.

## Pushing

A change's branch is pushed to open its PR. Ask before a branch's first push, which makes it public; once its PR is open, push each new commit on it as it is made without asking, so the PR stays up to date, except a push that adds a version bump (Switchboard's, the diff's or Notes', below), which publishes a release once auto-merge lands it and is always asked about. Before that first push, run `/review-loop` on the branch, unless Settings' "Review before pushing" (`review_before_push`) is off, so the PR opens on a reviewed change: review each commit as it is made, running the loop on it before starting the next and folding the round's fixes into that commit while it is unpushed, so each commit carries its own review rather than a pile of commits getting one loop and a batch of fixes at the end. The repo is public, so before the first push also run `switchboard leak-check <base>..HEAD` on the branch, which finds what identifies the user or their employer that a script can (the words in `~/.config/switchboard/leak-check.txt`, never in this repository, ticket IDs, PR numbers, home paths, addresses, token shapes, in a file only when the range's base doesn't already have them in its copy of it), and read the diff by eye as the second check, for organization or company names, ticket IDs, PR numbers, internal hosts, usernames, personal paths and tokens; never write such a detail into a commit, its message or the PR. A commit pushed after the PR opens (a follow-up, a fix `/queue-and-clean` makes for a failing check) gets the same before its push, `/review-loop` and `switchboard leak-check` on what it adds, since auto-merge lands it on `main` as soon as CI passes and nothing holds the merge for a review afterwards. The same goes for everything else that reaches GitHub, not only commits: an issue's title and body, a PR's title and description and each edit of them, a comment on an issue or PR, a review and its comments, a release's notes. Write the text to a file in the scratchpad and run `switchboard leak-check --file <file>` on it (or pipe it to `--file -`), fix what it finds or ask about it before posting (a hit on this repository's own issues and PRs is no leak), and read it by eye as the second check. `/queue-and-clean` opens the PR when the branch has none, turns on its auto-merge, and fixes and pushes what stops it merging.

A push straight to `main` is an admin's, which branch protection lets through (`enforce_admins` off), and Claude never makes one: every change lands through a PR, design-docs' `docs/design/` commits included. `.githooks/pre-push` and the review's record guard that push and nothing else: the hook refuses a push to main whose tip isn't the commit `/review-loop` last found clean, or whose review started past where main is on the remote (both recorded by `codex-review` itself in the clone's record, `git rev-parse --git-path` of it, from its `reviewedCommit` and `mergeBase`, after two clean rounds; no session writes it), unless "Review before pushing" is off. The one exception is the reviewed change rebased onto a newer main: a push of one commit, straight on main on the remote, whose change from main on the remote has the review's `patchId` (the third field, `switchboard codex-review --patch-id`, context lines included) and whose message is the reviewed commit's counts as reviewed; the hook also lets through a push whose every commit changes only `docs/design/`, an admin's own push of the design's pages. The skill offers to squash the loop's own commits; a squash that leaves the tree exactly as reviewed records its new commit in their place, with the same base (`codex-review --record-squash`), and one that changes it records nothing. Claude can't skip the hook: this repository's `.claude/settings.json` refuses a push that skips hooks, changing git's hooks path and writing the record, and denies editing the hooks, so it applies to any Claude working here and nowhere else. The way past it is yours alone: turn off "Review before pushing", or run `/push-unreviewed`, a project skill only you start (`.claude/skills/push-unreviewed/`), which checks the unpushed commits as above and puts the push, with the flag that skips the hooks, on your clipboard for you to run in your own shell, never running it itself. A direct landing's own pushes (its `ci/land-<id>` branch with `testIn` `ci`, and autopilot's "Land without asking" through `switchboard land-lock push`) belong to a repository that lands straight on its default branch, never this one.

A review loop here spends its rounds on what someone would hit in normal use. Start its notes file with this standing line, so the reviewer rates such findings low: `- Known gap: findings that need an unusual case (two events within the same moment, a terminal of unusual size or one resized mid-action, a name holding control characters or odd Unicode, permissions changed underneath, a signal sent by hand) are low here unless normal use hits them (the user's rule for this repository)`. Triage the same way: a medium of that kind is treated as low, so it is neither asked about nor fixed, outside a confirmation round as in it, and goes in the final report with the other lows. A fix that only closes one of them is not worth the round the reviewer then spends on the new code.

## Committing

Make each change on a branch in a worktree of its own (`wt`, `wtn`, `wtb`), never in the main clone on `main`, and land it through a PR that `/queue-and-clean` opens and auto-merges once every required CI job passes; `main` requires a PR's branch to be up to date with it, so a PR left behind by another's merge is brought up to date first, `main` merged into its branch and pushed, and its CI runs again. Each change gets a commit of its own, and nothing pushed is amended or reordered, since that rewrites public history and needs a force-push. A commit's message is a short subject line, a blank line, and a paragraph in prose on what changed and why.

Asked to squash unpushed commits, make one commit per feature, its message a description of the feature as it now stands, in prose, and keep other features' commits apart. Check the squashed commits' added lines and the new message for identifying details, as before a push (a real PR number in a test becomes 12345). Branch a `backup/pre-<what>` first, rebase with `--autostash`, and after the rebase check that the tree equals the backup's and that the tests pass at every rewritten commit, run in a temporary worktree.
