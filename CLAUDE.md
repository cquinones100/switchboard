# Switchboard

Switchboard, called editor-configs until October 2026, is a terminal workspace for working with coding agents: one Rust binary, `switchboard`, that is its own terminal multiplexer with a server, and has the sidebar, mission control, the palette, the PR and ticket views, the diff viewer, the notes app and the Slack relay built in. `switchboard` alone starts the workspace or attaches to it; `switchboard <command>` runs everything else. It was a tmux setup with Node, shell and Lua scripts until the rewrite, which replaced every part and removed them; each module's opening comment names the files it came from, which git's history still has.

[README.md](README.md) is the front page for someone new (what it is, the requirements, installing, the first keys, the files of your own); [docs/guide.md](docs/guide.md) describes every feature, key and command; [ARCHITECTURE.md](ARCHITECTURE.md) describes the code, and ends with what the binary doesn't do yet. Keep all three in step with the code: a new or changed key (`src/mux/keys.rs`, a part's `Command`), command (`src/cmd/mod.rs`'s `COMMANDS`, `src/mux/commands.rs`), setting (`assets/settings.json`) or file of your own belongs in the guide, and the README's keys, requirements and install steps follow `keys.rs` and `install.sh`.

A rule for one part goes in its file there (a new part gets a file of its own, with `paths:` naming files that exist, which `tests/it/claude_rules.rs` checks), never here.

- `architecture.md`: the server's one task, each part's shape, panes, apps in panes, commands, persistence, where things live, and the rules every module keeps (nothing on the drawing path waits, GitHub and Linear, links, the request audit, presence, macOS and Linux, other apps' configs, files).
- `plugin-boundary.md`: the crates and what crosses between a plugin and the workspace.
- `claude-settings.md`: Claude's state from its hooks, and Claude Code's settings and permissions.

## Building and testing

The Rust is pinned in `rust-toolchain.toml` (`rustup toolchain install` in the clone). Before every commit:

- `cargo fmt`;
- `cargo clippy --all-targets`, with no warnings (CI runs it with `-D warnings`);
- off a Mac, `cargo check --no-default-features --target aarch64-apple-darwin` (`rustup target add aarch64-apple-darwin` once), which type-checks every macOS path from Linux, since the `net` feature holds the only C the build compiles. On a Mac, clippy already checks those paths, and a check naming the target would compile every crate again in a directory of its own.

The repository is a Cargo workspace whose `default-members` are every crate (`switchboard` at its root, and `crates/ui`, `crates/plugin-api`, `crates/diff` and `crates/notes`), so `cargo fmt`, `cargo clippy --all-targets` and `cargo test` cover them all with no flag, and `cargo build --release` still makes `target/release/switchboard`, with `switchboard-diff` and `switchboard-notes` beside it. `switchboard-ui` and `switchboard-plugin-api` take the workspace's version (`[workspace.package]`, Switchboard's); the diff and Notes each have their own.

Each worktree builds into its own `target/`, never one shared with another checkout: cargo keys the `switchboard` crate's own units without the checkout's path, so one worktree's build would count as fresh for another. With Settings' `worktree_clone_build` on (off by default), a new worktree's `target/` starts as a copy-on-write clone of the main clone's (`src/cmd/clone_build.rs`), still its own: cargo rebuilds the worktree's crates, whose sources are newer than the clone, and reuses the dependencies without a build script, which share the main clone's blocks until a build changes them; build scripts and their output aren't cloned, so those dependencies (aws-lc-sys's C among them) and the ones built on them build again. Beyond that, a computer with many worktrees may set sccache as cargo's `rustc-wrapper` in `~/.cargo/config.toml`, which serves the crates another worktree compiled.

Builds, test runs and package installs run in a pane go through the queue for heavy work (`src/slots.rs`; the `cargo`, `npm` and `pnpm` first on a pane's PATH are the binary, `src/cmd/slot.rs`), so only Settings' caps of each go at once across the tabs, and one may print "Waiting for a build slot" before it starts.

The tests run once per change, before it reaches `main`, not before every commit: `cargo test`, all passing, is queue-and-clean's step at a landing, and for commits pushed to `main` by hand it runs once before the push question, after the review loop (whose fix commits are covered by that run), since a full run starts thousands of processes on a computer with a security agent and the review loop's rounds would each run it again. A landing may run them in CI instead of on this computer: with `testIn` `ci` in repos.json, queue-and-clean pushes the landing's commit to a `ci/land-<id>` branch of its own and waits for CI on it (`switchboard land-lock test`), running them here only when no CI answers. A build older than the skills it reads from the clone (`src/assets.rs`) stops a landing rather than working around a command it lacks: `switchboard skill-path` says on stderr which `switchboard` commands a skill's `allowed-tools` name that the build doesn't have (`cmd::SUBCOMMANDS` lists the subcommands it knows), and queue-and-clean stops there, as it does on any of its commands printing a usage line, so build and install from main and land again. The landing's CI runs before the review and, after the last rebase, again only when that rebase had a conflict or the default branch's CI is failing: a clean rebase gets repos.json's `afterRebase` instead (here clippy), so the landing lock is held about a minute rather than through a second CI run, and a landing whose change must be reviewed again lets the lock go for the review, waiting first in line (`land-lock requeue`). The tests for the files a change touches are run while working on it (`cargo test --test it <file>::` for a file of `tests/it/`, `cargo test --test <file>` for one of the three apart from it, or a unit test's module), and the whole suite when a change reaches `tests/common`, the server's core or the protocol.

## Testing in the workspace in use

The Switchboard you work in is the one in use, and the person may be typing in it. Before testing anything there (opening or closing a tab, moving focus, sending keys, `switchboard kill-server`, `switchboard upgrade` or restarting the server to load a new build), stop, say that the test needs the workspace and what it will do, and wait for a go-ahead. Test in a server of the tests' own where that can show the same thing.

When a change is ready to try, build it and put it in place of the binary the server runs without asking: `cargo build --release --locked`, then `install -m 755 target/release/switchboard ~/.local/bin/`, where the README and `install.sh` install it, both of which this repository's `.claude/settings.json` allows as these exact commands. When `command -v switchboard` names another path (`SWITCHBOARD_BIN_DIR`, or a binary put elsewhere on the PATH), install it there instead, which asks. With `CARGO_TARGET_DIR` (or cargo's `build.target-dir`) set, the build is that directory's `release/switchboard`, so install from there, which asks too. Work that lands through `/queue-and-clean` (a `/wtn` tab, autopilot) is ready to try once it has landed: build the landing target as it now is (the branch `switchboard landing` names), never the worktree before the landing, which would put code that hasn't landed into the binary the workspace runs. That is the commit the landing pushed (the target's branch on its remote, or the local branch when the target has none), not the local branch when it lags behind. Build it in the main clone when the main clone has the target checked out at that commit with nothing uncommitted (`git status --porcelain` printing nothing), as it normally does after the landing; otherwise in a detached worktree at that commit (`git worktree add --detach <dir> <commit>`), removed once the build is installed, whose install asks since it isn't the exact command allowed. Work tried before it lands, with no landing step, is built in the checkout it is in. Then say how to put it into the running workspace: `M-p`'s "Restart Switchboard on the latest main", which brings the main clone of the checkout the running binary was built from up to date with origin (refusing when it is off its default branch, has uncommitted changes or commits origin lacks) and builds it (a second, with nothing new; not at all when the build installed since the server started was made from that commit or one ahead of it), puts the result in place of the binary the server runs, and restarts the server on the path it started from, or, when that is in a cargo target directory, on `~/.local/bin/switchboard` or else the server's own copy in `~/.cache/switchboard/build`. Restarting it is still the person's to do, as above.

## This repository's own tooling

`.githooks/pre-push` refuses a push to `main` that `/review-loop` hasn't found clean (below). It runs only where the clone's `core.hooksPath` points at its `.githooks` by its full path, so run `git config core.hooksPath "$PWD/.githooks"` at the top of every new clone, and once in a clone set up with the relative `.githooks` this once said. The full path because git reads a relative hooks path from the top of the worktree a command runs in: in a worktree on someone else's branch (a fork's PR opened `wtpr --trusted`) a relative one runs the hooks that branch carries, on your next checkout, commit or push there, where the full path runs the main clone's own; a worktree `wtpr --untrusted` makes has hooks off in its own config whatever this says. The hook asks `switchboard` (the one on the PATH, else the build of the clone the hook is in, never the worktree's) for the `review_before_push` setting and the reviewed patch.

This repository's `.claude/settings.json` runs `.claude/hooks/enforce-push-review.sh`, which refuses `git push --no-verify`, a push that names `hooksPath`, `switchboard setting review_before_push` with a value, and a command that finds or writes the review's record (`review-loop-clean`, `review-loop-streak`), and `.claude/hooks/enforce-git-hooks-run.sh`, which refuses `git commit --no-verify` (or `-n`) and any change to `core.hooksPath` (`git -c`, `--config-env`, `GIT_CONFIG_KEY_<n>`, `GIT_CONFIG_PARAMETERS`, `git config`), before every command, so they apply to any Claude working here and nowhere else. Both read every line of a command, and refuse when `jq`, which they read Claude Code's JSON with and a clone working on Switchboard needs, is missing or the JSON can't be read. The same file denies Claude's Edit and Write on `.githooks/`, `.claude/hooks/`, itself and the review's record. The record is `switchboard codex-review`'s to write, after two clean rounds of the same commit and base, the second its confirmation round; the skills read it with `codex-review --recorded` and move it to a squashed commit of the same tree with `--record-squash`. `.claude/settings.local.json` is each clone's own and ignored, never tracked, since what it allows would reach every clone.

## Pushing

Always ask before pushing this repo, every time, whatever the branch and whatever an earlier push was allowed, but for three cases. The first: a landing whose tests run in CI (repos.json's `testIn` `ci`, the standing answer for it) pushes its candidate commit to a branch of its own, `ci/land-<id>` (the id a hash of the worktree's branch name, never the name), forced, and deletes the branch once its CI has answered, all through `switchboard land-lock test`, as queue-and-clean's "The tests in CI" says, with `switchboard leak-check` run before each such push and anything it finds asked about first, since the commit is public from then on. The second: a tab of autopilot with its "Land without asking" on (`@autopilot_land`), landing on main through queue-and-clean a commit whose change passed the tests on its base and, after a clean rebase, `afterRebase`, two clean review rounds (the pre-push hook's check) and `switchboard leak-check` with nothing found. The push is `switchboard land-lock push` (`src/cmd/land_push.rs`), which pushes `git push origin HEAD:main` itself, with the repository's hooks, only when that tab's mark and those checks pass as it pushes, and asks otherwise. Such a tab's Claude is started with that one command allowed for its session (`wtn`'s `push_rule`, Settings' `autopilot_push_rule`), so Claude Code's auto mode doesn't refuse it. The push after the landing's own question, `land-lock push --asked`, is allowed by no rule (every rule names `land-lock push` exactly, never a wildcard over it), so it gets Claude Code's own judgment (auto mode's, or its permission prompt in another mode), and outside a tab that lands without asking the server answers its PreToolUse hook with an ask besides (`src/agent/hands_free.rs`'s `ask_push`). The third: a push to main whose every commit changes only `docs/design/` (the design's board sources and pages, the GitHub Pages site), made with the design-docs skill's `node .claude/skills/design-docs/scripts/render.js push`, which refuses a range reaching past `docs/design/` or behind main on origin, and pushes only after `switchboard leak-check` finds nothing `made-up.json` doesn't explain (anything else it finds is asked about first), with the commits read by eye before it for what identifies the user, since the site is public; it runs without `/review-loop`, which `.githooks/pre-push` lets through by the same rule (every path any pushed commit touches, both sides of a rename, under `docs/design/`), and without asking, this repository's `.claude/settings.json` allowing that exact command. A change to anything else, the renderer and `made-up.json` included, lands as before. Review each commit as it is made: run `/review-loop` on it before starting the next, folding the round's fixes into that commit while it is unpushed, so each commit carries its own review rather than a pile of commits getting one loop and a batch of fixes at the end; working through a list, push each once it is clean, before the next. Before asking, run `/review-loop` on the unpushed commits, unless Settings' "Review before pushing" (`review_before_push`) is off, which the hook then follows too: `.githooks/pre-push` refuses a push to main whose tip isn't the commit the skill last found clean, or whose review started past where main is on the remote (both recorded by `codex-review` itself in the clone's `review-loop-clean`, `git rev-parse --git-path review-loop-clean`, from its `reviewedCommit` and `mergeBase`, after two clean rounds; no session writes it), so a fix made after the review needs a review of its own, and so does a commit the review left out. The one exception is the reviewed change rebased onto a newer main: a push of one commit, straight on main on the remote, whose change from main on the remote has the review's `patchId` (the third field, `switchboard codex-review --patch-id`, context lines included) and whose message is the reviewed commit's counts as reviewed. The skill offers to squash the loop's own commits before the push; a squash that leaves the tree exactly as reviewed records its new commit in their place, with the same base (`codex-review --record-squash`), and one that changes it records nothing. Claude can't skip it: this repository's `.claude/settings.json` refuses `git push --no-verify`, changing `core.hooksPath` and writing the record, and denies editing the hooks, so it applies to any Claude working here and nowhere else. The way past it is yours alone: turn off "Review before pushing", or run `/push-unreviewed`, a project skill only you start (`.claude/skills/push-unreviewed/`), which checks the unpushed commits as below and puts the push, with the flag that skips the hooks, on your clipboard for you to run in your own shell, never running it itself. The repo is public, so before asking, check the unpushed commits for anything that identifies the user or their employer: organization or company names, ticket IDs, PR numbers, internal hosts, usernames, personal paths, tokens. `switchboard leak-check <range>` finds the kinds a script can (the words in `~/.config/switchboard/leak-check.txt`, never in this repository, ticket IDs, PR numbers, home paths, addresses, token shapes, in a file only when the range's base doesn't already have them in its copy of it), and queue-and-clean runs it before every direct landing's push question; reading the diff by eye stays the second check.

A review loop here spends its rounds on what someone would hit in normal use. Start its notes file with this standing line, so the reviewer rates such findings low: `- Known gap: findings that need an unusual case (two events within the same moment, a terminal of unusual size or one resized mid-action, a name holding control characters or odd Unicode, permissions changed underneath, a signal sent by hand) are low here unless normal use hits them (the user's rule for this repository)`. Triage the same way: a medium of that kind is treated as low, so it is neither asked about nor fixed, outside a confirmation round as in it, and goes in the final report with the other lows. A fix that only closes one of them is not worth the round the reviewer then spends on the new code.

## Committing

Commit straight to `main`: there is no PR flow here, so a branch only adds a merge step. Each change gets a commit of its own, and nothing pushed is amended or reordered, since that rewrites public history and needs a force-push. A commit's message is a short subject line, a blank line, and a paragraph in prose on what changed and why.

Asked to squash unpushed commits, make one commit per feature, its message a description of the feature as it now stands, in prose, and keep other features' commits apart. Check the squashed commits' added lines and the new message for identifying details, as before a push (a real PR number in a test becomes 12345). Branch a `backup/pre-<what>` first, rebase with `--autostash`, and after the rebase check that the tree equals the backup's and that the tests pass at every rewritten commit, run in a temporary worktree.
